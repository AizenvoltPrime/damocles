# Invariants (long form)

Rationale and failure modes behind the one-line rules in `CLAUDE.md`. Read the entry before changing the subsystem it governs.

## Engine and message contract

- pi is the only agent engine; new sessions always construct `PiSession`. There is no harness selection.
- Map pi events to existing webview shapes via `pi-stream-adapter.ts` / `tool-normalization.ts`, never to a new message that mirrors a pi event. Add a message type to `src/shared/types/messages.ts` only for a user-facing capability no existing shape can carry (`steerTargets`, `resumeAccepted`, `sessionUsage`), with its producer and its webview handler in the same change.
- **`sessionUsage` is the only carrier of the status bar's billing totals.** Spend lands outside a completed turn: a stopped turn's partial request, a manual `/compact`, and the cache warmer's idle `usage` entries. `done` cannot carry it there, because the webview finalizes the streaming message on `done`, and `tokenUsageUpdate` is the context meter's last-request snapshot. Both producers build the message with `sessionUsageMessage` (`pi-session/session-usage.ts`): the adapter on every settle (aborted included), on `compaction_end` with a result and on `entry_appended` for an entry that carries usage, and `history-loader.ts` on reload. `done` carries no totals.
- **`/stats` has no session producer.** `requestUsageStats`, `usageStatsProgress` and `usageStats` are produced by `message-router/handlers/usage-stats-handlers.ts` through `UsageStatsService` (`src/extension/usage-stats/`), never by `PiSession`, because the figures aggregate every project and belong to no session. `/usage` sets the precedent: its handler posts straight to the webview. The three types exist because no existing message shape carries cross-project aggregates. The handler sends exactly one `usageStats` with `final: true` per `requestId`, including when validation or the worker fails, so the webview never waits on a request that already ended.
- `Edit` cannot create files (empty `old_string` throws); `Write` is the only creation path.
- Internal sub-calls (memory, structured output) use `PiRuntime.runStructuredCompletion` + the terminating-tool idiom (no `toolChoice`).
- Never mutate `process.env` for per-session config; pi reads a Damocles-owned `agentDir` (`~/.damocles/pi/agent`).
- **Account state has exactly one publisher.** `AccountInfo` derives from five inputs (active model, its catalog entry, Claude auth mode, OpenAI auth status, prefer-API-key) and was emitted once per adapter lifetime from `emitSessionStartOnce`, reached only at turn start. So a session restored from history never received it, and a model or auth change left it stale because the once-guard had already tripped. `PiSession.publishAccountInfo()` rebuilds and emits on demand, and is called wherever an input changes: session start, `setModel`, history replay, and both auth paths. It caches nothing, so it cannot drift from `buildAccountInfo`. A consumer must never paper over a missing publication with a fallback; fix the publisher.

- **`sessionStateChanged` has exactly one publisher, and every input it reads has exactly one mutator.** `PiSession.publishSessionState()` derives the state from the turn lifecycle plus every prompt map on `PermissionState` and `WebviewExtensionUIContext.pending`, and is the only site that constructs the message; the adapter reports the turn lifecycle through `onTurnStateChanged` instead of emitting. Those maps are mutated only inside `permission-handler/state.ts` and `extension-ui-context.ts`, because every mutator also fires the change notifier that reaches the publisher. A direct `state.pendingApprovals.delete(id)` in a manager (the shape seven abort handlers used before this rule existed) type-checks, keeps every test green, and parks the session on `requires_action` for the rest of its life with no dialog on screen, which is worse than the missing signal it replaced. `session-state.test.ts` ("single-writer discipline") walks every `.ts` file under `src/extension`, allows the mutation only in `permission-handler/state.ts`, and enforces both halves. A consumer must never infer the state locally to paper over a missing publication; fix the publisher.

- `src/shared` must not depend on `src/extension`, and that includes its tests. `tsconfig.webview.json` compiles `src/shared/**/*` for the webview bundle, so a file under `src/shared/__tests__` that imports extension code drags the extension host into the webview typecheck and fails the gate. A test whose subject is shared but which must read extension state belongs on the extension side; split it rather than moving it.

## Deferred tools / ToolSearch

- Browser/Compass/Web/MCP tools are deferred: registered but inactive, activated only via `ToolSearch` (`tools/deferred-tools.ts` is the leaf that owns the universe). They must stay in pi's `tools:`/eligible set. Dropping a name removes it from the registry and `setActiveToolsByName` silently ignores unknown names, so it could never come back. Deferral is only safe where `ToolSearch` is actually registered; gate on that, never on it merely being allowed. A ToolSearch group equals a Tools-panel subsystem: the whole subsystem defers or none of it does, so there is one rule for the model and one line in the menu.
- The deferrable universe composes from leaf spec modules only, never a barrel. `deferred-tools.ts` documents itself as composing the `*_PI_TOOL_NAMES` exports and importing nothing else, and `tool-search.test.ts` ("deferred-tools.ts import discipline") enforces it to keep the eval-time cycle `permission-gate` → `tool-catalog` → `browser-tools` closed. A barrel that re-exports a `vscode`-importing config module (as `web-access/index` does) forces that guard to be relaxed to "any import is fine", retiring it for every future group. Add a `-tool-specs` declaration leaf instead. The reason is guard preservation, not startup cost.
- A system prompt must never name a deferrable tool without stating how to load it. A deferred tool is not callable on turn one, so a prompt that names one without an adjacent `ToolSearch({tools:["<group>"]})` step is a dead end. The model calls it and gets an unknown-tool error. This held in five places at once (`system-prompt.ts`, `plan-mode-guidance.ts` ×2, `subagents/default-agents.ts`, `compass/system-prompt.ts`); the subsystem's enabled-ness is no defence, since that flag is exactly what makes the names eligible and deferred.
- ToolSearch republishers retire deterministically, never by exception, and every registered closure has exactly one owner responsible for retiring it. Which owner applies depends on whether an `AgentSession` ever binds the extension instance that registered it, and the two cases are genuinely different. Do not collapse them:
  - **Session-bound instances retire themselves.** `PiRuntime.registerToolSearchRepublisher` returns a disposer the instance calls from its own `session_shutdown` handler, for every reason, `'reload'` included. This deliberately diverges from the observe-only lifecycle handlers in `hooks/index.ts`, which skip `'reload'` because an internal rebuild is not a user-meaningful session end; here a reload genuinely retires the instance.
  - **Unbound instances are retired by `PiRuntime`.** `resourceLoader.reload()` also runs the extension factory where no bind follows, at four sites: the `.damocles`/`.claude`/`.codex` asset watcher, the workspace-trust grant, `_hotReloadExtensions`, and `_removeSubscriptionPlugin`. `createAgentSessionServices` also mints one at init before any session exists. Such an instance receives no session event at all, so there is no owner inside it. `_reloadResources` takes a `ReloadBinding` argument stating which kind of reload it is, and the runtime holds the unbound instance's disposer in `_unboundRepublisherDisposer`, retiring it the moment the next successful reload supersedes the instance. `prepareSessionExtensions` is the announcement that a session is about to bind whatever the loader currently holds, so it releases that claim (without retiring) on every exit path. That includes the first-session path that does no reload at all, and the path where the reload failed. Releasing is not optional politeness: a claim kept on an instance that has since gone live would retire a live panel's republisher on the next reload.
- Never infer a republisher's deadness from a throw: it retires live panels on unrelated failures, and it cannot see an unbound instance at all, whose `registerTool` succeeds into an unreferenced extension object and so never throws. Growth is the visible symptom. A window that never retires an unbound instance invokes a longer list of dead closures on every settings toggle.
- Every bind of the shared services must be announced by `prepareSessionExtensions()`. It is the handover point, so a bind that skips it leaves the runtime claiming a live instance as unbound and the next bare reload retires a live panel's republisher. `PiSession`'s session factory announces; `PiRuntime.createSession` does not announce for you, so any future caller of it must. Nested subagent/team sessions are exempt by construction, not by luck: `createSubagentSession` builds its own `AgentSessionServices` with its own `extensionFactories`, so it never binds this loader's instance and never registers a republisher into the shared set.
- Nested (subagent/team) MCP tools are delivered as `customTools` on `createSubagentSession`, never through the shared MCP registrar. And that is what preserves the exemption in the bullet above, not a workaround despite it. `customTools` are read during construction, so a nested session still binds no shared loader instance and still registers no republisher into the shared set. "Simplifying" this into sharing the registrar reopens exactly the bug class the republisher-ownership model was built to close; do not, however much simpler it looks.
- A nested agent's MCP set is frozen at spawn: one `getAllToolDescriptors()` read per spawn, from which its `tools:` names, its `customTools` definitions, its gate read-only classifier, its deferrable set and its ToolSearch blurbs are all derived. A second read anywhere in a spawn path reopens the divergence window. An `mcp__*` name in `tools:` with no matching definition is dropped silently (no error, no warning, no log), so set-equality between the two is what catches it. Asserted at both composition sites (`pi-session.ts`'s subagent and team engines), because a test that reaches only one of them leaves the other free to regress while the suite stays green. `createSubagentSession` also logs any orphan it is handed, since every nested spawn funnels through there and that is the one place the class is observable at runtime. A server connecting mid-run reaches the next spawned agent, never a running one; there is no live top-up. Each frozen tool also carries the `serverId` it was captured from and calls with `expectedServerId`, because tool-name prefixes are reassigned live (a user server made visible takes its prefix back from a folder server): a name that has passed to another server fails as vanished rather than running that server's tool under the snapshot's read-only classification. (The freeze is over the descriptor set, not connectivity. A server still connecting but with cached descriptors is in the snapshot and callable, since `callTool` awaits `ensureConnected`.)
- The nested MCP grant is uniform across every agent type and mode. Explore's explicit list, `tools: *`, and team specialists all get the panel's full eligible set. MCP names are dynamic and deployment-specific, so no agent author can name them in frontmatter; intersecting with the agent's `tools:` would give the explicit-list agents none. `disallowed_tools` is the one opt-out, and it is exact and case-sensitive (`mapName` passes unknown names through unchanged). A later "fix" that lowercases `mapName` would silently break every MCP denial.
- Every `_reloadResources` call is serialized on `_reloadSync`, and the ownership rules above depend on that serialization, not just on `extendResources` ordering. A reload identifies the instance it minted through a single scratch slot written by `registerToolSearchRepublisher`; two overlapping reloads would let one adopt the other's instance, and adopting a session-bound instance as unbound freezes a live panel's ToolSearch menu with no error anywhere.
- accepted, documented in `damocles-extension.ts`: `AgentSession.reload()` emits `session_shutdown({reason:'reload'})` before awaiting the loader reload, so a reload that throws leaves the still-live panel with its republisher removed and no replacement. Silently, since `runMcpReload` catches and logs. It self-heals on the next successful `session.reload()`. Do not add recovery machinery for it unless it is actually observed; the fix would be idempotent re-registration from a `session_start` handler guarded on the disposer being undefined.
- **An extension instance is process-global and outlives any one session, so its `session_shutdown` handler retires only what the instance owns outright: the ToolSearch republisher above. Its event handlers stay registered.** `SessionShutdownEvent` carries no session id (`types.d.ts:479-484`), so an instance-wide response to it answers for every session bound to that instance, including the one that binds it next. That next session is reachable, because a failed `prepareSessionExtensions` reload leaves `getExtensions()` returning the previous array (`resource-loader.js:328`, `pi-runtime.ts:679-684`). Retiring the handlers empties the instance's map (`loader.js:202-219`), and pi then skips the gate outright rather than calling it, since `beforeToolCall` treats `hasHandlers('tool_call') === false` as proceed (`agent-session.js:233-236`), so the session runs with no permission gate, no system prompt injection, no checkpoints and no hooks. Ownership is decided per dispatch by the session-keyed registries, `_panelRegistry` and `_checkpointRegistry`, never by instance-wide state. A tool call that finds no panel is blocked by `gateErrorFallback` rather than proceeding, because only main panel sessions dispatch into this instance and each is registered until its panel closes. The per-subagent instance retires nothing at all, since `createSubagentSession` gives each spawn its own services and loader and a nested session is disposed without an `AgentSessionRuntime` to emit the event. `handler-disposal.test.ts` pins three things: the handler count is unchanged after every shutdown reason, a session bound after a shutdown still gets its gate, prompt, checkpoints and hooks, and an unowned tool call is blocked.
- A tool's `description` is materialized at wrap time, not per request (`wrapToolDefinition` copies it as a plain string). A getter alone does not stay fresh: `pi.registerTool` is the only public re-wrap trigger, so anything whose description tracks live config must be re-registered (`FolderRuntime.republishToolSearch`, driven by `refreshActiveTools()`).
- Whatever `ToolSearch` advertises must be exactly what the session can load. The menu, the retry hint, the activation result and `/context` all derive from one loadable snapshot. Report what pi actually activated (re-read after activating), never what was requested. MCP tool names/descriptions are third-party text rendered into a line-structured menu: strip control chars at build time or a name forges a group line.

## Tool overrides

- A custom tool registered under a pi built-in's name replaces it. `_refreshToolRegistry` seeds the built-in definitions first, then writes every custom tool into the same map, so the last write wins. That is the only seam Damocles has for changing a built-in's behaviour, and it fails silently in both directions: a name that does not match exactly registers a second tool instead of overriding, and a built-in renamed upstream leaves the override in place as a tool nothing calls. `bash` is the live case, owned so a per-call `AbortController` can reach the running command.
- An override keeps the built-in's exact name, lowercase `bash` included. The permission gate classifies by the mapped name (`permission-gate.ts:188-189`, through `mapPiToolName`), and `PI_NATIVE_ACTIVE_TOOLS` plus every subagent and team toolset carry the pi spelling, so renaming to `Bash` means changing the gate, plan-mode classification, the read-only shell classifier, the active-set lists and the tool catalog together, and whichever one is missed fails open rather than loudly. `Edit` renamed because its schema had to diverge from pi's; bash's does not, so it has no reason to pay that price.
- Never pair an override with an `excludeTools` entry. `isAllowedTool` filters custom tools through the same allow and exclude sets as the built-ins, so excluding `bash` drops the replacement along with the original and leaves the model with no shell at all. The `edit` exclusion is not a precedent for it: that one is safe only because the replacement registered under a different name.
- Reading a host service at construction rather than at execute makes that service a precondition of building the session, not of running the tool. `createBashTool` spreads its metadata from a delegate built during `buildCustomTools`, so `createBashToolDefinition`, `getShellCommandPrefix` and `getShellPath` must all answer before a `PiSession` exists at all; four test files needed their doubles extended when the override landed. The symptom is a `TypeError` several frames inside session construction, naming a method rather than the tool that asked for it, and every later assertion then fails on a null session, so the cascade points nowhere near the cause. Suspect an incomplete double before suspecting the session. The construction-time read is still the right trade, since it is what keeps the model-visible schema and the system prompt identical to pi's, but the cost lands on whoever writes the next session test.

## Shell cancellation and process lifetime

- **A cancelled shell call says so in exactly one place: `details[CANCELLED_TOOL_DETAIL_KEY]` on the tool result** (`src/shared/types/session.ts`). `withPerCallCancel` sets it on both exit branches, merged over `lastPartial?.details` so the partial's `fullOutputPath` and truncation fields survive rather than being replaced (`tools/cancellable-shell.ts`, `cancelledDetails`). Both branches return a normal result, never an error, because the user asked for the stop and the retry heuristics that treat an error as worth retrying must stay quiet; so a cancelled call always lands as `toolCompleted` and the marker on `details` is the only thing that tells the card apart from a success. It rides on `details` because `details` is persisted and re-read on reload, which view state is not, and because the cancel registry releases its entry in a `finally` that runs before pi emits `tool_execution_end`, so a registry side-channel keyed by tool call id could not answer at the time the card is built. The guarantee is only as good as its producers, and there are three: `pi-stream-adapter.ts` and `subagents/subagent-stream-bridge.ts` emit `toolMetadata` from `result.details`, and the team path carries it on `teamAgentToolResult.metadata` (`src/extension/team/agent-runner.ts`), which was added because the team path dropped `details` outright and rendered a cancelled command as a green check. A new producer that does not carry `details` reopens exactly that. The reload path is a fourth producer and needs the marker too: `agent-runner.ts` persists a `tool_result` entry per call carrying `content`, `is_error` and the normalized `metadata`, and `useTeamStore.handleAgentDataLoaded` indexes those by `tool_use_id` and derives the same three statuses the live path shows. Persisting `content` alone would leave a reloaded cancelled call indistinguishable from a success, which is what the hardcoded `status: 'completed'` it replaced did to cancelled and errored calls alike. A call with no persisted result restores as `unrecorded`, a terminal status of its own: `completed` would claim an outcome that was never recorded, while `pending` and `running` are pre-terminal and put a spinner, a Stop control and a "Tool is running..." overlay on a tool that ended long ago. The main-session replay path derives the same status from the same fact (`convertHistoryTools`, `src/webview/composables/message-handler/utils.ts`), and so does the subagent transcript loader (`buildChatMessagesFromHistory`, `src/webview/stores/useSubagentStore.ts`), which is why `unrecorded` lives on `ToolCall['status']` rather than inside any one loader. `handleAgentDataLoaded`, `convertHistoryTools` and `buildChatMessagesFromHistory` all read a transcript whose run is over. The subagent one is reached only by a resume from disk and by the single `subagentMessagesUpdate` the stream bridge emits from `finish()`, so a block with no recorded result is unrecorded rather than still running. The live subagent path is a different function, `buildToolCallsWithStatus`, which sees a `tool_use` block before pi has started the tool and so defaults to `pending`, never to a terminal status. Team logs written before this landed hold no `tool_result` entries and cannot be repaired.

- **A cancel note is user turn content, delivered to the agent that ran the command, and never executed.** It is never appended to the tool result. A tool result is untrusted by construction, so an instruction found in one is prompt injection, and a correctly aligned model refuses it; that was observed, not predicted, before the note moved. The trailer says only that the user cancelled, how long the command ran, and that a reason follows. Delivery is bound per build context (`note-delivery.ts`, one builder per context, one `PiSession` method per builder), so the target is fixed when the tools are built rather than guessed when Stop is clicked: the panel session queues it through `sendUserMessage`, a subagent takes the steer channel a typed `/steer` uses, and a team agent takes `deliverUserNote`, the sink its own runner publishes for the duration of its run. A single delivery for all three would land a subagent's note on the main conversation. `expandPromptTemplates: false` is the whole leading-slash guard: it switches off the extension-command dispatch and the skill and template expansion inside `prompt()`, so a note beginning with `/` is queued as literal text and cannot be executed or throw. Do not swap it for `followUp()`, which runs `_throwIfExtensionCommand` unconditionally, nor for string mangling of the user's text. The same binds any path that puts a note back into pi's queue after taking it out, and any path that prompts queued content through `prompt()`, whose `expandPromptTemplates` defaults to true where `sendUserMessage`'s defaults to false. `resteerQueuedInputs` preserves follow-ups through `sendUserMessage(..., { expandPromptTemplates: false })`, and the team runner sends every flush of queued content through one wrapper that passes false. A note is the one queued string with no `[Message from X]:` prefix to make a leading slash impossible. Sanitization follows the trust level rather than the source: `stripBidiControls` stays because a human renders the note, `stripControlChars` is gone because it flattened the newlines the note box now lets the user type, and the 500 character cap is gone because truncating changes what the user asked for. No cap replaced it at any layer, and that is deliberate: `sanitizeCancelNote` strips and trims only (`tools/shell-cancel-registry.ts`), the note textarea carries no `maxlength` (`ToolCancelControl.vue`), and the router forwards `msg.note` unchanged (`chat-handlers.ts`, the `cancelToolCall` handler). The note is one human-authored message delivered to the agent as user turn content, so a cap can only drop the end of a reason the user meant the agent to read. Exactly one user-visible echo per context, `userMessage` for the panel, `subagentSteered` for a subagent, `teamAgentUserMessage` for a team agent. Zero echoes makes the model act on an instruction the user cannot see in the transcript; two double-render it. The team seam deliberately bypasses the `MessageBus`. A note sent through the bus is dropped with no signal to the sender once the run's `unsubscribeBus()` has fired, and again when the sender token equals the agent's own name, so the sink returns false instead and the caller logs it. The panel's echo is emitted when pi accepts the note, not when the delivery is called and not when pi delivers it, which is the last point still synchronous with the click and is where the subagent and team contexts echo too. A path that takes an accepted note back out of pi's queue owes the user a correction, which is what `stopForBudget` emits when it drops the queue to hold the budget bound.

- **The shell process-lifetime path has no timer, interval or process-table read on any platform, and neither arm carries shell-specific knowledge** (`tools/process-tree.ts`). Windows puts each spawned shell in its own job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and terminates it explicitly on abort; POSIX signals the process group, which works because both shell tools spawn with `detached: process.platform !== 'win32'` (`tools/bash-tool.ts`, `tools/powershell-tool.ts`, carried over from pi's own bash tool at `packages/coding-agent/src/core/tools/bash.ts` in pi 0.87.0) and a non-interactive bash leaves its background jobs in that group. **Two things are carried over from that tool, not invented here, and both have to move when it moves: the `detached` flag, and the exit code a signal-killed shell reports.** Damocles reimplements the operations so it can name the pid, so it owns the second one too: a null exit code becomes `128 + <signal number>` when a signal named the termination and `1` when none is named, applied where the tracked bash operations return, after the abort and timeout throws, and in the PowerShell `close` handler. The parity is behavioural rather than textual, and describing it as "the same code" is how the next editor gets it wrong. pi reads `child.signalCode` after its wait resolves; Damocles captures the signal in its `exit` handler and carries it out of `waitForShellExit`, which resolves `{ code, signal }` for that reason. Only an external kill reaches the mapping in the bash tool, because the abort and timeout throws still precede it, so `aborted` and `timeout:<seconds>` are unchanged and a cancelled or timed-out command still reports no exit code. PowerShell resolves a run object instead of throwing, so its timeout branch returns before the exit-code line; without that ordering a timed-out command would gain a trailing `[exit code 137]` and the timeout text would change. A null exit code no longer passes as success in either direction: pi's tool body throws `Command terminated without an exit code` on one, and neither Damocles spawn site can report a terminated shell as a null exit code. `bash-operations.test.ts` > "an externally killed shell" pins the two implementations to the same answer rather than to a fixed number, because win32 reports a plain exit code where POSIX reports a signal. Job membership is inherited and cannot be escaped, `BREAKAWAY_OK` deliberately unset, so a severed parent link stops mattering and the kernel walks nothing. Two earlier designs were tried and deleted, a process-table poller and an MSYS `ps -W` group lookup, and both were compensating for not having that one property; the measurement that killed the poller is that the fork helper lives about ten milliseconds while the cheapest query reporting parent links costs 384ms, so no polling rate can observe the link. `createShellJob(pid, shellJob)` must stay the first statement after `spawn` in both shell tools: the two assignments cost 0.13ms and Git Bash forks its background jobs 10 to 20ms in, so the margin is about a hundredfold, but a child created before assignment is outside the job permanently and unkillable. The no-running-cost rule is asserted, not argued, by `bash-operations.test.ts` > "no running cost in the process-lifetime path", which drives a full call including the abort and pins the global `setInterval`, `node:timers` and `node:timers/promises` all uncalled plus exactly one spawn; a poller reaching for any of the three goes red, checked by reintroducing one.
- **The Windows jobs are nested, and only the outer one kills on close.** A call job holds one shell call; a session job holds the panel and carries `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. The two ways a call job ends are not symmetric and must never be described together. Stop terminates it, which kills every member, the background jobs the command left included, and reaches nothing outside that call; that is the defect this exists to fix. The end of a normal call merely releases the handle, which kills nothing. The whole difference is one `TerminateJobObject`, and grouping the two is how a reader concludes that Stop leaks. **The rule that keeps this correct is that the call job never carries kill-on-close**: releasing its handle at the end of a call has to leave a deliberately backgrounded process running, which is what makes Windows match the POSIX process group, and adding that one flag is the silent undo (it reads as harmless and turns the "outlives its call" case red, which is how it is pinned). The assignment order, session job then call job, is convention and not the thing keeping this correct: reversing it was mutation-tested and every case still passed, because the shell ends up a member of both jobs either way. Do not write, or rely on, "the order forms the nesting". `BREAKAWAY_OK` stays unset, since a child that could leave defeats the design.
- **The session job is per panel, held on `PiSession`, and there is deliberately no module-level instance.** One panel is one `PiSession` and a user can have several open, so a host-wide job would either kill another panel's commands when one panel is disposed, or, if never closed, degrade session cleanup into host-exit cleanup. Neither failure shows up in a single-panel test. Its lifetime is the panel and not the conversation: `PiSession` survives `reset()` and `clear()`, so tying the handle to the pi `AgentSession` would make `/clear` kill a process the user backgrounded earlier, which is the exact behaviour the nesting exists to preserve.
- **State the parity, then name the mechanism, because they are not the same thing.** Stop, background survival, cleanup at session dispose and cleanup after a host crash now behave the same on Windows, Linux and macOS. The mechanisms differ and must never be collapsed into one sentence. Windows nests job objects and gets the dispose and crash cases from `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` on the outer one (`tools/process-tree.ts`). POSIX has no job object, so `createShellSessionJob()` returns a sentinel-backed handle instead (`tools/shell-sentinel-client.ts`, driving the bundle built from `tools/shell-sentinel.ts` to `dist/sentinel.js`): one helper process per panel, spawned `detached` with `stdio: ['pipe', 'ignore', 'ignore']` so the host keeps the write end of the helper's stdin, with each shell's process group id written down that pipe as the command starts. Both platforms take the crash guarantee from the same property, the kernel acting at process teardown with no cooperation from the dying process: Windows releases the last job handle, POSIX closes a dead process's file descriptors, so a pipe whose only writer has died gives its reader EOF. **One pipe is both the registration channel and the liveness channel, and that is the design rather than an economy.** A heartbeat, a goodbye message or any other separate liveness signal would need code running in the dying host, which is precisely what SIGKILL and an OOM kill deny. Panel close and host death are therefore one code path: `dispose()` calls `child.stdin.end()`, and calling `end()` rather than dropping the reference is what actually produces the EOF. Do not add a second killer inside `dispose()` on the grounds that it is synchronous and can report failure; it would need its own copy of the identity check below, and that check is the one part of this feature that can kill a stranger's process if it is wrong. Never write that the two platforms reach this the same way.
- **The write end must reach the sentinel and nothing else, or the EOF never arrives.** A duplicate of that fd in any longer-lived process holds the pipe open, and the guarantee degrades silently to "the sentinel acts when the last copy closes", which for a long-running server is never. It holds today because libuv creates the parent-side stdio ends close-on-exec, and only the fds named in a child's `stdio` array are `dup2`'d onto 0, 1 and 2, which clears close-on-exec on those copies alone. Checked against a live `/proc` snapshot under WSL rather than assumed: with a detached shell and its background jobs running, the shell's fd table held exactly `0`, `1`, `2` and nothing else, while the host held the write end and the sentinel held its peer. Anything that later spawns with an explicit fd list, or gives a descendant of the host `stdio: 'inherit'`, has to be re-checked against that table, and the check is behavioural too: if `dispose()` on a live panel no longer kills the group, an inherited write end is the first place to look.
- **No sentinel on Windows, and the reason is not symmetry.** `createShellSessionJob()` dispatches on platform in its first statement and the win32 arm never reaches `shell-sentinel-client.ts`. A job object is kernel-owned and has no userspace component that can be killed, starved or crashed, so it is strictly better than a helper process; putting a sentinel beside it would add a weak point and buy nothing. This is asserted rather than argued, by `process-tree.test.ts` > "starts no sentinel on win32, where the job object already gives the guarantee", which pins zero `startShellSentinel` calls and zero spawns. The cost the POSIX arm pays for having no job object is real and worth knowing before anyone adds a second helper: one idle sentinel measured about 43 MB VmRSS and 7.1 MB private on Linux, per panel.
- **The sentinel re-identifies a group immediately before it signals it, and that check is the one part of this feature that can kill a stranger's process if it is wrong.** The sweep runs possibly hours after registration, and operating systems recycle pids, so `kill(-P)` on a bare remembered id is a silent kill of whatever holds P now. Two things stop that (`tools/shell-sentinel.ts`, `sweep`). First, an anchor: the sentinel reads the leader's start time at registration, `/proc/<pid>/stat` field 22 on Linux and `ps -o lstart=` on macOS, and refuses to signal when the live process holding P no longer matches it. The anchor is read by the sentinel and never by the host, which is what keeps the host's `createShellJob` free of a process-table read right after `spawn`. Second, for the case where the leader is already gone, which is the headline case `sleep 600 &` produces within milliseconds, the member anchors taken at the `x` record do the identifying instead. Both rest on the same kernel property: **both kernels refuse to hand out a pid that is currently in use as a process group id**, so while any process still has `pgid == P` no new process can be given pid P, and one identified survivor therefore vouches for the whole group. Refusing to kill whenever the leader is gone would refuse exactly the case panel-close cleanup exists for, so that branch is required, not an optimisation; what it may never do is fire without a matching anchor. Do not replace the anchor with a plain "is pid P alive" check, and do not unregister a group when its call ends: a process backgrounded with `&` has to stay registered or panel close cannot reach it, which is the whole difference this feature exists to remove.
- **The pid-reservation claim is measured on Linux and read-only on macOS, and the difference matters to whoever edits `sweep` next.** On Linux it is `__change_pid()` in `kernel/pid.c`, which walks every pid type and returns without freeing the number if any task still holds it, `PIDTYPE_PGID` included. That was confirmed by running rather than by reading: with `/proc/sys/kernel/ns_last_pid` steering the allocator, a request for a pid in use as a non-empty group's id was refused and skipped, and the identical request succeeded the instant the group emptied. On macOS it is the "find an unused PID" loop in `forkproc()`, `bsd/kern/kern_fork.c`, whose condition includes `pghash_exists_locked(pid)`, so the allocator advances past a pid in use as a pgid. **That macOS reading has never been executed, because no Mac was reachable.** The two platforms are equal on this point, and the only difference left is that macOS anchors are one-second resolution against Linux's clock ticks. **There is deliberately no session-id filter on either platform, and reinstating one would be a regression rather than a hardening.** An earlier design tested `sid === pgid` before signalling a leaderless group, which was worth having only because that branch signalled without any anchor at all. Against member anchors it can only subtract: a backgrounded job that calls `setsid`, which is what every daemonizer does, has `sid !== pgid` while still being a process the sentinel anchored by pid and start time, so the filter would turn correct kills into misses for precisely the long-lived background processes panel-close cleanup exists to reach. The field was never viable on macOS in any case, which is how the question first arose: `ps`'s `sess` keyword reports a kernel pointer rather than an id (`adv_cmds`, `ps/keyword.c`, `KPTR`), and Darwin has no `sid` keyword at all.
- **The sweep never signals a group it has not positively identified, and the member anchor is what makes that possible when the leader is gone.** An earlier design signalled a leaderless group on the strength of its membership alone, which after a pid wrap could kill a stranger's processes; that hole is closed and must not be reopened. The host writes two records now, `r<pgid>` as a command starts and `x<pgid>` when its shell exits, and the `x` is the whole point: **at the instant the shell exits, every process still in the group is ours by construction**, so the sentinel snapshots each one with its own start time. At EOF a group is signalled only if the leader is alive and matches its anchor, or some member anchor is still alive and matches. Otherwise it is skipped. One matching anchor is sufficient because a pid cannot be recycled while a group still holds it, so a single identified survivor proves the whole pgid was never reissued. Do not reintroduce an unanchored branch, do not treat `x` as an unregistration (the group stays tracked, or a deliberately backgrounded process becomes unreachable at panel close), and do not replace the snapshot with a poll: it is one process-table read at one known event, inside the sentinel, never in the extension host and never on a schedule.
- **Known residual, and it fails the safe way. The general condition is "no anchored member is alive at sweep time", which is wider than the race that first suggested it.** Two shapes reach it, and the second is the one you will actually meet. First, a host killed between the shell exiting and the `x` record being written: that group has no member anchors at all. Second, and with no crash involved, a group whose anchored members have since exited leaving processes they forked after the snapshot. The snapshot is one read at one instant, so a double-forking wrapper, the shape `sh -c 'sleep 2; sleep 600 &' &` produces, anchors the wrapper and never sees the process it leaves behind. Measured under WSL rather than reasoned about: with a correct `r` and `x` pair, the late-forked process survived a `kill -9` of the host, `sleeps after: 1`. Note what does not reach it: `sleep 600 &` anchors the sleep itself, and `npm run dev &` anchors npm, which stays alive as the parent, so both clean up. Those processes leak. **That is a miss, not a stranger's death, and the difference is the entire reason the design changed.** A leaked process is the pre-2.23.0 behaviour for one group in a narrow window; a wrong kill is data loss with no warning and no log the user will ever read. Anyone tempted to widen the sweep to catch this case is trading the second failure for the first and must not. Two escapes were examined and rejected on evidence rather than taste: holding an fd on `/proc/<pid>` does not reserve a pid, which the kernel documents explicitly, and `pidfd_send_signal` returns ESRCH once the leader is dead, so it refuses precisely the case that needs covering.
- **The accepted residual is `kill -9` on the sentinel itself.** No userspace process can refuse SIGKILL, so killing the helper loses the cleanup for that panel, and there is no in-process defence against it. Linux could close this with a PID namespace or a systemd transient scope. macOS has neither, and no job objects and no cgroups, so closing it on Linux alone would create a three-way asymmetry, and the PID-namespace form would additionally change what every shell command sees of its own process tree. The user reviewed both options and chose to leave the gap. Do not reopen it, and do not substitute a mutual watchdog: two processes each restarting the other is a new failure mode of its own and still loses to a `kill -9` that names both.
- **koffi is required lazily, behind the win32 check, and its failure is reported rather than swallowed.** It is the project's only native dependency, so `createShellJob` returns on `process.platform !== 'win32'` before the loader is reached and no POSIX path ever requires it. The native binary lives in a per-platform `@koromix/koffi-<platform>-<arch>` optional dependency resolved at run time, which is why koffi is an esbuild external and reaches the VSIX through `scripts/extension-externals.mjs` and the generated `.vscodeignore` (run `npm run sync:vscodeignore`, never hand-edit it). A load failure logs the consequence in user terms and degrades to the bare `taskkill /T` sweep, which cannot reach a severed parent link, and each of the four kernel32 calls that can fail logs which call and which pid. There is no empty catch anywhere in the module: the degradation is announced at the point it is decided, so a user reporting surviving processes has a log line naming the cause.

## Permissions and plan mode

- All tool calls route through the central permission gate (`permission-gate.ts`): read auto-allowed, write/shell → diff approval. In plan mode, `Bash`/`PowerShell` are classified by `readonly-shell.ts` (fail-closed allowlist); non-plan-file `Edit`/`Write` stay blocked (the session plan file is the sole write carve-out); memory/Compass/enabled MCP tools stay available. The same classifier also holds a subagent whose resolved toolset has no write tool (`ResolvedToolset.readOnly` → `readOnlyShell`) in every mode. No write tool must mean no writes via the shell either.
- A block the runtime made itself (settings rule, plan mode, read-only agent, hook) uses `formatPolicyBlockReason`/`POLICY_BLOCK_MARKER`; only a real approval-prompt rejection uses `formatDenyReason`/`FEEDBACK_MARKER`. Never tell the model the user refused something the user was never asked. Both render as "denied"; `FEEDBACK_MARKER` is persisted in old sessions, so its value must not change.
- **`terminate` is per-batch, not per-call, and it is emitted only for an unexplained "no".** pi ends the turn only when every finalized result in the batch is terminating and the batch is non-empty. `executeToolCalls` dispatches to a sequential or a parallel batch runner, and both take the flag from `shouldTerminateToolBatch`, which requires `finalizedCalls.length > 0 && finalizedCalls.every((finalized) => finalized.result.terminate === true)`, consumed by the agent loop as `hasMoreToolCalls = !executedToolBatch.terminate` (`@earendil-works/pi-agent-core@^0.87.0`, shipped at `node_modules/@earendil-works/pi-agent-core/dist/agent-loop.js:463-465` and `:167`; the line numbers are only meaningful against that installed version, so re-read the file before trusting them). So denying one of three parallel calls does not stop the agent: the other two ran and produced results the model must see. That is correct, not a bug. Do not "fix" it by terminating harder. Damocles sets it in exactly two places: the interactive `canUseTool` deny, conditional on `PermissionResult.interrupt`, and a `tool_call` hook that explicitly opted in with `"terminate": true` alongside its deny (read strictly as the JSON boolean `true`; a string or number is ignored). `interrupt` is set by exactly two functions, `buildUserDenyResult` and `buildUserFileEditDenyResult` (`src/extension/permission-handler/utils.ts`), and only when the user actually answered the prompt (`ApprovalResult.userAnswered`) and left the feedback box empty. A deny with feedback is *instruction* the model must act on, so it must not end the turn. Every deny the user was never asked about is built by `buildUnaskedDenyResult`, which cannot set it. Grepping `interrupt` under `src/extension/permission-handler/` is therefore a complete enumeration of the terminating sites. Keep it that way. Everywhere else stays non-terminating on purpose: the gate's own error fallback (a Damocles bug must not kill the user's turn), settings-rule denials (policy, not a user decision), and above all the plan-mode / read-only-agent blocks, whose entire reason for existing is to make the model self-correct. Terminating there breaks plan mode.
- The on-disk plan file is the single source of truth for plan-mode handoff. `ExitPlanMode` takes no `plan` argument; everything reads it via `ChatSession.getPlanContent()`.
- A `damocles.*` setting whose workspace value grants a capability or relaxes a guard must be listed in `capabilities.untrustedWorkspaces.restrictedConfigurations` in `package.json`. Every setting that declares no `scope` defaults to `window`, so a repository sets it from its own `.vscode/settings.json` and `config.get` returns that value in a workspace the user never trusted. Listing it makes VS Code serve the user value instead until trust is granted, with no code change at the read site. The bar is a capability grant, not a preference: a budget, a model choice or a display toggle does not qualify, and an over-broad list breaks legitimate per-workspace configuration for trusted users. Known pending case: `damocles.sandbox`'s `autoAllowBashIfSandboxed`, `allowUnsandboxedCommands`, `networkAllowedDomains` and `networkAllowLocalBinding` are declared in the manifest with no reader anywhere in `src/`, so today they grant nothing and are deliberately absent from the list. Whoever gives one of them a reader adds `damocles.sandbox` to the list in the same change.
- Compass is off in an untrusted workspace, and the gate is `isCompassEnabled()` (`compass/index.ts`), never a call site. That one function is what tool eligibility (`moduleToolNames`), the system prompt section, the webview handlers, the sidebar views and `ensureInitialized` all read (the views directly, the rest through the `CompassService.isEnabled` getter that returns it), so trust belongs in that function and the rest follows with no other edit. The reason is what Compass does with a repository: it walks the entire tree, parses every source file into `~/.damocles/compass/<hash>/graph.db`, returns raw source lines to the model through `compass_review_context(include_source)`, and runs git inside the workspace. `damocles.compass.enabled` sitting in `restrictedConfigurations` only stops a repository turning Compass on for itself and does nothing about a user who enabled it globally, which is everyone who uses Compass. Prevent the work, do not filter its output: untrusted means no worker, no walk and no watcher. Trust is granted and never revoked in place, so the service subscribes to `onDidGrantWorkspaceTrust` and starts then with no window reload, if something already asked it to start, and there is no reachable state in which an index built while untrusted keeps serving.
- Every git call in `compass/git.ts` passes `-c core.fsmonitor=false`, an argv rather than a shell command string, and no `ExecEnv`. Git reads the repository's own `.git/config` first and runs `core.fsmonitor` as a command while refreshing the index, so `git diff` in a hostile clone is arbitrary code execution; `compass/__tests__/git.integration.test.ts` verifies against real git that the hook fires without the override and not with it. An `ExecEnv` from the checkpoint engine would retarget git at its private bare repo and answer about the wrong repository. This is the same finding as the one fixed in `mcp-local-gitignore.ts`, so treat any new git caller as needing both.
- Plan-mode guidance has one source: `pi-session/plan-mode-guidance.ts` (`buildPlanModeGuidance`), consumed by both `agent-start.ts` and `tools/plan-mode-tools.ts`. Edit the builder, not the call sites.
- The Damocles system prompt has one assembler: `agent-start.ts` (`assembleDamoclesSystemPrompt`). Never read `session.systemPrompt` for display. It holds pi's boilerplate outside a turn.

## Browser

- Browser tools resolve tabs through the caller's `BrowserAgentScope`, never a global active page: main agent + human share `PRIMARY_SCOPE_ID`; every subagent/team agent passes its own id and its scope is disposed at settle (tabs closed only on success).
- Anything a page produces is hostile input on the extension host. Console/network/picker output is redacted and bounded at capture (`redaction.ts` + `collectors.ts`), never at a render site. The guarantee must not depend on whoever adds the next reader. The in-page bridge's caps live in the page's own world and are the page's to edit, so every bound is re-enforced host-side in `installContextObservers`/`onConsoleBinding`. Every redaction pattern must be linear-time (unrolled-loop form, bounded affixes): it runs synchronously on the host, so a backtracking pattern is a remote editor freeze.
- `ScreencastHealth`'s stall clock is armed by intent (`noteWanted`, on panel visibility), not by the CDP `start()` call. The webview's `ready` message is the sole trigger for `start()`, so anchoring on it makes the watchdog blind to a lost handshake.
- `damocles.browser.devToolsPort` (default on) opens an unauthenticated loopback CDP endpoint on the logged-in profile; it is a launch-time flag, so a change needs a relaunch.

## Teams and subagents

- Team message delivery branches on `TeamMessage.kind`, never on rendered text (a peer can mimic any prefix). `scratchpad-notice` reaches only a `standby` specialist; `ledger-notice` reaches no inbox at all (the ledger is a pull surface). Both still broadcast, so persistence/timeline/`getInbox` see every write. Filter at delivery, never at emission.
- The verification fingerprint is computed by the extension, never supplied by an agent (`team_record_verification` has no `fingerprint` param, asserted by test). It must fail visibly: `unverifiable`, never a hash that silently missed files. `git status` needs `-uall -z` and paths resolved against `--show-toplevel`. Without all three it goes blind to real edits (collapsed untracked dirs, C-quoted paths, subdirectory workspaces) and a stale pass looks reusable forever.
- The team profile catalog is generated, never hand-edited: change `agent-profiles/`, run `npm run generate:profiles`, commit the output (a pinned test locks the exact set). Its mirror policy (`TRACKED_DIVISIONS`, `EXCLUDE`, `DIVISION_ALLOWLIST`) is duplicated in `~/.claude/scripts/sync-claude-agents.mjs`, which governs `~/.claude/agents`. Separate repos, no shared state, so edit both together. Both scripts and the generator fail closed (flattened-path collision, duplicate profile id): a profile must never go missing silently.
- Each nested spawn path collapses to one `buildAgentToolset` call (`agent-manager.ts`, and both `team-runner.ts` spawn sites), made inside the per-spawn path for the same reason `buildExtensionFactory` is invoked per spawn: it must read live panel state at spawn. Hoisting it to a construction-time local would freeze the snapshot at team-construction time and silently miss a server the user enabled mid-run. `mcp.names` must reach `tools:`, `customTools` and `mcpToolNames:` from that one call. And `tools:` must never be narrowed to the deferred baseline, which evicts the tools permanently while ToolSearch still reports success.
- The read-only-agent rule is a shell-escape guard, not a general capability ceiling. `toolCategory('mcp__*')` is `'other'`, so the read-only branch does not catch MCP: a read-only subagent (Explore/Plan, or any agent with no write tool) can invoke a non-annotated MCP tool, and in `default`/`acceptEdits` it still routes through `canUseTool` and prompts. That is a decision, not an oversight. Filtering it would make nested agents stricter than the panel and stricter than plan mode, and most servers omit `readOnlyHint` entirely so it would fail closed against the common case. The trust boundary for MCP is the server enablement list, not the agent type. Do not "fix" it in either direction without changing this line.
- A subagent's model is configuration, never the spawning model's choice: the `Agent` tool deliberately has no `model` param. `resolveSubagentModel(agentConfig)` takes only a config. Template `model:` > Explore settings (Explore only) > the panel's session model. An unresolvable/unauthed/out-of-scope template `model:` fails the spawn naming the template; never fall back to the session model, which leaves a broken pin working-but-wrong forever.
- **`team_standby` and `team_report_complete` end the turn from the engine, not from the model.** Both used to set a flag and return, leaving the model free to carry on, and it did: 771 of 826 recorded standby calls were followed by more work. The stop is a `finishTurn` decider registered through `installTurnDecider`, which defers to the hook pi already installed, keyed on the tool *result* rather than the call because both tools throw for the wrong role and the agent needs that turn to read the error. It holds no opinion while `session.agent.peekQueuedMessages()` is non-empty. Never `session.pendingMessageCount`: that counts the `_steeringMessages`/`_followUpMessages` mirror, which `sendCustomMessage` bypasses by steering the agent directly (`agent-session.js:1481`), so a queued follow-up reads as zero there and the decider ends a turn pi was about to feed. Nothing is lost when it does, because `_runBeforeSettleBoundary` continues on `hasQueuedMessages()` anyway; the cost is an extra continuation request and a one-turn delay. Do not make the tool block instead: the team state machine runs only after `session.prompt` resolves and pi has no tool timeout, so a block hangs silently until abort. Do not abort either, which marks the agent failed.

- **Scratchpad read state is per session and must be cleared when a session is replaced.** The unchanged marker withholds a section on the premise that its text is already in the reader's context. `redispatchSpecialist` gives an agent a brand new session under the same name, so `Scratchpad.clearReader(name)` runs alongside the other per-attempt resets. Without it the re-run's first read answers "unchanged since you last read it" for text it has never seen, and because the marker holds until a peer writes a new version, `mission-brief` (which has no other writer) is withheld for the rest of the run. Appending is not reading, so `appendTo` records nothing: `team_record_verification` echoes only the last 25 of up to 200 ledger entries.

- **A team agent's work fields are per attempt; its usage fields are cumulative.** Status, last tool, start and end time, tool count and result describe the attempt running now. A `resume_team` continues the attempt, so its tool count carries on; a redispatch starts a new attempt at zero. Tokens and cost sum across every attempt, because a cancelled attempt's spend was still spent. Three places must agree or a reopened team contradicts the live one: the runner (`carriedUsage` plus the running attempt's usage, and `carriedToolCallCount`, restored from the checkpoint, plus the tool calls since the resume), the loader (each `agent-completed` entry holds its own run's usage, so it sums those, and takes the work fields from the last, including `toolCallCount`, which is the attempt's running total), and the webview store (which resets the work fields when the `attempt` counter advances). `attempt` is 0-based; a log written before it existed has no field and its spawns are the first attempt. Never write cumulative usage into `agent-completed`, or the loader double counts; never write a per-run tool count there, or a resumed member's count restarts. A team card's per-run totals are a separate figure: `TeamRunLog` (`runs.ts`) takes them from the `run` field of `team-completed` or `team-cancelled`, and otherwise derives them from the `agent-completed` entries of that run. A run's usage has the same counters as an agent's (`TeamRunSummary.usage`: each token kind and the cost), so the card's tokens and cache rate use the definitions `AgentUsageStats` uses on the agent cards and overlays, and the runner, `TeamRunLog` and the store each derive all of them. A log written before those counters recorded `run.tokens`, input plus output only; it is read into `legacyTokens` and never into the token kinds, so such a card shows that figure and no cache rate.

- **A live agent's usage is a `getSessionStats()` delta, never a sum of `message_end` usage** (`session-usage.ts` `runUsageMeter`, used by the subagent stream bridge and the team `AgentRunner`). The baseline is taken when the run attaches to its session, so a reopened session's earlier runs stay on earlier cards. pi's total counts every billed entry, compaction summaries and cache warms included, which is what keeps the tokens consistent with the cost; a per-message sum misses both. pi notifies `message_end` listeners before it persists the message, so a reading taken inside the listener lags one response: the reading is deferred a microtask. A subagent's budget roll (`AgentManager.rollCost`) takes the same reading the bridge sends the card, through `onUsage`, so each response is read once and the budget never runs a response behind; the run's end reads once more (`settleUsage`) for spend that raised no event. The reload path rebuilds the same figure per segment with `usageOfEntry` (`agent-records.ts` `parseAgentEntries`). A resume segment records `dollarBilled` from the model its session reopened on, and the loader prefers it over the launch entry's flag, so a resumed card is labelled the same live and after a reload.

- **The nineteen team tools have one naming table, `src/shared/team-tool-labels.ts`.** The Tools panel catalog, the card in the transcript and any future reader all take their label from it: `team-tools.ts` keeps the descriptions and the schemas but no labels of its own, mapping each spec through `toSpec`, which throws at module load for a name with no entry. That is deliberate and must stay: a `?? name` fallback would render a card reading `team_write_scratchpad` and nobody would notice for a release. The table is imported by both the webview bundle and the extension host, so it imports nothing at all. The raw snake_case name is still what the expanded overlay shows, because session logs and greps are keyed on the name the agent actually called, so a label must never replace the name in a persisted or searchable surface. Adding a team tool means adding its label in the same change.

## Webview overlays

- **An overlay's z-index is derived from the shared overlay stack, never hardcoded and never left to DOM sibling order** (`composables/useOverlayEscape.ts`, consumed by `OverlayShell.vue`). Every overlay used to render at `z-50`, so equal-z siblings painted in the order they appear in `App.vue`: a tool overlay opened from inside a team agent overlay opened behind it and looked like a dead click, while the same card worked from a subagent overlay purely because that mount is written earlier in the file. The stack `useOverlayEscape` already keeps is the same ordering paint order needs, and the composable now returns `zIndex` = base + stack depth. Reordering mounts in `App.vue` fixes one pair and leaves the next nested overlay to rediscover the bug, so it is not the fix. Mount order is what the stack records and a nested overlay mounts strictly after the one it opens over; Vue guarantees nothing about sibling order, which is exactly why the stack rather than the DOM is the source. An overlay that reintroduces a fixed `z-` class cannot be opened over.

- **The overlay stack's Escape listener stays on `document` in the bubble phase, so a control inside an overlay can keep Escape for itself** (`composables/useOverlayEscape.ts`, consumed by `OverlayShell.vue`; the control is `components/ToolCancelControl.vue`). The cancel note textarea closes its note on Escape and stops the event, which only works because the stack's handler runs later, on an ancestor node. Bind it in the capture phase, or on the overlay root, and it fires first and throws away a half-typed note by closing the overlay around it. `overlay-stacking.test.ts` goes red if either moves.
- **While a reka popup or dialog is open, the overlay stack leaves Escape to it** (`composables/useOverlayEscape.ts`). reka's dismissable layers (Select, Popover, DropdownMenu, the range calendar's Popover, Dialog) hear Escape on `window`, which a keydown reaches after `document`, so the stack's handler runs first. It therefore returns without stopping the event whenever an open element carries `data-dismissable-layer`; a stopped event never reaches the popup, and Escape closes the whole overlay around a half-picked date range. A stack overlay that is itself built on a reka dismissable layer (the image lightbox's `DialogContent`) marks that element `data-overlay-layer`, or the stack would yield Escape to the overlay forever.
- **Popper content inside an overlay paints one above it** (`usePopperZIndex` in `composables/useOverlayEscape.ts`, bound by `ui/popover/PopoverContent.vue`, `ui/select/SelectContent.vue` and the two `ui/dropdown-menu` contents). Popper content is portalled to `body`, so it stacks against the overlay rather than inside it; a fixed `z-50` ties with an overlay at the base of the stack and sinks behind one opened at depth 1 or deeper. Every stack overlay provides its z-index, and the popper binds that plus one; outside any overlay it keeps `z-50`.

## Session store

- **Nothing may append to a session file after it is deleted.** pi's `SessionManager._persist` sets `flushed = true` on its first write and from then on appends blindly, without re-checking that the file still exists. So a late write recreates the path holding only that one entry. Such a file has no `session` header, `SessionManager.open` rejects it forever, `listPiSessions` skips it, and because it is not in the list it cannot be deleted from the UI. Damocles cannot fix the writer, so it refuses to create the precondition, at three points: every holder detaches before the `rm`; a writer that resumes after an `await` re-checks liveness; and the reader caches negatives so one bad file is re-read once per change, not once per rebuild.
- **Detach is routed by session id, not by "is this my panel".** Two panels resuming the same file get the same session id (it comes from the header), and `registerSessionMutator` is a `Map`, so the second registration displaces the first. `deleteSession` therefore detaches the registered owner and `ctx.session`, deduped. The panel you clicked in may be the displaced one, or may only be pointing at the session as a not-yet-started resume/fork target. A panel mid-`start()` has no runtime yet, so detach awaits `startPromise` before resetting; without that, `reset()` bails, `whenReplaced()` resolves instantly, and `start()` goes on to open a manager on the path being removed.
- **`whenReplaced()` must report reality.** `runtime.newSession()` can throw, and returns `{ cancelled: true }` without tearing the old session down when a `session_before_switch` handler cancels. In both cases the old session is still installed and still writable. The promise rejects for both, and the logging `.catch` hangs off a separate handle so the rejection stays observable to callers while never becoming an unhandled rejection. `MessageRouter` catches handler throws, so a failed detach surfaces to the user and aborts the delete with no per-handler try/catch.
- **Only `maybeGenerateTitle` writes across an unbounded await** (a 15s-timeout sub-call on the small/fast model). `recordMidStreamMarker` and `recordSteer` re-read `this.runtime?.session` and write synchronously; `renameActiveSession`/`setActiveSessionTag` re-read after `ensureStarted()`. `recordOriginalInputIfDiverged` receives a captured session and is ordered safely only by pi's teardown awaiting `abort()` first. An implementation detail of the dependency, so it carries the liveness check explicitly rather than relying on it.

## Usage accounting

- **One inclusion rule decides what counts as spend** (`src/shared/usage-accounting.ts`). It mirrors pi's `getSessionStats()`: every assistant message whatever its `stopReason` (aborted and error turns were billed), a `toolResult` message that carries usage, `usage` entries (the cache warmer writes `kind: 'cache_warm'`), and `compaction` and `branch_summary` entries that carry usage. The status bar (live and on reload), the subagent meters and reload, and the `/stats` worker all import this module, so a figure never differs between the live view and a reload. The module is imported by the webview bundle and the worker thread, so it imports nothing from pi, `vscode` or Node. `pi-parity.test.ts` builds a session with pi's `SessionManager` and asserts the indexed cost equals a real `AgentSession.getSessionStats()`.
- **A fork's inherited spend is not its own.** A fork copies its parent's entries verbatim (same `id`, same `timestamp`) into a new file whose header carries a later timestamp, so a copied entry always predates its file's header. `isOwnEntry(entry, headerTimestamp)` is that test; a conversation's totals count only its own entries. They are derived from `sessionManager.getEntries()` on every read, never cached, so a session replacement or a switch cannot leave a stale baseline.
- **The budget counts the conversation's own spend plus its subagent and team spend.** `ownSessionUsage` (`session-usage.ts`) is the figure for the status bar and for every budget check (`checkBudgetAtTurnEnd`, `enforceBudgetInFlight`, `addExternalCost`, the pre-prompt gate), so a fork is never stopped by what its parent spent. Subagent and team cost is added from the adapter's external total, which resets when a new conversation is seeded. The status bar shows the conversation's own spend only; subagent and team spend show on their own cards. The in-flight check runs a microtask after `message_end`, because pi appends the message only after notifying listeners.
- **Never bill from `history-loader.ts`'s context snapshot.** Those fields describe the last request's prompt size for the context meter. Cumulative spend comes from summing entries under the rule above, and the two sets of fields are kept apart in the webview store. The snapshot follows pi's `getContextUsage`: it skips an aborted or errored message and one with no tokens, and a compaction resets it to zero until the next response, live (`compaction_end`) and on reload (`contextSnapshotOf` in `context-snapshot.ts`).
- **Every billed internal model call appends one ledger line.** Titles, memory work (extraction, rerank, merge, profile, query expansion) and `/btw` run outside any session file, so their spend lives in `~/.damocles/usage/subcalls.jsonl` (`usage-stats/subcall-ledger.ts`). `PiRuntime.runStructuredCompletion` appends the line for titles and memory. The `/btw` aside runs on an in-memory pi session, so its own `message_end` subscriber in `pi-session.ts` appends it. A call site that does neither is spend `/stats` never sees. `appendSubCallUsage` skips a call with no tokens and no cost (`carriesUsage` in `usage-accounting.ts`). It never reads `totalTokens`, because a provider may leave that at 0 while it reports tokens. The ledger is append-only JSONL, one `appendFileSync` per line, which is safe across VS Code windows.
- **Formulas.** Every `/stats` card shows its formula in a tooltip and must match these.
  - Cost is the recorded `cost.total`. An entry with tokens and a zero cost is unpriced: its tokens go into a separate "unpriced tokens" figure and never read as $0.
  - Total tokens is `input + output + cacheRead + cacheWrite`, pi's `totalTokens`.
  - Cache hit rate is `cacheRead / (input + cacheRead + cacheWrite)`, and has no value when the denominator is 0.
  - Net cache savings is `(cacheRead + cacheWrite) × inputRate − (cost.cacheRead + cost.cacheWrite)`: what the cached tokens would have cost as plain input, minus what they did cost. `inputRate` is `cost.input / input` from the same entry, which follows pi's pricing tiers. When `input` is 0 it falls back to the registry rate the host passes to the worker (pi's `model.cost.input` is USD per million tokens, the worker takes USD per token). Unpriced entries are excluded. The figure can be negative when 1-hour cache writes are rarely read.
  - The cost label always reads "API-equivalent" and adds "est." when the current account is not dollar-billed, because the billing mode at request time was never recorded.
- **The `/stats` index is a cache, and it never forgets spend** (`src/extension/usage-stats/`). `~/.damocles/usage/usage.db` is a `node:sqlite` WAL database owned by one worker thread per window, because the first scan can read more than 1 GB. The worker imports neither `vscode` nor pi and takes every path from the host. The host closes it after 2 minutes idle, and never while it is making progress. When the worker sends nothing for 5 minutes with a request in flight, the host terminates it and rejects the waiting requests. The next request starts a fresh worker. Each file commits in its own transaction, so at most the file in progress is lost.
  - The first worker in each extension host runs `PRAGMA quick_check` on open. Later workers skip it, because it reads the whole file. SQLite still reports corruption from real statements, and the worker then closes the index, so the next open checks it and moves it aside.
  - Rows upsert on `entry_key = "<id>|<timestamp>"`. A copied entry belongs to the oldest top-level session whatever the scan order. For session-file rows, `entries.session_started_ms` is the start of the top-level session the row is attributed to, not the file's own header time: a fork copies subagent files into its own folder (`fork-agent-data.ts`), and the copies' own headers cannot order them. Ties break on session id, agent session id and path, a strict total order, so every scan order gives the same rows.
  - Nested subagent and team files attribute to their parent's session id and keep their own id in `agent_session_id`. Team event logs and `.json` checkpoints are not sessions and are never indexed.
  - Rows keep the raw provider and model. `model_key` maps a dated id to its base id when only the base is in the registry. `meta.model_registry` holds a fingerprint of the registry keys the rows were keyed with. When a scan sees a different registry, it re-keys every row in one `UPDATE`, so the model filter, `byModel` and the fallback rate join never split one model across two keys.
  - Files are read from a stored byte offset, complete lines only; a trailing partial line waits for the next scan. A shrink or a changed tail hash reparses from byte 0, which is idempotent. Each file is indexed in one `BEGIN IMMEDIATE` transaction. The worker re-reads the file's row and its size inside it, so a second window's worker serializes rather than resuming from a stale offset. A migration re-reads `user_version` under the write lock, so two windows opening an old index migrate it once.
  - Marking vanished files and recording the scan time fail soft. When another window holds the write lock too long, the worker logs it, retries on the next scan, and still answers with the rows it indexed.
  - Spend rows are never deleted. When a file vanishes its rows stay, its conversation is marked missing and its title is cleared, so it shows as "Deleted conversation". A file counts as vanished only when a stat inside the marking transaction finds it gone, because another window may have indexed a file created after this scan listed the directory. The index runs with `secure_delete` and truncates its WAL after it clears a title, so the title leaves the database files too. Rebuilding the database would lose that spend, so schema changes are additive migrations under `PRAGMA user_version` and the code never rebuilds a readable database.
  - A corrupt database is moved aside as `usage.db.corrupt-<ms>` and the loss is logged. Only the newest aside copy is kept, and it can still hold titles from before the corruption. Windows refuses the move while another window's worker holds the file open, and the request then fails with an error that says so.
  - Filter values reach SQL only as bound `json_each` parameters. Time buckets use the webview's zone, not the extension host's. Under Remote-SSH, WSL or a container the two often differ, and the webview matches bucket keys as strings. The webview sends its IANA zone with each query. The host rejects a zone that is not a name of at most 64 characters or that `Intl.DateTimeFormat` does not accept. The worker cuts days, weeks, months, heatmap weekdays and hours, and active days in that zone through the `usage_local` SQL function in `queries.ts`, with the zone as a bound parameter. The function formats each 15-minute UTC slot once per zone with `Intl.DateTimeFormat` and caches it. That is exact because every UTC offset and DST change since 1972 falls on a 15-minute UTC boundary. An offset zone such as `+05:37` breaks that, so the host accepts zone names only. Weeks start on Monday in every locale. The chart never drops a point whose bucket it did not expect. `chartRows` gives it its own row in key order, so the chart still sums to the KPI.
  - Every breakdown (`series`, `byModel`, `byProject`, `bySource`) groups the same filtered rows as the totals with the same unpriced rule, so each sums to the KPI total; `queries.test.ts` asserts it under every filter kind. `buildReport` reads every figure in one read transaction, so another window's commit never lands between the totals and a breakdown. Sources are exclusive: a ledger row is a background task by purpose; otherwise a `compaction` or `branch_summary` entry is compaction and summaries, and a `usage:cache_warm` entry is cache warming, whichever file it sits in; only the rest take the file's origin (main chat, subagent by agent type, team by role). A new source must keep that one-branch-per-entry `CASE` in `queries.ts`, or a row is counted twice or dropped.

## Tests

- Every test file runs under its own temp home: `src/__mocks__/hermetic-home.setup.ts` points `USERPROFILE` and `HOME` at a fresh dir before any module reads `os.homedir()`, so nothing a test writes through `DAMOCLES_HOME_DIR` reaches the developer's real `~/.damocles`. That setup file must never import `paths.ts`, which freezes the home at import.
- Those homes live under one per-run root that `src/__mocks__/test-home.global-setup.ts` removes in its teardown. Cleanup belongs there and not in a per-file `afterAll`: vitest skips a file's hooks when every test in it is skipped or filtered out by `-t`, and the teardown runs after the fork workers exit, when Windows has released their file handles.
- The redirect needs vitest's `forks` pool, pinned in `vitest.config.ts`. In a worker thread, `process.env` writes do not reach `os.homedir()`.

## Packaging

- **The VSIX node_modules allowlist is generated, never hand-edited** (`scripts/sync-vscodeignore.mjs`, run through `npm run sync:vscodeignore`). `.github/workflows/release.yml` runs the script with `--check` on `ubuntu-latest` while developers generate the block on their own machines, so every pattern it emits has to be identical on every platform. A native binary package therefore collapses to a family glob (`@vscode/ripgrep-win32-x64` becomes `@vscode/ripgrep-*`), and a name that is nothing but platform tokens collapses to its scope (`@esbuild/win32-x64` becomes `@esbuild/*`). A literal platform name in the block fails `--check` on the release runner and aborts the tag push before the package matrix runs. `scripts/__tests__/sync-vscodeignore.test.ts` pins both halves.
- **The closure walk follows Node resolution, so it must climb the whole ancestor `node_modules` chain.** Checking the immediate parent and then jumping to the project root reports the hoisted top-level copy for any dependency npm nested to satisfy a version conflict, and that copy can be a devDependency the extension never loads. That is how a 10 MB Windows compiler binary reached the VSIX: `@earendil-works/chord` requires `esbuild@0.28.2`, npm nested it under `@earendil-works/pi-coding-agent`, and the walk reported our build-time `esbuild@0.24.2` instead. `assertNoDevOnlyPackages` fails the run when a devDependencies-only package reaches the closure, and names the package that asked for it.
- **Known exception, reported upstream: five nested `@earendil-works/*` lock entries carry `resolved` with no `integrity`, so `npm ci` fetches those tarballs with no subresource check.** The same tarballs carry an `integrity` hash on another entry for the same version, so the gap is confined to the duplicates npm writes under `node_modules/@earendil-works/pi-coding-agent/node_modules/`. Do not describe those other entries as the top-level ones: `chord` has no top-level entry at all, and which copy npm hoists changes whenever the dependency set does. The omission is upstream rather than local. pi ships its own `npm-shrinkwrap.json`, that file carries `resolved` with no `integrity` for exactly these five, and npm copies the gap into our lockfile, so no amount of regenerating or cache-clearing fixes it here. The cache is not a variable: pi-coding-agent's own top-level entry does carry an `integrity` hash, and the shrinkwrap ships inside that verified tarball. Never hand-edit a hash into `package-lock.json`: a hand-written value is unverifiable and turns a missing check into a false one.
