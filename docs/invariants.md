# Invariants (long form)

Rationale and failure modes behind the one-line rules in `CLAUDE.md`. Read the entry before changing the subsystem it governs.

## Engine and message contract

- pi is the only agent engine; new sessions always construct `PiSession` — there is no harness selection.
- Don't change the webview message contract to add a feature — map pi events to existing shapes via `pi-stream-adapter.ts` / `tool-normalization.ts`.
- `Edit` cannot create files (empty `old_string` throws); `Write` is the only creation path.
- Internal sub-calls (memory, structured output) use `PiRuntime.runStructuredCompletion` + the terminating-tool idiom (no `toolChoice`).
- Never mutate `process.env` for per-session config; pi reads a Damocles-owned `agentDir` (`~/.damocles/pi/agent`).

## Deferred tools / ToolSearch

- Browser/Compass/Web/MCP tools are DEFERRED: registered but inactive, activated only via `ToolSearch` (`tools/deferred-tools.ts` is the leaf that owns the universe). They must stay in pi's `tools:`/eligible set — dropping a name removes it from the registry and `setActiveToolsByName` silently ignores unknown names, so it could never come back. Deferral is only safe where `ToolSearch` is actually REGISTERED; gate on that, never on it merely being allowed. A ToolSearch group equals a Tools-panel subsystem: the whole subsystem defers or none of it does, so there is one rule for the model and one line in the menu.
- The deferrable universe composes from leaf SPEC modules only, never a barrel. `deferred-tools.ts` documents itself as composing the `*_PI_TOOL_NAMES` exports and importing nothing else, and `tool-search.test.ts` ("deferred-tools.ts import discipline") enforces it to keep the eval-time cycle `permission-gate` → `tool-catalog` → `browser-tools` closed. A barrel that re-exports a `vscode`-importing config module (as `web-access/index` does) forces that guard to be relaxed to "any import is fine", retiring it for every future group. Add a `-tool-specs` declaration leaf instead — the reason is guard preservation, not startup cost.
- A system prompt must never name a deferrable tool without stating how to load it. A deferred tool is not callable on turn one, so a prompt that names one without an adjacent `ToolSearch({tools:["<group>"]})` step is a dead end — the model calls it and gets an unknown-tool error. This held in FIVE places at once (`system-prompt.ts`, `plan-mode-guidance.ts` ×2, `subagents/default-agents.ts`, `compass/system-prompt.ts`); the subsystem's enabled-ness is no defence, since that flag is exactly what makes the names eligible AND deferred.
- ToolSearch republishers retire DETERMINISTICALLY, never by exception, and every registered closure has exactly one owner responsible for retiring it. Which owner applies depends on whether an `AgentSession` ever binds the extension instance that registered it, and the two cases are genuinely different — do not collapse them:
  - **Session-bound instances retire themselves.** `PiRuntime.registerToolSearchRepublisher` returns a disposer the instance calls from its own `session_shutdown` handler, for every reason, `'reload'` included. This deliberately diverges from the observe-only lifecycle handlers in `hooks/index.ts`, which skip `'reload'` because an internal rebuild is not a user-meaningful session end; here a reload genuinely retires the instance.
  - **Unbound instances are retired by `PiRuntime`.** `resourceLoader.reload()` also runs the extension factory where no bind follows — the `.claude`/`.codex` compat watcher, `_hotReloadExtensions`, `_removeSubscriptionPlugin` — and `createAgentSessionServices` mints one at init before any session exists. Such an instance receives no session event at all, so there is no owner inside it. `_reloadResources` takes a `ReloadBinding` argument stating which kind of reload it is, and the runtime holds the unbound instance's disposer in `_unboundRepublisherDisposer`, retiring it the moment the next successful reload supersedes the instance. `prepareSessionExtensions` is the announcement that a session is about to bind whatever the loader currently holds, so it RELEASES that claim (without retiring) on every exit path — including the first-session path that does no reload at all, and the path where the reload failed. Releasing is not optional politeness: a claim kept on an instance that has since gone live would retire a live panel's republisher on the next reload.
- Never infer a republisher's deadness from a throw: it retires live panels on unrelated failures, and it cannot see an unbound instance at all, whose `registerTool` succeeds into an unreferenced extension object and so never throws. Growth is the visible symptom — a window that never retires an unbound instance invokes a longer list of dead closures on every settings toggle.
- Every bind of the SHARED services must be announced by `prepareSessionExtensions()` — it is the handover point, so a bind that skips it leaves the runtime claiming a live instance as unbound and the next bare reload retires a live panel's republisher. `PiSession`'s session factory announces; `PiRuntime.createSession` does NOT announce for you, so any future caller of it must. Nested subagent/team sessions are exempt by construction, not by luck: `createSubagentSession` builds its own `AgentSessionServices` with its own `extensionFactories`, so it never binds this loader's instance and never registers a republisher into the shared set.
- Nested (subagent/team) MCP tools are delivered as `customTools` on `createSubagentSession`, never through the shared MCP registrar — and that is what PRESERVES the exemption in the bullet above, not a workaround despite it. `customTools` are read during construction, so a nested session still binds no shared loader instance and still registers no republisher into the shared set. "Simplifying" this into sharing the registrar reopens exactly the bug class the republisher-ownership model was built to close; do not, however much simpler it looks.
- A nested agent's MCP set is FROZEN AT SPAWN: one `getAllToolDescriptors()` read per spawn, from which its `tools:` names, its `customTools` definitions, its gate read-only classifier, its deferrable set and its ToolSearch blurbs are ALL derived. A second read anywhere in a spawn path reopens the divergence window — an `mcp__*` name in `tools:` with no matching definition is dropped SILENTLY (no error, no warning, no log), so set-equality between the two is what catches it — asserted at BOTH composition sites (`pi-session.ts`'s subagent and team engines), because a test that reaches only one of them leaves the other free to regress while the suite stays green. `createSubagentSession` also logs any orphan it is handed, since every nested spawn funnels through there and that is the one place the class is observable at runtime. A server connecting mid-run reaches the NEXT spawned agent, never a running one; there is no live top-up. (The freeze is over the descriptor set, not connectivity — a server still connecting but with cached descriptors is in the snapshot and callable, since `callTool` awaits `ensureConnected`.)
- The nested MCP grant is UNIFORM across every agent type and mode — Explore's explicit list, `tools: *`, and team specialists all get the panel's full eligible set. MCP names are dynamic and deployment-specific, so no agent author can name them in frontmatter; intersecting with the agent's `tools:` would give the explicit-list agents none. `disallowed_tools` is the one opt-out, and it is exact and CASE-SENSITIVE (`mapName` passes unknown names through unchanged) — a later "fix" that lowercases `mapName` would silently break every MCP denial.
- Every `_reloadResources` call is serialized on `_reloadSync`, and that serialization is load-bearing for the above, not just for `extendResources` ordering. A reload identifies the instance it minted through a single scratch slot written by `registerToolSearchRepublisher`; two overlapping reloads would let one adopt the other's instance, and adopting a session-bound instance as unbound freezes a live panel's ToolSearch menu with no error anywhere.
- ACCEPTED, documented in `damocles-extension.ts`: `AgentSession.reload()` emits `session_shutdown({reason:'reload'})` BEFORE awaiting the loader reload, so a reload that throws leaves the still-live panel with its republisher removed and no replacement — silently, since `runMcpReload` catches and logs. It self-heals on the next successful `session.reload()`. Do not add recovery machinery for it unless it is actually observed; the fix would be idempotent re-registration from a `session_start` handler guarded on the disposer being undefined.
- A tool's `description` is materialized at WRAP time, not per request (`wrapToolDefinition` copies it as a plain string). A getter alone does not stay fresh: `pi.registerTool` is the only public re-wrap trigger, so anything whose description tracks live config must be re-registered (`PiRuntime.republishToolSearch`, driven by `refreshActiveTools()`).
- Whatever `ToolSearch` advertises must be exactly what the session can load — the menu, the retry hint, the activation result and `/context` all derive from one loadable snapshot. Report what pi ACTUALLY activated (re-read after activating), never what was requested. MCP tool names/descriptions are third-party text rendered into a line-structured menu: strip control chars at build time or a name forges a group line.

## Permissions and plan mode

- All tool calls route through the central permission gate (`permission-gate.ts`): read auto-allowed, write/shell → diff approval. In plan mode, `Bash`/`PowerShell` are classified by `readonly-shell.ts` (fail-closed allowlist); non-plan-file `Edit`/`Write` stay blocked (the session plan file is the sole write carve-out); memory/Compass/enabled MCP tools stay available. The same classifier also holds a subagent whose resolved toolset has no write tool (`ResolvedToolset.readOnly` → `readOnlyShell`) in every mode — no write tool must mean no writes via the shell either.
- A block the runtime made itself (settings rule, plan mode, read-only agent, hook) uses `formatPolicyBlockReason`/`POLICY_BLOCK_MARKER`; only a real approval-prompt rejection uses `formatDenyReason`/`FEEDBACK_MARKER`. Never tell the model the user refused something the user was never asked. Both render as "denied"; `FEEDBACK_MARKER` is persisted in old sessions, so its value must not change.
- The on-disk plan file is the single source of truth for plan-mode handoff. `ExitPlanMode` takes no `plan` argument; everything reads it via `ChatSession.getPlanContent()`.
- Plan-mode guidance has one source: `pi-session/plan-mode-guidance.ts` (`buildPlanModeGuidance`), consumed by both `agent-start.ts` and `tools/plan-mode-tools.ts`. Edit the builder, not the call sites.
- The Damocles system prompt has one assembler: `agent-start.ts` (`assembleDamoclesSystemPrompt`). Never read `session.systemPrompt` for display — it holds pi's boilerplate outside a turn.

## Browser

- Browser tools resolve tabs through the caller's `BrowserAgentScope`, never a global active page: main agent + human share `PRIMARY_SCOPE_ID`; every subagent/team agent passes its own id and its scope is disposed at settle (tabs closed only on success).
- Anything a PAGE produces is hostile input on the extension host. Console/network/picker output is redacted and bounded at CAPTURE (`redaction.ts` + `collectors.ts`), never at a render site — the guarantee must not depend on whoever adds the next reader. The in-page bridge's caps live in the page's own world and are the page's to edit, so every bound is re-enforced host-side in `installContextObservers`/`onConsoleBinding`. Every redaction pattern must be linear-time (unrolled-loop form, bounded affixes): it runs synchronously on the host, so a backtracking pattern is a remote editor freeze.
- `ScreencastHealth`'s stall clock is armed by INTENT (`noteWanted`, on panel visibility), not by the CDP `start()` call — the webview's `ready` message is the sole trigger for `start()`, so anchoring on it makes the watchdog blind to a lost handshake.
- `damocles.browser.devToolsPort` (default on) opens an unauthenticated loopback CDP endpoint on the logged-in profile; it is a launch-time flag, so a change needs a relaunch.

## Teams and subagents

- Team message delivery branches on `TeamMessage.kind`, never on rendered text (a peer can mimic any prefix). `scratchpad-notice` reaches only a `standby` specialist; `ledger-notice` reaches no inbox at all (the ledger is a pull surface). Both still broadcast, so persistence/timeline/`getInbox` see every write — filter at DELIVERY, never at emission.
- The verification fingerprint is computed by the extension, never supplied by an agent (`team_record_verification` has no `fingerprint` param, asserted by test). It must fail VISIBLY: `unverifiable`, never a hash that silently missed files. `git status` needs `-uall -z` and paths resolved against `--show-toplevel` — without all three it goes blind to real edits (collapsed untracked dirs, C-quoted paths, subdirectory workspaces) and a stale pass looks reusable forever.
- The team profile catalog is generated, never hand-edited: change `agent-profiles/`, run `npm run generate:profiles`, commit the output (a pinned test locks the exact set). Its mirror policy (`TRACKED_DIVISIONS`, `EXCLUDE`, `DIVISION_ALLOWLIST`) is duplicated in `~/.claude/scripts/sync-claude-agents.mjs`, which governs `~/.claude/agents` — separate repos, no shared state, so edit both together. Both scripts and the generator fail closed (flattened-path collision, duplicate profile id): a profile must never go missing silently.
- Each nested spawn path collapses to ONE `buildAgentToolset` call (`agent-manager.ts`, and both `team-runner.ts` spawn sites), made INSIDE the per-spawn path for the same reason `buildExtensionFactory` is invoked per spawn: it must read live panel state at spawn. Hoisting it to a construction-time local would freeze the snapshot at team-construction time and silently miss a server the user enabled mid-run. `mcp.names` must reach `tools:`, `customTools` and `mcpToolNames:` from that one call — and `tools:` must never be narrowed to the deferred baseline, which evicts the tools permanently while ToolSearch still reports success.
- The read-only-agent rule is a SHELL-escape guard, not a general capability ceiling. `toolCategory('mcp__*')` is `'other'`, so the read-only branch does not catch MCP: a read-only subagent (Explore/Plan, or any agent with no write tool) CAN invoke a non-annotated MCP tool, and in `default`/`acceptEdits` it still routes through `canUseTool` and prompts. That is a DECISION, not an oversight — filtering it would make nested agents stricter than the panel and stricter than plan mode, and most servers omit `readOnlyHint` entirely so it would fail closed against the common case. The trust boundary for MCP is the server enablement list, not the agent type. Do not "fix" it in either direction without changing this line.
- A subagent's model is configuration, never the spawning model's choice: the `Agent` tool deliberately has NO `model` param. `resolveSubagentModel(agentConfig)` takes only a config — template `model:` > Explore settings (Explore only) > the panel's session model. An unresolvable/unauthed/out-of-scope template `model:` fails the spawn naming the template; never fall back to the session model, which leaves a broken pin working-but-wrong forever.
