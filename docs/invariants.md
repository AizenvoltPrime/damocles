# Invariants (long form)

Rationale and failure modes behind the one-line rules in `CLAUDE.md`. Read the entry before changing the subsystem it governs.

## Engine and message contract

- pi is the only agent engine; new sessions always construct `PiSession`. There is no harness selection.
- Map pi events to existing webview shapes via `pi-stream-adapter.ts` / `tool-normalization.ts`, never to a new message that mirrors a pi event. Add a message type to `src/shared/types/messages.ts` only for a user-facing capability no existing shape can carry (`steerTargets`, `resumeAccepted`, `sessionUsage`), with its producer and its webview handler in the same change.
- **`sessionUsage` is the only carrier of the status bar's billing totals.** Spend lands outside a completed turn: a stopped turn's partial request, a manual `/compact`, and the cache warmer's idle `usage` entries. `done` cannot carry it there, because the webview finalizes the streaming message on `done`, and `tokenUsageUpdate` is the context meter's last-request snapshot. Both producers build the message with `sessionUsageMessage` (`pi-session/session-usage.ts`): the adapter on every settle (aborted included), a microtask after each `message_end` whose message the inclusion rule counts (once pi has persisted it), on `compaction_end` with a result and on `entry_appended` for an entry that carries usage, and `history-loader.ts` on reload. `done` carries no totals.
- **`/stats` has no session producer.** `requestUsageStats`, `usageStatsProgress` and `usageStats` are produced by `message-router/handlers/usage-stats-handlers.ts` through `UsageStatsService` (`src/core/usage-stats/`), never by `PiSession`, because the figures aggregate every project and belong to no session. `/usage` sets the precedent: its handler posts straight to the webview. The three types exist because no existing message shape carries cross-project aggregates. The handler sends exactly one `usageStats` with `final: true` per `requestId`, including when validation or the worker fails, so the webview never waits on a request that already ended.
- `Edit` cannot create files (empty `old_string` throws). `Write` is the only text-file creation path. `GenerateImage` creates only a new image file, never overwrites, and goes through the same write gate (category `write`, never `GATEABLE_MODULE_NAMES`).
  - It is in `WRITE_TOOLS`, so plan mode and read-only agents block it with `formatPolicyBlockReason`, acceptEdits and YOLO allow it, `GenerateImage(<glob>)` rules match the path it writes (see "File rules" under "Permissions and plan mode"), and the checkpoint baseline wait applies. `GATEABLE_MODULE_NAMES` allows before the plan-mode check, so adding it there would let a planner spend money and write files.
  - The path resolves as `Write`'s does (`resolveToCwd`), must end in `.png`, `.jpg`, `.jpeg` or `.webp`, and is written with `writeFile(..., {flag:'wx'})`. The approved path is never changed: a returned MIME type that does not match the extension fails, writes nothing, and keeps `usage`.
  - It runs only in the main session. `resolveAgentToolset` and `teamAgentBaseToolNames` strip the name and no nested build carries the definition.
  - It is eligible only while `damocles.imageGeneration.enabled` holds, the chosen model resolves in pi's OpenRouter image catalog with finite, non-negative prices and a positive output token price (`isOfferedImageModel`), and `hasConfiguredAuth('openrouter')` holds. The `damocles.explore.apiKey.openrouter` secret reaches pi as the `openrouter` runtime key, which is what both that check and `ModelRuntime.generateImages` read, so the menu equals the loadable set. `syncCustomProviders` refreshes every panel's tools once the key is applied.
  - `damocles.imageGeneration.enabled` and `damocles.imageGeneration.model` are both user scope only (`scope: application` and `restrictedConfigurations`), and Settings writes both at user scope: one turns on spending, the other decides what each image costs. The approval prompt names the model and says the call is billed to the user's OpenRouter key.
  - It is not wrapped in `abortableTool`. pi forwards the tool's `signal` to the HTTP request, so an abort settles the call promptly, and a wrapper would answer first and drop the usage of a response that landed as the turn was aborted.
- Internal sub-calls (memory, structured output) use `PiRuntime.runStructuredCompletion` + the terminating-tool idiom (no `toolChoice`). Classifier sub-calls use `PiRuntime.runClassification`, which keeps untrusted text in `state`; see "Memory judges on Jev".
- Never mutate `process.env` for per-session config; pi reads a Damocles-owned `agentDir` (`~/.damocles/pi/agent`).
- **Account state has exactly one publisher.** `AccountInfo` derives from five inputs (active model, its catalog entry, Claude auth mode, OpenAI auth status, prefer-API-key) and was emitted once per adapter lifetime from `emitSessionStartOnce`, reached only at turn start. So a session restored from history never received it, and a model or auth change left it stale because the once-guard had already tripped. `PiSession.publishAccountInfo()` rebuilds and emits on demand, and is called wherever an input changes: session start, `setModel`, history replay, and both auth paths. It caches nothing, so it cannot drift from `buildAccountInfo`. A consumer must never paper over a missing publication with a fallback; fix the publisher.

- **`sessionStateChanged` has exactly one publisher, and every input it reads has exactly one mutator.** `PiSession.publishSessionState()` derives the state from the turn lifecycle plus every prompt map on `PermissionState` and `WebviewExtensionUIContext.pending`, and is the only site that constructs the message; the adapter reports the turn lifecycle through `onTurnStateChanged` instead of emitting. Those maps are mutated only inside `permission-handler/state.ts` and `extension-ui-context.ts`, because every mutator also fires the change notifier that reaches the publisher. A direct `state.pendingApprovals.delete(id)` in a manager (the shape seven abort handlers used before this rule existed) type-checks, keeps every test green, and parks the session on `requires_action` for the rest of its life with no dialog on screen, which is worse than the missing signal it replaced. `session-state.test.ts` ("single-writer discipline") walks every `.ts` file under `src/core` and `src/vscode` (`src/__mocks__/source-tree.ts`), allows the mutation only in `permission-handler/state.ts`, and enforces both halves. A consumer must never infer the state locally to paper over a missing publication; fix the publisher.

- `src/shared` must not depend on `src/core` or `src/vscode`, and that includes its tests. `tsconfig.webview.json` compiles `src/shared/**/*` for the webview bundle, so a file under `src/shared/__tests__` that imports extension code drags the extension host into the webview typecheck and fails the gate. A test whose subject is shared but which must read extension state belongs on the extension side; split it rather than moving it.

## Deferred tools / ToolSearch

- Browser/Compass/Web/Image/MCP tools are deferred: registered but inactive, activated only via `ToolSearch` (`tools/deferred-tools.ts` is the leaf that owns the universe). They must stay in pi's `tools:`/eligible set. Dropping a name removes it from the registry and `setActiveToolsByName` silently ignores unknown names, so it could never come back. Deferral is only safe where `ToolSearch` is actually registered; gate on that, never on it merely being allowed. A built-in ToolSearch group equals a Tools-panel subsystem: the whole subsystem defers or none of it does, so there is one rule for the model and one line in the menu. MCP defers per tool, by the exposure each descriptor carries (`mcp/exposure.ts`): `off` is subtracted from eligibility through the one `disabledToolSet()` gate (`offToolNames()`), `direct` (Always loaded) is eligible and active from the first turn and never on the menu, and only `deferred` tools are deferrable (`deferrableToolNames()`). An MCP group line lists that server's deferred tools only. Every deferral call site (the panel's active set and snapshot, `FolderRuntime.createSubagentSession`, the subagent and team extension factories) passes the deferrable MCP names, never all MCP names; a site that passes all of them holds an Always-loaded tool back and advertises it. An exact-name request for an active tool outside the deferrable set, such as a direct MCP tool, is answered as already active, never resolved, and so is a request for a server group with no deferred tool whose eligible tools are Always loaded (`directMcpGroups`, `NestedMcpToolset.directGroups`). `buildNestedMcpToolset` skips an Off descriptor itself and grants only `direct` beside `deferred`, whatever eligible set it is handed.
- The deferrable universe composes from leaf spec modules only, never a barrel. `deferred-tools.ts` documents itself as composing the `*_PI_TOOL_NAMES` exports and importing nothing else, and `tool-search.test.ts` ("deferred-tools.ts import discipline") enforces it to keep the eval-time cycle `permission-gate` → `tool-catalog` → `browser-tools` closed. A barrel that re-exports runtime modules (as `web-access/index` does with `./config`, which reads settings through `platform-host`, and `./web-tools`, the tool bodies) forces that guard to be relaxed to "any import is fine", retiring it for every future group. Add a `-tool-specs` declaration leaf instead. The reason is guard preservation, not startup cost.
- A system prompt must never name a deferrable tool without stating how to load it. A deferred tool is not callable on turn one, so a prompt that names one without an adjacent `ToolSearch({tools:["<group>"]})` step is a dead end. The model calls it and gets an unknown-tool error. This held in five places at once (`system-prompt.ts`, `plan-mode-guidance.ts` ×2, `subagents/default-agents.ts`, `compass/system-prompt.ts`); the subsystem's enabled-ness is no defence, since that flag is exactly what makes the names eligible and deferred.
- ToolSearch republishers retire deterministically, never by exception, and every registered closure has exactly one owner responsible for retiring it. Which owner applies depends on whether an `AgentSession` ever binds the extension instance that registered it, and the two cases are genuinely different. Do not collapse them:
  - **Session-bound instances retire themselves.** `PiRuntime.registerToolSearchRepublisher` returns a disposer the instance calls from its own `session_shutdown` handler, for every reason, `'reload'` included. This deliberately diverges from the observe-only lifecycle handlers in `hooks/index.ts`, which skip `'reload'` because an internal rebuild is not a user-meaningful session end; here a reload genuinely retires the instance.
  - **Unbound instances are retired by `PiRuntime`.** `resourceLoader.reload()` also runs the extension factory where no bind follows, at four sites: the `.damocles`/`.claude`/`.codex` asset watcher, the workspace-trust grant, `_hotReloadExtensions`, and `_removeSubscriptionPlugin`. `createAgentSessionServices` also mints one at init before any session exists. Such an instance receives no session event at all, so there is no owner inside it. `_reloadResources` takes a `ReloadBinding` argument stating which kind of reload it is, and the runtime holds the unbound instance's disposer in `_unboundRepublisherDisposer`, retiring it the moment the next successful reload supersedes the instance. `prepareSessionExtensions` is the announcement that a session is about to bind whatever the loader currently holds, so it releases that claim (without retiring) on every exit path. That includes the first-session path that does no reload at all, and the path where the reload failed. Releasing is not optional politeness: a claim kept on an instance that has since gone live would retire a live panel's republisher on the next reload.
- Never infer a republisher's deadness from a throw: it retires live panels on unrelated failures, and it cannot see an unbound instance at all, whose `registerTool` succeeds into an unreferenced extension object and so never throws. Growth is the visible symptom. A window that never retires an unbound instance invokes a longer list of dead closures on every settings toggle.
- Every bind of the shared services must be announced by `prepareSessionExtensions()`. It is the handover point, so a bind that skips it leaves the runtime claiming a live instance as unbound and the next bare reload retires a live panel's republisher. `PiSession`'s session factory announces; `PiRuntime.createSession` does not announce for you, so any future caller of it must. Nested subagent/team sessions are exempt by construction, not by luck: `createSubagentSession` builds its own `AgentSessionServices` with its own `extensionFactories`, so it never binds this loader's instance and never registers a republisher into the shared set.
- Nested (subagent/team) MCP tools are delivered as `customTools` on `createSubagentSession`, never through the shared MCP registrar. And that is what preserves the exemption in the bullet above, not a workaround despite it. `customTools` are read during construction, so a nested session still binds no shared loader instance and still registers no republisher into the shared set. "Simplifying" this into sharing the registrar reopens exactly the bug class the republisher-ownership model was built to close; do not, however much simpler it looks.
- A nested agent's MCP set is frozen at spawn: one `getAllToolDescriptors()` read per spawn, from which its `tools:` names, its `customTools` definitions, its gate read-only classifier, its exposure split (`deferrable` and `direct`, so `deferrable ⊆ names`) and its ToolSearch blurbs are all derived. The direct names reach `createSubagentSession` as `directMcpToolNames`, which only subtracts from the deferral: omitting it defers every MCP tool rather than activating any. A second read anywhere in a spawn path reopens the divergence window. An `mcp__*` name in `tools:` with no matching definition is dropped silently (no error, no warning, no log), so set-equality between the two is what catches it. Asserted at both composition sites (`pi-session.ts`'s subagent and team engines), because a test that reaches only one of them leaves the other free to regress while the suite stays green. `createSubagentSession` also logs any orphan it is handed, since every nested spawn funnels through there and that is the one place the class is observable at runtime. A server connecting mid-run reaches the next spawned agent, never a running one; there is no live top-up. Each frozen tool also carries the `serverId` it was captured from and calls with `expectedServerId`, because tool names are reassigned live (a folder server's tools are named with the user servers' tool names reserved, so a user server made visible takes a colliding name back and the folder tool moves to a hashed name): a name that has passed to another server fails as vanished rather than running that server's tool under the snapshot's read-only classification. (The freeze is over the descriptor set, not connectivity. A server still connecting but with cached descriptors is in the snapshot and callable, since `callTool` awaits `ensureConnected`.)
- The nested MCP grant is uniform across every agent type and mode. Explore's explicit list, `tools: *`, and team specialists all get the panel's full eligible set. MCP names are dynamic and deployment-specific, so no agent author can name them in frontmatter; intersecting with the agent's `tools:` would give the explicit-list agents none. `disallowed_tools` is the one opt-out, and it is exact and case-sensitive (`mapName` passes unknown names through unchanged). A later "fix" that lowercases `mapName` would silently break every MCP denial.
- Every `_reloadResources` call is serialized on `_reloadSync`, and the ownership rules above depend on that serialization, not just on `extendResources` ordering. A reload identifies the instance it minted through a single scratch slot written by `registerToolSearchRepublisher`; two overlapping reloads would let one adopt the other's instance, and adopting a session-bound instance as unbound freezes a live panel's ToolSearch menu with no error anywhere.
- accepted, documented in `damocles-extension.ts`: `AgentSession.reload()` emits `session_shutdown({reason:'reload'})` before awaiting the loader reload, so a reload that throws leaves the still-live panel with its republisher removed and no replacement. Silently, since `runMcpReload` catches and logs. It self-heals on the next successful `session.reload()`. Do not add recovery machinery for it unless it is actually observed; the fix would be idempotent re-registration from a `session_start` handler guarded on the disposer being undefined.
- **An extension instance is process-global and outlives any one session, so its `session_shutdown` handler retires only what the instance owns outright: the ToolSearch republisher above. Its event handlers stay registered.** `SessionShutdownEvent` carries no session id (`types.d.ts:609-614` in pi 0.99.2, as are the dist lines below), so an instance-wide response to it answers for every session bound to that instance, including the one that binds it next. That next session is reachable, because a failed `prepareSessionExtensions` reload leaves `getExtensions()` returning the previous array (`resource-loader.js:417`; the catch in `FolderRuntime.prepareSessionExtensions`, `folder-runtime.ts`). Retiring the handlers empties the instance's map (`loader.js:213-230`), and pi then skips the gate outright rather than calling it, since `beforeToolCall` treats `hasHandlers('tool_call') === false` as proceed (`agent-session.js:308-312`), so the session runs with no permission gate, no system prompt injection, no checkpoints and no hooks. Ownership is decided per dispatch by the session-keyed registries, `_panelRegistry` and `_checkpointRegistry`, never by instance-wide state. A tool call that finds no panel is blocked by `gateErrorFallback` rather than proceeding, because only main panel sessions dispatch into this instance and each is registered until its panel closes. The per-subagent instance retires nothing at all, since `createSubagentSession` gives each spawn its own services and loader and a nested session is disposed without an `AgentSessionRuntime` to emit the event. `handler-disposal.test.ts` pins three things: the handler count is unchanged after every shutdown reason, a session bound after a shutdown still gets its gate, prompt, checkpoints and hooks, and an unowned tool call is blocked.
- A tool's `description` is materialized at wrap time, not per request (`wrapToolDefinition` copies it as a plain string). A getter alone does not stay fresh: `pi.registerTool` is the only public re-wrap trigger, so anything whose description tracks live config must be re-registered (`FolderRuntime.republishToolSearch`, driven by `refreshActiveTools()`).
- Whatever `ToolSearch` advertises must be exactly what the session can load. The menu, the retry hint, the activation result and `/context` all derive from one loadable snapshot. Report what pi actually activated (re-read after activating), never what was requested. MCP tool names/descriptions are third-party text rendered into a line-structured menu: strip control chars at build time or a name forges a group line.

## Tool overrides

- A custom tool registered under a pi built-in's name replaces it. `_refreshToolRegistry` seeds the built-in definitions first, then writes every custom tool into the same map, so the last write wins. That is the only seam Damocles has for changing a built-in's behaviour, and it fails silently in both directions: a name that does not match exactly registers a second tool instead of overriding, and a built-in renamed upstream leaves the override in place as a tool nothing calls. `bash` is one live case, owned so a per-call `AbortController` can reach the running command.
- `grep` and `find` are overridden so they never reach pi's tools manager (`tools/search-tools.ts`). pi resolves `rg` and `fd` there, looking in its own bin directory (`~/.pi/agent/bin`) and then on PATH, and downloads whichever it finds in neither from GitHub into that directory: a network connection the README's privacy statement does not name, a write into the pi CLI's directory, and an unsigned executable run by a signed app. pi's `grep` takes no binary path, so Damocles keeps pi's definition and replaces `execute` with a copy that runs the ripgrep `@vscode/ripgrep` ships. `search-tools.test.ts` runs pi's own `grep` against the same rg as the oracle, comparing text, `details` and errors, and pins pi's parameter names to `GREP_PARAMETER_NAMES`, so a pi upgrade that changes the output or adds a parameter fails there. The one deliberate difference: a match whose path is not UTF-8 counts toward pi's limit but not toward ours, since neither prints it.
- `find` goes through pi's `operations.glob` hook instead, with ripgrep listing the files and `fdGlobMatcher` applying fd's rules: smart case, dotfiles, a name match without a `/`, no `!` negation and no extglobs. The pattern is matched in JavaScript because an rg `--glob` include overrides `.gitignore`, which fd's never does. rg runs with the search root as its working directory, because rg matches its globs against the path below that directory and the hook's `node_modules` and `.git` excludes would otherwise reject every file under a root inside either. The hook, not fd, is where those two excludes come from. Directories are derived from the listed files, so unlike fd `find` reports no empty directory, no directory whose files are all ignored, and no symlink. The hook branch of pi's `find` drops the "Use limit=N for more" hint its fd branch gives, and `createFindTool` puts it back.
- An override keeps the built-in's exact name, lowercase `bash` included. The permission gate classifies by the mapped name (`mapPiToolName` then `toolCategory`, `permission-gate.ts:159` and `permission-gate.ts:214`), and `PI_NATIVE_ACTIVE_TOOLS` plus every subagent and team toolset carry the pi spelling, so renaming to `Bash` means changing the gate, plan-mode classification, the read-only shell classifier, the active-set lists and the tool catalog together, and whichever one is missed fails open rather than loudly. `Edit` renamed because its schema had to diverge from pi's; bash's does not, so it has no reason to pay that price.
- Never pair an override with an `excludeTools` entry. `isAllowedTool` filters custom tools through the same allow and exclude sets as the built-ins, so excluding `bash` drops the replacement along with the original and leaves the model with no shell at all. The `edit` exclusion is not a precedent for it: that one is safe only because the replacement registered under a different name.
- Reading a host service at construction rather than at execute makes that service a precondition of building the session, not of running the tool. `createBashTool` spreads its metadata from a delegate built during `buildCustomTools`, so `createBashToolDefinition`, `getShellCommandPrefix` and `getShellPath` must all answer before a `PiSession` exists at all, and so must `createGrepToolDefinition` and `createFindToolDefinition` for the search overrides; four test files needed their doubles extended each time an override landed. The search overrides read `platform().paths` only at execute time, through the rg path thunk, so the platform is not a precondition of building a session. The symptom is a `TypeError` several frames inside session construction, naming a method rather than the tool that asked for it, and every later assertion then fails on a null session, so the cascade points nowhere near the cause. Suspect an incomplete double before suspecting the session. The construction-time read is still the right trade, since it is what keeps the model-visible schema and the system prompt identical to pi's, but the cost lands on whoever writes the next session test.

## Shell cancellation and process lifetime

- **A cancelled shell call says so in exactly one place: `details[CANCELLED_TOOL_DETAIL_KEY]` on the tool result** (`src/shared/types/session.ts`). `withPerCallCancel` sets it on both exit branches, merged over `lastPartial?.details` so the partial's `fullOutputPath` and truncation fields survive rather than being replaced (`tools/cancellable-shell.ts`, `cancelledDetails`). Both branches return a normal result, never an error, because the user asked for the stop and the retry heuristics that treat an error as worth retrying must stay quiet; so a cancelled call always lands as `toolCompleted` and the marker on `details` is the only thing that tells the card apart from a success. It rides on `details` because `details` is persisted and re-read on reload, which view state is not, and because the cancel registry releases its entry in a `finally` that runs before pi emits `tool_execution_end`, so a registry side-channel keyed by tool call id could not answer at the time the card is built. The guarantee is only as good as its producers, and there are three: `pi-stream-adapter.ts` and `subagents/subagent-stream-bridge.ts` emit `toolMetadata` from `result.details`, and the team path carries it on `teamAgentToolResult.metadata` (`src/core/team/agent-runner.ts`), which was added because the team path dropped `details` outright and rendered a cancelled command as a green check. A new producer that does not carry `details` reopens exactly that. The reload path is a fourth producer and needs the marker too: `agent-runner.ts` persists a `tool_result` entry per call carrying `content`, `is_error` and the normalized `metadata`, and `useTeamStore.handleAgentDataLoaded` indexes those by `tool_use_id` and derives the same three statuses the live path shows. Persisting `content` alone would leave a reloaded cancelled call indistinguishable from a success, which is what the hardcoded `status: 'completed'` it replaced did to cancelled and errored calls alike. A call with no persisted result restores as `unrecorded`, a terminal status of its own: `completed` would claim an outcome that was never recorded, while `pending` and `running` are pre-terminal and put a spinner, a Stop control and a "Tool is running..." overlay on a tool that ended long ago. The main-session replay path derives the same status from the same fact (`convertHistoryTools`, `src/webview/composables/message-handler/utils.ts`), and so does the subagent transcript loader (`buildChatMessagesFromHistory`, `src/webview/stores/useSubagentStore.ts`), which is why `unrecorded` lives on `ToolCall['status']` rather than inside any one loader. `handleAgentDataLoaded`, `convertHistoryTools` and `buildChatMessagesFromHistory` all read a transcript whose run is over. The subagent one is reached only by a resume from disk and by the single `subagentMessagesUpdate` the stream bridge emits from `finish()`, so a block with no recorded result is unrecorded rather than still running. The live subagent path is a different function, `buildToolCallsWithStatus`, which sees a `tool_use` block before pi has started the tool and so defaults to `pending`, never to a terminal status. Team logs written before this landed hold no `tool_result` entries and cannot be repaired.

- **A cancel note is user turn content, delivered to the agent that ran the command, and never executed.** It is never appended to the tool result. A tool result is untrusted by construction, so an instruction found in one is prompt injection, and a correctly aligned model refuses it; that was observed, not predicted, before the note moved. The trailer says only that the user cancelled, how long the command ran, and that a reason follows. Delivery is bound per build context (`note-delivery.ts`, one builder per context, one `PiSession` method per builder), so the target is fixed when the tools are built rather than guessed when Stop is clicked: the panel session steers it through `prompt(..., { streamingBehavior: 'steer' })`, a subagent takes the steer channel a typed `/steer` uses, and a team agent takes `deliverUserNote`, the sink its own runner publishes for the duration of its run. A single delivery for all three would land a subagent's note on the main conversation. All three reach the agent at the next tool boundary of the run the command belongs to, so the model's next request carries the cancelled result and the note together. Never deliver the panel note as a follow-up: pi hands a follow-up over only once the model has stopped calling tools, so the model answers the cancelled result, typically by waiting for the reason the trailer promised, before it sees the note. The note arrives while the command is still dying, since the call's registry entry lives until the tool settles and the run cannot end before its tools do, so pi accepts it into the running run. `expandPromptTemplates: false` is the whole leading-slash guard: it switches off the extension-command dispatch and the skill and template expansion inside `prompt()`, so a note beginning with `/` is queued as literal text and cannot be executed or throw. Do not swap it for `steer()` or `followUp()`, which run `_throwIfExtensionCommand` unconditionally, nor for string mangling of the user's text. The same binds any path that puts a note back into pi's queue after taking it out, and any path that prompts queued content through `prompt()`, whose `expandPromptTemplates` defaults to true where `sendUserMessage`'s defaults to false. The team runner sends every flush of queued content through one wrapper that passes false. A note is the one queued string with no `[Message from X]:` prefix to make a leading slash impossible. Sanitization follows the trust level rather than the source: `stripBidiControls` stays because a human renders the note, `stripControlChars` is gone because it flattened the newlines the note box now lets the user type, and the 500 character cap is gone because truncating changes what the user asked for. No cap replaced it at any layer, and that is deliberate: `sanitizeCancelNote` strips and trims only (`tools/shell-cancel-registry.ts`), the note textarea carries no `maxlength` (`ToolCancelControl.vue`), and the router forwards `msg.note` unchanged (`chat-handlers.ts`, the `cancelToolCall` handler). The note is one human-authored message delivered to the agent as user turn content, so a cap can only drop the end of a reason the user meant the agent to read. Exactly one user-visible echo per context, `userMessage` for the panel, `subagentSteered` for a subagent, `teamAgentUserMessage` for a team agent. Zero echoes makes the model act on an instruction the user cannot see in the transcript; two double-render it. The team seam deliberately bypasses the `MessageBus`. A note sent through the bus is dropped with no signal to the sender once the run's `unsubscribeBus()` has fired, and again when the sender token equals the agent's own name, so the sink returns false instead and the caller logs it. The panel's echo is emitted when pi accepts the note, not when the delivery is called and not when pi delivers it, which is the last point still synchronous with the click and is where the subagent and team contexts echo too. A path that takes an accepted note back out of pi's queue owes the user a correction, which is what `withdrawQueue`, shared by `stopForBudget` and `beginAbort`, emits through `dropEchoedNotes` when it drops the queue. That correction covers every echoed note not yet delivered, not only the ones found in pi's queue, because a re-steer holds notes outside pi's queue while it puts them back.

  **A queued chip batch never displaces a panel note, and the note goes first.** `resteerQueuedInputs` re-steers the whole batch on every queued message, and the `clearQueue()` each pass (`resteerOnce`) needs drops every pending steer, the note included. So it puts back the accepted notes pi still held (`heldNotes`, pi's undelivered steers matched one for one against `injectedNotes`, so a batch whose text equals a note stays a batch), then the batch, each awaited so pi's queue holds exactly that order, and re-queues follow-ups, all through `sendUserMessage(..., { expandPromptTemplates: false })`. A note accepted while a batch is already queued triggers the same re-steer. Both reach the model in the same request, the note right after the cancelled result and the batch after the note, so one reply answers both (see the next paragraph). A note is listed in `injectedNotes` before it is handed to pi, so its delivery can never be read as the batch however soon pi delivers it.

  **Every pending steer reaches the model at the next boundary.** Every pi `SettingsManager` Damocles creates goes through `withQueuePolicy` (`pi-session/queue-policy.ts`), which pins its `getSteeringMode()` to `all`: the folder's, which every panel session, replacement and reload builds on, the in-memory one each nested session gets (subagents, team agents, `/btw`), and the package manager's, so the rule has no exception. pi reads the mode only through that method, when `createAgentSession` builds the agent and when `AgentSession.reload()` re-syncs it after re-reading the settings files, so the pin outlives every reload. pi's default, `one-at-a-time`, hands the model one steer per boundary: a note and a batch pending together were answered in two model calls, the first reply covering the note alone. The mode is not carried by a setting. `applyOverrides` is dropped by `settingsManager.reload()`, which pi runs in `AgentSession.reload()` and in every `resourceLoader.reload()`. A value in the Damocles agent `settings.json` loses to a trusted project's `.pi/settings.json`, because pi merges project over global. pi exports no `SettingsStorage` implementation to wrap, so a storage layer would mean reimplementing pi's locked file storage. A project may not override the policy: only Damocles puts steers into its sessions' queues, the note-then-batch order and the single reply depend on it, and a repository file that changed it would split them with nothing telling the user. `AgentSession.setSteeringMode` bypasses the pin and writes the global file, and nothing in Damocles calls it. `followUpMode` keeps pi's default, since a Damocles session never holds two follow-ups: `sendMessage` refuses a second prompt while one runs, and every other queued input is a steer. Several user messages can now arrive at one boundary, so the adapter finds each delivered batch's and note's entry by message identity for its mid-stream marker (`resolveMidStreamMarkers`), because the branch's last user entry names only the last of them. The checkpoint engine still mints one turn per boundary, keyed on the last user entry: no tool runs between messages delivered together, so a second turn would snapshot the same tree, and a mid-stream row has no rewind control. A subagent or team agent gets every steer pending at a boundary together too, each still its own user message, so no steer shares a message with peer text. `queue-policy.test.ts` pins the folder session over a project and an agent file that both ask for `one-at-a-time`, across `session.reload()`, a nested session, and that every `SettingsManager` factory call under `src/core` and `src/vscode` is wrapped.

  **A note pi accepts with no run in progress starts one, and that run belongs to the prompt the note annotates.** pi reports acceptance through `preflightResult`, after queueing (`queued`) or immediately before starting that run (`started`), so the echo still waits only for acceptance, and `noteDeliveryForMain` opens a turn for such a run because no `sendMessage` did. `handled` means an input handler consumed the note, so pi neither queued nor ran it: the note leaves `injectedNotes` with no echo, and a later stop has no discarded note to report. The note's committed entry gets its mid-stream marker from the run's opening user message, which pi emits like any other delivery. The cancelled call's `details` carry the note's text under `CANCEL_NOTE_DETAIL_KEY` (pi never sends `details` to the model, so this is not the note in a tool result), and `isCancelNoteDispatch` (`session-store/prompt-index.ts`) recognises a dispatch whose prompt is the note of a cancelled call no user message has followed yet.

  **pi's input handlers judge each queued message once, as it is queued, and the batch carries only the messages they let through.** `queueInput` holds a message in `screeningInputs` while `screenQueuedInputs` runs `extensionRunner.emitInput` on it as `interactive` input with `streamingBehavior: 'steer'`, one message at a time and oldest first, so the batch keeps the order the user typed in. That is how a UserPromptSubmit hook (the configured-hooks `input` handler) and every other loaded extension's `input` handler see a typed prompt. A message a handler answers `handled`, which is what a hook's block is, loses its chip through `queueCancelled` without `returnToInput`, and the hook's reason reaches the user through the `notification` the hook handler posts for any blocked prompt; a `transform` rewrites the message before it joins `queuedInputs`. The combined re-steer is then sent as `source: 'extension'`, which the configured hooks skip, as they skip a cancel note and anything else from an extension. Never let a hook judge the combined batch: it would run once per re-steer on text it already judged, stash its `additionalContext` once per pass, and block or allow a message by the messages beside it, and a block there names no chip, so every chip would stay pending. With no input handler loaded, a message is admitted synchronously, so the first re-steer still starts before `queueInput` returns.

  **Re-steers run one pass at a time, so pi never holds two batches.** A pass awaits pi's input handlers inside `prompt()`, which another loaded extension can hold for as long as it likes. Two passes in flight at once each clear pi's queue before the other has queued anything, then both queue, and the model receives the first batch and then the combined one. A queued message that arrives while a pass runs sets `resteerRequested`, and the running loop makes one more pass that reads the buffer as it is then; the first pass starts synchronously, so the common case still steers before `queueInput` returns. `steeredCount` records how many leading inputs the batch pi holds carries, set from `preflightResult`, which pi calls synchronously right after queueing and so before any boundary can deliver it. A delivery consumes exactly those inputs, so one queued after that batch was steered keeps its chip and goes out with the next pass rather than being reported delivered. `admitSteer` acts on pi's disposition: on `started` the batch opens a run of its own, which it opens as a turn because no `sendMessage` did; on `handled` an extension command or input handler consumed the batch, which pi neither queued nor ran, so its inputs leave the buffer and their chips are cancelled.

  **A stopped run delivers nothing more from pi's queue, and nothing it held reaches the next run.** pi keeps both queues across `abort()`, and the next run polls the steering queue before its first request (`runLoop` in `@earendil-works/pi-agent-core`, `agent-loop.js`), so a leftover batch or note would reach the model at the start of the next prompt, unmatched and counted as a prompt. ESC (`beginAbort`) and the budget stop (`stopForBudget`) both go through `withdrawQueue`, which clears pi's queue, returns every chip to the composer, the ones still being screened included (`queueCancelled` with `returnToInput`, which the webview appends after whatever the box holds, images included), and drops the notes pi held with their echoes corrected, since each annotates a command in the turn that was stopped. A queued message was never sent, so no stop may discard it. `beginAbort` clears the queue again once the abort settles, for a note a re-steer was putting back. A note for a stopped run (`runStopped`: the budget stop pending, or an abort not yet settled) is refused at the click and again at acceptance, when a stop landed while pi ran its input handlers, and the user is told it was not sent instead of shown an echo; queueing it would bill a continuation past the limit, because `_runBeforeSettleBoundary` continues on a non-empty queue whatever the decider answers. A re-steer the stop withdrew (`batchWithdrawn`: its inputs are no longer the head of the buffer, or the session was replaced) is judged in `admitSteer`, from `preflightResult`, which is the one point every steer passes after all of pi's input and `before_agent_start` handlers, whichever extension registered them and in whatever order they run. pi calls it synchronously right after queueing the batch into the running run, where a withdrawn batch is taken back out, or right before `_runAgentPrompt` opens a run with it because the run ended while those handlers ran. There a withdrawn batch is refused by throwing `WithdrawnSteerError`: pi calls `preflightResult('started')` outside its preflight `try` on that path, so the throw rejects that `prompt()` before any run starts or anything is persisted. Never move the check into an `input` handler: pi runs handlers in extension order, so a handler registered after the check could still hold the batch, and every await after the handlers (the auth check, a pre-prompt compaction, `before_agent_start`, image resizing) is a window an ESC can land in. A pass never calls `prompt()` while pi is settling an ended run (it awaits `waitForIdle` when no run is streaming), because pi defers such a prompt into that settle and a throw from it would reject the settle of the run before.

- **The shell process-lifetime path has no timer, interval or process-table read on any platform, and neither arm carries shell-specific knowledge** (`tools/process-tree.ts`). Windows puts each spawned shell in its own job object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` and terminates it explicitly on abort; POSIX signals the process group, which works because both shell tools spawn with `detached: process.platform !== 'win32'` (`tools/bash-tool.ts`, `tools/powershell-tool.ts`, carried over from pi's own bash tool at `packages/coding-agent/src/core/tools/bash.ts` in pi 0.99.2) and a non-interactive bash leaves its background jobs in that group. **Two things are carried over from that tool, not invented here, and both have to move when it moves: the `detached` flag, and the exit code a signal-killed shell reports.** Damocles reimplements the operations so it can name the pid, so it owns the second one too: a null exit code becomes `128 + <signal number>` when a signal named the termination and `1` when none is named, applied where the tracked bash operations return, after the abort and timeout throws, and in the PowerShell `close` handler. The parity is behavioural rather than textual, and describing it as "the same code" is how the next editor gets it wrong. pi reads `child.signalCode` after its wait resolves; Damocles captures the signal in its `exit` handler and carries it out of `waitForShellExit`, which resolves `{ code, signal }` for that reason. Only an external kill reaches the mapping in the bash tool, because the abort and timeout throws still precede it, so `aborted` and `timeout:<seconds>` are unchanged and a cancelled or timed-out command still reports no exit code. PowerShell resolves a run object instead of throwing, so its timeout branch returns before the exit-code line; without that ordering a timed-out command would gain a trailing `[exit code 137]` and the timeout text would change. A null exit code no longer passes as success in either direction: pi's tool body throws `Command terminated without an exit code` on one, and neither Damocles spawn site can report a terminated shell as a null exit code. `bash-operations.test.ts` > "an externally killed shell" pins the two implementations to the same answer rather than to a fixed number, because win32 reports a plain exit code where POSIX reports a signal. Job membership is inherited and cannot be escaped, `BREAKAWAY_OK` deliberately unset, so a severed parent link stops mattering and the kernel walks nothing. Two earlier designs were tried and deleted, a process-table poller and an MSYS `ps -W` group lookup, and both were compensating for not having that one property; the measurement that killed the poller is that the fork helper lives about ten milliseconds while the cheapest query reporting parent links costs 384ms, so no polling rate can observe the link. `createShellJob(pid, shellJob)` must stay the first statement after `spawn` in both shell tools: the two assignments cost 0.13ms and Git Bash forks its background jobs 10 to 20ms in, so the margin is about a hundredfold, but a child created before assignment is outside the job permanently and unkillable. The no-running-cost rule is asserted, not argued, by `bash-operations.test.ts` > "no running cost in the process-lifetime path", which drives a full call including the abort and pins the global `setInterval`, `node:timers` and `node:timers/promises` all uncalled plus exactly one spawn; a poller reaching for any of the three goes red, checked by reintroducing one.
- **The Windows jobs are nested, and only the outer one kills on close.** A call job holds one shell call; a session job holds the panel and carries `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`. The two ways a call job ends are not symmetric and must never be described together. Stop terminates it, which kills every member, the background jobs the command left included, and reaches nothing outside that call; that is the defect this exists to fix. The end of a normal call merely releases the handle, which kills nothing. The whole difference is one `TerminateJobObject`, and grouping the two is how a reader concludes that Stop leaks. **The rule that keeps this correct is that the call job never carries kill-on-close**: releasing its handle at the end of a call has to leave a deliberately backgrounded process running, which is what makes Windows match the POSIX process group, and adding that one flag is the silent undo (it reads as harmless and turns the "outlives its call" case red, which is how it is pinned). The assignment order, session job then call job, is convention and not the thing keeping this correct: reversing it was mutation-tested and every case still passed, because the shell ends up a member of both jobs either way. Do not write, or rely on, "the order forms the nesting". `BREAKAWAY_OK` stays unset, since a child that could leave defeats the design.
- **The session job is per panel, held on `PiSession`, and there is deliberately no module-level instance.** One panel is one `PiSession` and a user can have several open, so a host-wide job would either kill another panel's commands when one panel is disposed, or, if never closed, degrade session cleanup into host-exit cleanup. Neither failure shows up in a single-panel test. Its lifetime is the panel and not the conversation: `PiSession` survives `reset()` and `clear()`, so tying the handle to the pi `AgentSession` would make `/clear` kill a process the user backgrounded earlier, which is the exact behaviour the nesting exists to preserve.
- **State the parity, then name the mechanism, because they are not the same thing.** Stop, background survival, cleanup at session dispose and cleanup after a host crash now behave the same on Windows, Linux and macOS. The mechanisms differ and must never be collapsed into one sentence. Windows nests job objects and gets the dispose and crash cases from `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` on the outer one (`tools/process-tree.ts`). POSIX has no job object, so `createShellSessionJob()` returns a sentinel-backed handle instead (`tools/shell-sentinel-client.ts`, driving the bundle built from `tools/shell-sentinel.ts` to `dist/sentinel.js`): one helper process per panel, spawned `detached` with `stdio: ['pipe', 'ignore', 'ignore']` so the host keeps the write end of the helper's stdin, with each shell's process group id written down that pipe as the command starts. Both platforms take the crash guarantee from the same property, the kernel acting at process teardown with no cooperation from the dying process: Windows releases the last job handle, POSIX closes a dead process's file descriptors, so a pipe whose only writer has died gives its reader EOF. **One pipe is both the registration channel and the liveness channel, and that is the design rather than an economy.** A heartbeat, a goodbye message or any other separate liveness signal would need code running in the dying host, which is precisely what SIGKILL and an OOM kill deny. Panel close and host death are therefore one code path: `dispose()` calls `child.stdin.end()`, and calling `end()` rather than dropping the reference is what actually produces the EOF. Do not add a second killer inside `dispose()` on the grounds that it is synchronous and can report failure; it would need its own copy of the identity check below, and that check is the one part of this feature that can kill a stranger's process if it is wrong. Never write that the two platforms reach this the same way.
- **The write end must reach the sentinel and nothing else, or the EOF never arrives.** A duplicate of that fd in any longer-lived process holds the pipe open, and the guarantee degrades silently to "the sentinel acts when the last copy closes", which for a long-running server is never. It holds today because libuv creates the parent-side stdio ends close-on-exec, and only the fds named in a child's `stdio` array are `dup2`'d onto 0, 1 and 2, which clears close-on-exec on those copies alone. Checked against a live `/proc` snapshot under WSL rather than assumed: with a detached shell and its background jobs running, the shell's fd table held exactly `0`, `1`, `2` and nothing else, while the host held the write end and the sentinel held its peer. Anything that later spawns with an explicit fd list, or gives a descendant of the host `stdio: 'inherit'`, has to be re-checked against that table, and the check is behavioural too: if `dispose()` on a live panel no longer kills the group, an inherited write end is the first place to look.
- **No sentinel on Windows, and the reason is not symmetry.** `createShellSessionJob()` dispatches on platform in its first statement and the win32 arm never reaches `shell-sentinel-client.ts`. A job object is kernel-owned and has no userspace component that can be killed, starved or crashed, so it is strictly better than a helper process; putting a sentinel beside it would add a weak point and buy nothing. This is asserted rather than argued, by `process-tree.test.ts` > "starts no sentinel on win32, where the job object already gives the guarantee", which pins zero `startShellSentinel` calls and zero spawns. The cost the POSIX arm pays for having no job object is real and worth knowing before anyone adds a second helper: one idle sentinel measured about 43 MB VmRSS and 7.1 MB private on Linux, per panel.
- **The sentinel re-identifies a group immediately before it signals it, and that check is the one part of this feature that can kill a stranger's process if it is wrong.** The sweep runs possibly hours after registration, and operating systems recycle pids, so `kill(-P)` on a bare remembered id is a silent kill of whatever holds P now. Two things stop that (`tools/shell-sentinel.ts`, `sweep`). First, an anchor: the sentinel reads the leader's start time at registration, `/proc/<pid>/stat` field 22 on Linux and `ps -o lstart=` on macOS, and refuses to signal when the live process holding P no longer matches it. The anchor is read by the sentinel and never by the host, which is what keeps the host's `createShellJob` free of a process-table read right after `spawn`. Second, for the case where the leader is already gone, which is the headline case `sleep 600 &` produces within milliseconds, the member anchors taken at the `x` record do the identifying instead. Both rest on the same kernel property: **both kernels refuse to hand out a pid that is currently in use as a process group id**, so while any process still has `pgid == P` no new process can be given pid P, and one identified survivor therefore vouches for the whole group. Refusing to kill whenever the leader is gone would refuse exactly the case panel-close cleanup exists for, so that branch is required, not an optimisation; what it may never do is fire without a matching anchor. Do not replace the anchor with a plain "is pid P alive" check, and do not unregister a group when its call ends: a process backgrounded with `&` has to stay registered or panel close cannot reach it, which is the whole difference this feature exists to remove.
- **The pid-reservation claim is measured on Linux and read-only on macOS, and the difference matters to whoever edits `sweep` next.** On Linux it is `__change_pid()` in `kernel/pid.c`, which walks every pid type and returns without freeing the number if any task still holds it, `PIDTYPE_PGID` included. That was confirmed by running rather than by reading: with `/proc/sys/kernel/ns_last_pid` steering the allocator, a request for a pid in use as a non-empty group's id was refused and skipped, and the identical request succeeded the instant the group emptied. On macOS it is the "find an unused PID" loop in `forkproc()`, `bsd/kern/kern_fork.c`, whose condition includes `pghash_exists_locked(pid)`, so the allocator advances past a pid in use as a pgid. **That macOS reading has never been executed, because no Mac was reachable.** The two platforms are equal on this point, and the only difference left is that macOS anchors are one-second resolution against Linux's clock ticks. **There is deliberately no session-id filter on either platform, and reinstating one would be a regression rather than a hardening.** An earlier design tested `sid === pgid` before signalling a leaderless group, which was worth having only because that branch signalled without any anchor at all. Against member anchors it can only subtract: a backgrounded job that calls `setsid`, which is what every daemonizer does, has `sid !== pgid` while still being a process the sentinel anchored by pid and start time, so the filter would turn correct kills into misses for precisely the long-lived background processes panel-close cleanup exists to reach. The field was never viable on macOS in any case, which is how the question first arose: `ps`'s `sess` keyword reports a kernel pointer rather than an id (`adv_cmds`, `ps/keyword.c`, `KPTR`), and Darwin has no `sid` keyword at all.
- **The sweep never signals a group it has not positively identified, and the member anchor is what makes that possible when the leader is gone.** An earlier design signalled a leaderless group on the strength of its membership alone, which after a pid wrap could kill a stranger's processes; that hole is closed and must not be reopened. The host writes two records now, `r<pgid>` as a command starts and `x<pgid>` when its shell exits, and the `x` is the whole point: **at the instant the shell exits, every process still in the group is ours by construction**, so the sentinel snapshots each one with its own start time. At EOF a group is signalled only if the leader is alive and matches its anchor, or some member anchor is still alive and matches. Otherwise it is skipped. One matching anchor is sufficient because a pid cannot be recycled while a group still holds it, so a single identified survivor proves the whole pgid was never reissued. Do not reintroduce an unanchored branch, do not treat `x` as an unregistration (the group stays tracked, or a deliberately backgrounded process becomes unreachable at panel close), and do not replace the snapshot with a poll: it is one process-table read at one known event, inside the sentinel, never in the extension host and never on a schedule.
- **Known residual, and it fails the safe way. The general condition is "no anchored member is alive at sweep time", which is wider than the race that first suggested it.** Two shapes reach it, and the second is the one you will actually meet. First, a host killed between the shell exiting and the `x` record being written: that group has no member anchors at all. Second, and with no crash involved, a group whose anchored members have since exited leaving processes they forked after the snapshot. The snapshot is one read at one instant, so a double-forking wrapper, the shape `sh -c 'sleep 2; sleep 600 &' &` produces, anchors the wrapper and never sees the process it leaves behind. Measured under WSL rather than reasoned about: with a correct `r` and `x` pair, the late-forked process survived a `kill -9` of the host, `sleeps after: 1`. Note what does not reach it: `sleep 600 &` anchors the sleep itself, and `npm run dev &` anchors npm, which stays alive as the parent, so both clean up. Those processes leak. **That is a miss, not a stranger's death, and the difference is the entire reason the design changed.** A leaked process is the pre-2.23.0 behaviour for one group in a narrow window; a wrong kill is data loss with no warning and no log the user will ever read. Anyone tempted to widen the sweep to catch this case is trading the second failure for the first and must not. Two escapes were examined and rejected on evidence rather than taste: holding an fd on `/proc/<pid>` does not reserve a pid, which the kernel documents explicitly, and `pidfd_send_signal` returns ESRCH once the leader is dead, so it refuses precisely the case that needs covering.
- **The accepted residual is `kill -9` on the sentinel itself.** No userspace process can refuse SIGKILL, so killing the helper loses the cleanup for that panel, and there is no in-process defence against it. Linux could close this with a PID namespace or a systemd transient scope. macOS has neither, and no job objects and no cgroups, so closing it on Linux alone would create a three-way asymmetry, and the PID-namespace form would additionally change what every shell command sees of its own process tree. The user reviewed both options and chose to leave the gap. Do not reopen it, and do not substitute a mutual watchdog: two processes each restarting the other is a new failure mode of its own and still loses to a `kill -9` that names both.
- **koffi is required lazily, behind the win32 check, and its failure is reported rather than swallowed.** It is the project's only native dependency, so `createShellJob` returns on `process.platform !== 'win32'` before the loader is reached and no POSIX path ever requires it. The native binary lives in a per-platform `@koromix/koffi-<platform>-<arch>` optional dependency resolved at run time, which is why koffi is an esbuild external and reaches the VSIX through `scripts/extension-externals.mjs` and the generated `.vscodeignore` (run `npm run sync:vscodeignore`, never hand-edit it). A load failure logs the consequence in user terms and degrades to the bare `taskkill /T` sweep, which cannot reach a severed parent link, and each of the four kernel32 calls that can fail logs which call and which pid. There is no empty catch anywhere in the module: the degradation is announced at the point it is decided, so a user reporting surviving processes has a log line naming the cause.

## Permissions and plan mode

- All tool calls route through the central permission gate (`permission-gate.ts`): read auto-allowed, write/shell → diff approval.
- **A check that cannot decide blocks the call, whatever the tool** (`gateErrorFallback`, used when the gate throws, when no panel owns the session, and when a PreToolUse hook failed for a write or shell call). A read is not exempt, because a deny or ask rule may name the file it reads and an undecided check cannot show that none does. The block is policy-worded and never terminates. A rule list entry that is not a string never reaches the matcher: `readPermissionsFromPath` drops it and logs the file path and index (or that the list is not a list), never the value, which may hold a secret.
- **Settings rules decide before any mode or tool default, deny > ask > allow across every settings file** (`EvaluatorManager.matchRule`). A deny in any file wins, then an ask in any file, then an allow, so a repository's committed allow never overrides the user's own deny or ask, and an ask prompts even when a more specific allow matches. Only `dangerouslySkipPermissions` skips rules. An ask rule prompts wherever Damocles would otherwise run the call unasked: a read-only tool or read-only-annotated MCP tool in any mode, an Edit, Write or GenerateImage in acceptEdits, a read-only shell command in plan mode or for a read-only agent, an in-process module tool (`GATEABLE_MODULE_NAMES`), the plan file, and a subagent whose edits the user accepted. Plan mode's and the read-only agent's blocks still come first. A tool with no prompt of its own gets the generic webview prompt (`ApprovalManager.handleToolPermission`), which registers in `PermissionState` like every other prompt; never answer one with a host modal, which leaves the session reading as working while it waits.
- **The plan-file carve-out resolves the path as the tool does** (`PermissionHandler.isPlanFile`, `resolveToCwd` against the session cwd), in the evaluator and in the gate's plan-mode check alike. `isPlanFilePath` takes the absolute path the tool writes; a relative path would resolve against the process cwd and let a plan-mode write through to a file the evaluator does not see as the plan file. Both the path as written (`spelledPath`: 8.3 names, case and `\\?\` resolved, no link followed) must sit below the plans folder spelled the same way, and the file it resolves to (`canonicalPath`, links and dangling links followed) below the canonical plans folder, with a `.md` name; on win32 the comparison and the extension ignore case. An existing file with more than one hard link is not the plan file either (`nlink > 1`): a hard link in the plans folder shares its content with a name outside it, and no path comparison can see that. A junction, symlink or hard link inside `~/.damocles/plans` therefore never carries the carve-out to a file outside it, and a `~/.damocles` that is itself a link (a dotfiles repository) still works, because each side is compared with the plans folder resolved the same way. It is evaluated after the settings rules, so a deny or ask rule on the plan file wins. In plan mode, `Bash`/`PowerShell` are classified by `readonly-shell.ts` (fail-closed allowlist); non-plan-file `Edit`/`Write` stay blocked (the session plan file is the sole write carve-out); memory/Compass/enabled MCP tools stay available. The same classifier also holds a subagent whose resolved toolset has no write tool (`ResolvedToolset.readOnly` → `readOnlyShell`) in every mode. No write tool must mean no writes via the shell either.
- A block the runtime made itself (settings rule, plan mode, read-only agent, hook) uses `formatPolicyBlockReason`/`POLICY_BLOCK_MARKER`; only a real approval-prompt rejection uses `formatDenyReason`/`FEEDBACK_MARKER`. Never tell the model the user refused something the user was never asked. Both render as "denied"; `FEEDBACK_MARKER` is persisted in old sessions, so its value must not change.
  - The deciding flag is `PermissionResult.policy`, set only by `buildUnaskedDenyResult`, and it covers every deny nobody answered: a settings rule, no webview, no tool use id, an abort before the answer, teardown. The gate and the three tools that call `canUseTool` themselves (AskUserQuestion, BrowserRequestInput, ExitPlanMode) word a `policy` deny with `formatPolicyBlockReason`. A prompt manager knows the user answered only through `userAnswered` on its result, which only its resolve method sets, so any other settle builds an unasked deny. An abort of the call's signal always settles a prompt as that deny, approval and plan prompts alike: pi aborts the signal only when the run stops, and there is no abort that means yes.
- **File rules match the path the tool writes, with Claude Code's gitignore semantics** (`EvaluatorManager.matchFileSpecifier`, shared by Read, Edit, Write, GenerateImage and the searches below; spec: https://code.claude.com/docs/en/permissions.md, "Read and Edit"). `file_path` resolves with the tools' own `resolveToCwd` against the session cwd (`PermissionState.cwd`, which the panel sets from its folder next to `workspacePath`; the home folder when there is no project). `fileRulePattern` (`permission-settings.ts`) splits a rule's path into an anchor and a gitignore pattern: `//path` from the file system root; `~/path` from the home `resolveToCwd` uses; `/path` from the root of the settings file that holds the rule (`FilePermissions.root`: the project folder for the four project files, the file's own directory for a home file, as Claude Code resolves `/path` in `~/.claude/settings.json` to `~/.claude/path`); anything else, with a leading `./` dropped, from the cwd. An anchored pattern keeps its leading `/`, so `~/.zshrc` is home's own `.zshrc` and `//**/.env` is needed to reach any depth. A drive-letter path (`C:/x/**`, `C:\x\**`) is a Damocles extension, read as `//c/x/**` with `\` as a separator; everywhere else `\` is gitignore's escape (`\[2024-06\] Reports/**` matches the literal folder). Matching is node-ignore (`ignore`, the gitignore library pi uses) on paths in POSIX form (`C:\Users` as `/c/Users`, a UNC path as `//server/share`), each made relative to the rule's anchor first, so a rule never matches above its anchor and node-ignore never sees a path it would reject (a `\\?\` or `\\.\` device path is not under `//`; the spelled and canonical forms below give its drive form). Depth: a bare name (`.env`, `*.env`) matches at any depth under its anchor and never in a parent folder; a relative pattern with exactly one folder before its last segment (`src/**`, `secrets/**`, `src/*.ts`, after dropping `./`) matches only at `<cwd>/src` as an allow rule and as `**/src/**` (any depth under the cwd) as a deny or ask rule; every other shape (`/src/**`, `src/components/**`, `**/src/**`, `build/`) matches the same in every rule type. A path node-ignore compiles into no rule that can match (`usableGitignorePattern`: blank, a `#` comment, a lone trailing `\`, a bracket that never closes or names an unknown class, ported from node-ignore's `index.js` and kept in step with it) still guards that exact anchored path as a deny or ask rule (on Windows read as a path, `\` as a separator, so `Read(vaultdir\)` guards the folder `vaultdir`); as an allow rule it approves nothing. Negation: a deny or ask rule whose path starts with `!` matches nothing itself and carves its paths out of the relative (`path`, `./path`) rules for the same tool listed before it in the same list of the same settings file (gitignore order, so a first-listed `!` carves nothing); the `!` pattern is always cwd-relative, even as `!/x`, `!~/x` or `!//x`, so it never reaches an anchored rule, and gitignore's parent rule holds (`Read(secrets/**)` then `Read(!secrets/public/**)` still blocks `secrets/public`). Carve-outs never cross settings files. An allow rule cannot be a carve-out. An allow rule needs the requested path inside the cwd and the canonical path inside the canonical cwd, both matching the rule, so `..`, another drive, `~` or an absolute path outside the cwd never earns an allow, an anchored allow rule included. The requested path's cwd-relative form is taken between `spelledPath` of both, which resolves 8.3 names, case, `\\?\` prefixes and loopback admin shares segment by segment and stops at the first link, so `<8.3 cwd>\src\a.ts` earns `Edit(src/**)` while a path through a link keeps the link's name. Deny and ask rules match the requested, spelled and canonical forms, each relative to the anchor as written, spelled and canonical, so no path form escapes them. On win32 the match ignores case (macOS and Linux match case), and an NTFS stream suffix (`name::$DATA`, `dir::$INDEX_ALLOCATION`) is cut off for deny and ask and bars an allow. Every file rule also checks the canonical path (`core/canonical-path.ts`): `realpathSync.native` of the deepest existing ancestor plus the segments below it, so a symlink, junction or 8.3 short name resolves even for a file not yet created, and a UNC path to a drive's admin share on this machine (`\\localhost\C$`, `\\127.0.0.1\C$`, `\\::1\C$`, `\\0--1.ipv6-literal.net\C$`, the host name, any interface address, and their `\\?\UNC\` and `\\.\UNC\` forms) becomes the drive path first, since realpath returns it unchanged. A dangling link is followed to its target (up to 40 hops), because writing through one creates that target, and a segment realpath cannot resolve (missing, unreadable, looping) ends the walk instead of throwing, which would block the call through `gateErrorFallback` instead of applying the rules. The cwd is canonicalized the same way.
- **`Edit` rules cover every tool that edits files, and `Read` deny and ask rules cover Grep, Glob and Ls** (`EDIT_RULE_TOOLS`, `SEARCH_TOOLS` in `evaluator-manager.ts`), as Claude Code applies them. An `Edit` rule, bare or with a path, also matches Write and GenerateImage; a Write or GenerateImage rule still matches only its own tool. A `Read` deny or ask rule (allow never) matches a search through its search root as a file, the root's contents (`<root>/` against the glob, so `secrets/**` covers a search of `secrets` or anything below it) and the root joined with Grep's `glob` or Glob's `pattern`, so `find secret.txt` or `grep --glob secret.txt` is blocked or asks. A search rooted above a covered path is decided by the root and runs; Grep and Glob then leave every file a `Read` deny or ask rule covers out of their results (`PermissionHandler.readRuleFilter`, passed into `createGrepTool`/`createFindTool`) and append a notice saying so. Asking there would fire for every search of a project with a `Read(.env)` rule, since a bare name matches at any depth, and an ask nobody can weigh turns into reflex approval; leaving the files out keeps their content from the model without stopping ordinary searches. Ls is pi's tool and lists names only, so a covered folder's name still shows above it. A file an ask rule covers is left out rather than prompted for, because a search cannot prompt per file; reading it with `Read` prompts. A rule's literal leading folders are resolved too (spelled and canonical), and the rest of the pattern also matches from there, so a `//`, `~/` or `/` rule written through a linked folder also covers its target, Claude Code's `/etc` → `/private/etc` case; on Windows a `//` rule's folders resolve only from a drive (`//c/...`), since `//tmp` is `/tmp`, not `C:\tmp`. A relative deny or ask rule's folders resolve only to a place inside the cwd, so an 8.3 name in the rule covers the long spelling while a link out of the cwd adds nothing. A `Read` deny rule with a path (not ask, not allow) also blocks Edit, Write and GenerateImage on the paths it covers, including creating a file there. acceptEdits does not auto-approve an Edit, Write or GenerateImage whose path is inside the cwd as written but resolves outside it through a link or junction (`EvaluatorManager.linksOutOfCwd`, Claude Code's "Writes through a symlink"); it asks instead. A `Read` rule matches the file pi will open: pi's `resolveReadPath` (`dist/core/tools/path-utils.js`, used by `read.js` through `resolveReadPathAsync`) falls back to a narrow no-break space before AM/PM, NFD, a curly apostrophe and NFD with a curly apostrophe when the requested file is missing, and the package does not export it (its `exports` map has no `core/tools` entry), so `evaluator-manager.ts` ports it and the two must be kept in step. macOS case is not folded.
- **Settings rules apply to MCP tools.** Deny and ask rules are evaluated before MCP's default allow, and an MCP tool no rule names still auto-allows. An ask rule prompts even for a read-only-annotated tool, because the annotation is the server's own claim. Claude Code's three forms match against the call's MCP descriptor, never the pi name: the gate looks up the server's config name and the server's own tool name (`GatePermissionContext.mcpToolIdentity`, from the live descriptors for a panel and from the frozen `NestedMcpToolset.identity` for a nested agent) and passes them as `CanUseToolContext.mcpTool`. `mcp__server` and `mcp__server__*` match when the server part equals the config name as written or as Claude Code writes it (`[^A-Za-z0-9_-]` as `_`), and `mcp__server__tool` does the same for both parts at every `__` split. The pi name is sanitized, cut to 64 characters and hashed, so matching on it let `mcp__srv` cover `srv_` or `srv-`, `mcp__a` cover `a__b`, `mcp__my-srv` cover `my.srv`, and two server names sharing their first 50 characters share rules. A rule equal to the pi name also matches, because the renamed-tool migration writes rules that way; pi names are unique within a session, hashed or not. A call with no descriptor matches only that exact-name form. An `mcp__` rule with parentheses is skipped, as Claude Code skips it. Tool-name wildcards (`*` matches any run of characters) follow Claude Code's "Tool name wildcards": a deny or ask rule's tool name may be a glob of the full name (`*` matches every tool, `mcp__*` every MCP tool, `Bas*` Bash), with the server and tool parts of an `mcp__` glob matched against the descriptor's names as above. An allow rule may glob only after a literal `mcp__<server>__` (`mcp__puppeteer__*`, `mcp__github__get_*`); `readPermissionsFromPath` drops any other allow glob (`*`, `B*`, `mcp__*`, `mcp__git*__x`), an allow rule starting with `!`, an allow rule whose path is not a usable gitignore pattern, and an allow `Write(path)` rule (Claude Code consults only `Edit(path)` and `Read(path)`; a deny or ask `Write(path)` is still matched, because dropping it would fail open), logging the file path and index, never the value.
- **`terminate` is per-batch, not per-call, and it is emitted only for an unexplained "no".** pi ends the turn only when every finalized result in the batch is terminating and the batch is non-empty. `executeToolCalls` dispatches to a sequential or a parallel batch runner, and both take the flag from `shouldTerminateToolBatch`, which requires `finalizedCalls.length > 0 && finalizedCalls.every((finalized) => finalized.result.terminate === true)`, consumed by the agent loop as `hasMoreToolCalls = !executedToolBatch.terminate` (`@earendil-works/pi-agent-core@^0.99.2`, shipped at `node_modules/@earendil-works/pi-agent-core/dist/agent-loop.js:465-467` and `:167`; the line numbers are only meaningful against that installed version, so re-read the file before trusting them). So denying one of three parallel calls does not stop the agent: the other two ran and produced results the model must see. That is correct, not a bug. Do not "fix" it by terminating harder. Damocles sets it in exactly two places: the interactive `canUseTool` deny, conditional on `PermissionResult.interrupt`, and a `tool_call` hook that explicitly opted in with `"terminate": true` alongside its deny (read strictly as the JSON boolean `true`; a string or number is ignored). `interrupt` is set by exactly two functions, `buildUserDenyResult` and `buildUserFileEditDenyResult` (`src/core/permission-handler/utils.ts`), and only when the user actually answered the prompt (`ApprovalResult.userAnswered`) and left the feedback box empty. A deny with feedback is *instruction* the model must act on, so it must not end the turn. Every deny the user was never asked about is built by `buildUnaskedDenyResult`, which cannot set it. Grepping `interrupt` under `src/core/permission-handler/` is therefore a complete enumeration of the terminating sites. Keep it that way. Everywhere else stays non-terminating on purpose: the gate's own error fallback (a Damocles bug must not kill the user's turn), settings-rule denials (policy, not a user decision), and above all the plan-mode / read-only-agent blocks, whose entire reason for existing is to make the model self-correct. Terminating there breaks plan mode.
- The on-disk plan file is the single source of truth for plan-mode handoff. `ExitPlanMode` takes no `plan` argument; everything reads it via `ChatSession.getPlanContent()`.
- A `damocles.*` setting whose workspace value grants a capability or relaxes a guard must be listed in `capabilities.untrustedWorkspaces.restrictedConfigurations` in `package.json`. Every setting that declares no `scope` defaults to `window`, so a repository sets it from its own `.vscode/settings.json` and `config.get` returns that value in a workspace the user never trusted. Listing it makes VS Code serve the user value instead until trust is granted, with no code change at the read site. The bar is a capability grant, not a preference: a budget, a model choice or a display toggle does not qualify, and an over-broad list breaks legitimate per-workspace configuration for trusted users. The exception is `damocles.imageGeneration.model`, which decides what each image costs on the user's OpenRouter key and is user-only like `damocles.imageGeneration.enabled`. Known pending case: `damocles.sandbox`'s `autoAllowBashIfSandboxed`, `allowUnsandboxedCommands`, `networkAllowedDomains` and `networkAllowLocalBinding` are declared in the manifest with no reader anywhere in `src/`, so today they grant nothing and are deliberately absent from the list. Whoever gives one of them a reader adds `damocles.sandbox` to the list in the same change.
- Compass is off in an untrusted workspace, and the gate is `isCompassEnabled(platform, folderPath)` (`compass/index.ts`), never a call site. That one function is what tool eligibility (`moduleToolNames`), the system prompt section, the webview handlers, the sidebar views and `ensureInitialized` all read (the views directly, the rest through the `CompassService.isEnabled` getter that returns it), so trust belongs in that function and the rest follows with no other edit. The reason is what Compass does with a repository: it walks the entire tree, parses every source file into `~/.damocles/compass/<hash>/graph.db`, returns raw source lines to the model through `compass_review_context(include_source)`, and runs git inside the workspace. `damocles.compass.enabled` sitting in `restrictedConfigurations` only stops a repository turning Compass on for itself and does nothing about a user who enabled it globally, which is everyone who uses Compass. Prevent the work, do not filter its output: untrusted means no worker, no walk and no watcher. Trust is granted and never revoked in place, so the service listens on `TrustService.onDidGrantTrust`, filtered to its own folder, and starts then with no window reload, if something already asked it to start, and there is no reachable state in which an index built while untrusted keeps serving.
- Every git call in `compass/git.ts` passes `-c core.fsmonitor=false`, an argv rather than a shell command string, and no `ExecEnv`. Git reads the repository's own `.git/config` first and runs `core.fsmonitor` as a command while refreshing the index, so `git diff` in a hostile clone is arbitrary code execution; `compass/__tests__/git.integration.test.ts` verifies against real git that the hook fires without the override and not with it. An `ExecEnv` from the checkpoint engine would retarget git at its private bare repo and answer about the wrong repository. This is the same finding as the one fixed in `mcp-local-gitignore.ts`, so treat any new git caller as needing both.
- Plan-mode guidance has one source: `pi-session/plan-mode-guidance.ts` (`buildPlanModeGuidance`), consumed by both `agent-start.ts` and `tools/plan-mode-tools.ts`. Edit the builder, not the call sites.
- The Damocles system prompt has one assembler: `agent-start.ts` (`assembleDamoclesSystemPrompt`). Never read `session.systemPrompt` for display. It holds pi's boilerplate outside a turn.

## Browser

- Browser tools resolve tabs through the caller's `BrowserAgentScope`, never a global active page. A chat's main agent and its human share that chat's human scope (`BrowserService.chatScope`): on VS Code every chat gets the one `PRIMARY_SCOPE_ID`, and with `WindowService.chatBrowserPane` (desktop) each chat panel gets its own, registered for the chat's lifetime and kept across a browser teardown as the primary one is. Every subagent/team agent passes its own id, created with the chat its session runs in, and its scope is disposed at settle (tabs closed only on success). A human scope is never disposed by an agent and is the only kind that reveals a page it opens or navigates.
- Every page records the chat panel that owns it (`PageEntry.chat`), separately from its scope, because a failed subagent's kept tab outlives its scope: an explicit open takes the scope's chat, a popup takes its opener's chat (and the opener's scope while it lives, else that chat's human scope), and a racing `context.on('page')` registration reads the explicit owner first. Core passes it as `PanelOptions.owner`; VS Code ignores it. With a chat browser pane a page whose owner is unknown or already closed is closed at registration, never re-attributed to whichever chat launched Chromium, and a chat panel's dispose closes every page it owns. The human's paths resolve the requesting chat on desktop and the primary scope on VS Code: the chat toolbar's open (`openForChat`), the pane's New page and the page's own New Tab (the page's chat), a pick requested from a chat (that chat's page) and a pick from a page's toolbar (posted to the page's chat, else the active chat). A chat browser pane draws the page's navigation chrome, so core omits the page's in-page toolbar there and posts `navigationState` (loading, back and forward, from `Page.getNavigationHistory`) for the host to read; the VS Code page HTML is unchanged.
- Anything a page produces is hostile input on the extension host. Console/network/picker output is redacted and bounded at capture (`redaction.ts` + `collectors.ts`), never at a render site. The guarantee must not depend on whoever adds the next reader. The in-page bridge's caps live in the page's own world and are the page's to edit, so every bound is re-enforced host-side in `installContextObservers`/`onConsoleBinding`. Every redaction pattern must be linear-time (unrolled-loop form, bounded affixes): it runs synchronously on the host, so a backtracking pattern is a remote editor freeze.
- `ScreencastHealth`'s stall clock is armed by intent (`noteWanted`, on panel visibility), not by the CDP `start()` call. The webview's `ready` message is the sole trigger for `start()`, so anchoring on it makes the watchdog blind to a lost handshake.
- `damocles.browser.devToolsPort` (default off) opens an unauthenticated loopback CDP endpoint on the logged-in profile when enabled; it is a launch-time flag, so a change needs a relaunch.
- Chromium's sandbox is always on (`chromiumSandbox: true` in `launcher.ts`); never pass `--no-sandbox`, whatever environment fails to launch. Pages render in the user's logged-in profile. Chromium refuses to run as root with the sandbox on, so `launchBrowserContext` refuses a POSIX root process before launching, and maps Chromium's "Running as root without --no-sandbox" and "No usable sandbox" launch errors to localized messages that say how to fix the environment.

## Teams and subagents

- Team message delivery branches on `TeamMessage.kind`, never on rendered text (a peer can mimic any prefix). `scratchpad-notice` reaches only a `standby` specialist; `ledger-notice` reaches no inbox at all (the ledger is a pull surface). Both still broadcast, so persistence/timeline/`getInbox` see every write. Filter at delivery, never at emission.
- The verification fingerprint is computed by the extension, never supplied by an agent (`team_record_verification` has no `fingerprint` param, asserted by test). It must fail visibly: `unverifiable`, never a hash that silently missed files. `git status` needs `-uall -z` and paths resolved against `--show-toplevel`. Without all three it goes blind to real edits (collapsed untracked dirs, C-quoted paths, subdirectory workspaces) and a stale pass looks reusable forever. `team_read_scratchpad` adds `currentFingerprint` to every read that returns the `verification` section, the unchanged marker included, because the tree can change while the ledger does not. It is the only way an agent that cannot record a run (a read-only reviewer) or did not record the latest one tells which entries cover the current tree.
- The team profile catalog is generated, never hand-edited: change `agent-profiles/`, run `npm run generate:profiles`, commit the output (a pinned test locks the exact set). Its mirror policy (`TRACKED_DIVISIONS`, `EXCLUDE`, `DIVISION_ALLOWLIST`) is duplicated in `~/.claude/scripts/sync-claude-agents.mjs`, which governs `~/.claude/agents`. Separate repos, no shared state, so edit both together. Both scripts and the generator fail closed (flattened-path collision, duplicate profile id): a profile must never go missing silently.
- Each nested spawn path collapses to one `buildAgentToolset` call (`agent-manager.ts`, and both `team-runner.ts` spawn sites), made inside the per-spawn path for the same reason `buildExtensionFactory` is invoked per spawn: it must read live panel state at spawn. Hoisting it to a construction-time local would freeze the snapshot at team-construction time and silently miss a server the user enabled mid-run. `mcp.names` must reach `tools:`, `customTools` and `mcpToolNames:` from that one call. And `tools:` must never be narrowed to the deferred baseline, which evicts the tools permanently while ToolSearch still reports success.
- The read-only-agent rule is a shell-escape guard, not a general capability ceiling. `toolCategory('mcp__*')` is `'other'`, so the read-only branch does not catch MCP: a read-only subagent (Explore/Plan, or any agent with no write tool) can invoke a non-annotated MCP tool, and in `default`/`acceptEdits` it still routes through `canUseTool` and prompts. That is a decision, not an oversight. Filtering it would make nested agents stricter than the panel and stricter than plan mode, and most servers omit `readOnlyHint` entirely so it would fail closed against the common case. The trust boundary for MCP is the server enablement list, not the agent type. Do not "fix" it in either direction without changing this line. A team specialist spawned with `kind: 'reviewer'` gets the same posture: `buildTeamEngine().buildAgentToolset` drops every write-category name, `teamAgentPiToolNames` withholds `team_record_verification` (a read-only shell has no run to record, so an entry from it would vouch for nothing; both the names and the definitions read that one function), and the toolset returns `readOnly` computed from the names it resolved (as `resolveAgentToolset` does), and the runner hands that flag to the same spawn's `buildExtensionFactory` as `readOnlyShell`. Never pass `kind` to the gate directly, so no path can pair a write tool with an open shell. `kind` is persisted on `agent-spawned`, so a resumed reviewer keeps the posture, and a redispatch re-declares it.
- A subagent's model is configuration, never the spawning model's choice: the `Agent` tool deliberately has no `model` param. `resolveSubagentModel(agentConfig)` takes only a config. Template `model:` > Explore settings (Explore only) > the panel's session model. An unresolvable/unauthed/out-of-scope template `model:` fails the spawn naming the template; never fall back to the session model, which leaves a broken pin working-but-wrong forever.
- **Every background outcome reaches the parent once per branch** (`undelivered-results.ts`, `deliveredBackgroundResults` in `agent-records.ts`). Each background invocation's outcome reaches the model exactly once on a branch, as a delivered result or as an interruption-notice entry. The parent branch and the agent files are the source of truth; the `AgentManager` map is only a cache of the bound session's agents. D(branch), the delivered set, is the `toolCallId`s in every `damocles-subagent-results` entry's `details.agents[]` plus those in every `GetSubagentResult` fetch marker (`SubagentResultFetchDetails` in that result's `details`). Three paths deliver, and each records the invocation's `toolCallId`: the keep-alive injection at turn settle and the prompt-start delivery are pushes, and both deliver only `AgentManager.deliverableLive()` (plus, at prompt start, the file results), which drops what is already in D; a `GetSubagentResult` fetch is a pull, so it always answers and records the marker. D is the only record of delivery: nothing on a record is set when its result reaches the model, because the keep-alive's draft and a fetch marker are delivered only once pi commits them. pi commits each settle's draft before the next settle runs, so the keep-alive sees its own earlier injection in D. The prompt-start delivery reads D again with no await before its append, so two prompts racing past the early check append one message. It appends only to an idle session: while a run streams, pi defers a custom message sent with `triggerTurn: false` to that run's settle (`sendCustomMessage` pushes it onto `_pendingCustomMessages`, flushed in `_runBeforeSettleBoundary` after the handlers' drafts are committed, `agent-session.js` in pi 0.99.2), so D would miss it when that settle's keep-alive reads D and the same records would be injected twice. A streaming session therefore gets no prompt-start delivery and no notice: the records stay with the run's keep-alive, and both flags stay set. The prompt-start delivery appends one hidden results message before the interruption notice and before `beginTurn`, so a rewind cannot split an invocation from its delivery. Both run only for a prompt that will commit a user message: a prompt the budget refuses and a pi extension command (`/todos`) get neither. The live records are delivered even when the file scan fails, and the notice runs only after a delivery that appended or had nothing to append, so a card-stopped agent is never both announced as resumable and delivered later. A live record is deliverable when it is background, terminal, not `discarded`, ran the agent's latest invocation on the branch and is not in D. A record whose own invocation entry failed to append still counts as the latest while its `Agent` call is on the branch, because any later invocation of that id would have replaced it in the manager. Only `abortAll`/`dispose` set `discarded`, so an agent stopped from its card (`abort()`) is delivered with its partial output and resume note. A resume switch first retires the bound session's agents the way a panel close does (`retireAgents`: `abortAll('shutdown')`, the team cancelled as a user stop so it stays resumable, the turn stopped, the subagent and team runs awaited up to `ABORTED_AGENTS_SETTLE_TIMEOUT_MS`, then `clear()`), so the session switched to never sees them and a draining team never streams into its panel, and the first session's next bind finds each one in its file, resumable or deliverable by the scan. While it retires them, `stopRequested()` is true, so a turn held in `agent_before_settle` commits neither a keep-alive nor a plan-mode nudge to the session being retired; `clear()` writes each stopped record's status to its agent file at once, as `dispose` does, so a run that outlives the wait cannot record its status after the conversation was re-bound and scanned, and a run that ends after `clear()` posts nothing to the panel. The timeout caps only the agent runs: the turn's own `abort()` is awaited in full, as pi's `switchSession` awaits it again in `teardownCurrent`. Both flags are set before `switchSession`, because pi opens the target file before tearing the bound session down, so a switch that throws on an unreadable file leaves the old session bound with its agents already retired. An agent the manager does not hold is deliverable from its file when its latest invocation's `Agent` result was `async_launched`, that invocation is not in D, and its segment status is `completed`, `steered`, `aborted` or `error`. `stopped` is excluded because a file cannot tell a card stop from an abort kill (the notice announces user and shutdown stops, and budget and reset stops are discarded by design), and so is an invocation with no recorded status. The live check runs at every prompt start with no flag, which covers ESC, a budget stop and a team cancel without file IO. The file scan runs once after a stored session is bound (a resume at start, a fork, a resume switch) through `undeliveredScanPending`, which clears only after a scan that read every candidate (`collectUndeliveredFromFiles` reports `incomplete` when a candidate's file fails to read, or has no indexed file while `indexAgentFiles` reported a file it could not read), so an IO failure such as a Windows `EBUSY` is retried at the next prompt. Never scan files on every prompt: abort-killed agents never enter D, so their files would be re-read forever. The interruption notice skips an agent whose latest invocation is in D, because a delivered result already carries its status note and resume call, and an agent whose file could not be read or might be an unindexed one, because from the branch alone a finished agent reads as interrupted and the retried scan would then deliver it too. `GetSubagentResult` and `SteerSubagent` answer from a live record only when it ran this branch's latest invocation of that id (`AgentManager.branchRecord`), and otherwise through `AgentManager.readBranchAgent`, which resolves only a well-formed id that this branch invoked, never an arbitrary file in the folder. A finished agent's fetched result is its file's status entry, else what the branch holds (its results injection or its foreground `Agent` result), else its status note. Verbose `GetSubagentResult` formats the agent file's messages, because a finished record no longer holds its session.

- **`team_standby` and `team_report_complete` end the turn from the engine, not from the model.** Both used to set a flag and return, leaving the model free to carry on, and it did: 771 of 826 recorded standby calls were followed by more work. The stop is a `finishTurn` decider registered through `installTurnDecider`, which defers to the hook pi already installed, keyed on the tool *result* rather than the call because both tools throw for the wrong role and the agent needs that turn to read the error. It holds no opinion while `session.agent.peekQueuedMessages()` is non-empty. Never `session.pendingMessageCount`: that counts the `_steeringMessages`/`_followUpMessages` mirror, which `sendCustomMessage` bypasses by steering the agent directly (`agent-session.js:1738` in pi 0.99.2), so a queued follow-up reads as zero there and the decider ends a turn pi was about to feed. Nothing is lost when it does, because `_runBeforeSettleBoundary` continues on `hasQueuedMessages()` anyway; the cost is an extra continuation request and a one-turn delay. Do not make the tool block instead: the team state machine runs only after `session.prompt` resolves and pi has no tool timeout, so a block hangs silently until abort. Do not abort either, which marks the agent failed.

- **Scratchpad read state is per session and must be cleared when a session is replaced.** The unchanged marker withholds a section on the premise that its text is already in the reader's context. `redispatchSpecialist` gives an agent a brand new session under the same name, so `Scratchpad.clearReader(name)` runs alongside the other per-attempt resets. Without it the re-run's first read answers "unchanged since you last read it" for text it has never seen, and because the marker holds until a peer writes a new version, `mission-brief` (which has no other writer) is withheld for the rest of the run. Appending is not reading, so `appendTo` records nothing: `team_record_verification` echoes only the last 25 of up to 200 ledger entries.

- **A reviewer's sign-off covers one landed revision of each implementor it reviews** (`review-coverage.ts`, whose `ReviewCoverage` is the one owner of the pairs, stamps, sign-offs, dismissals and owed re-reviews). A `kind: 'reviewer'` spawn must declare `reviews`, the implementors it reviews (`[]` for a reviewer of nobody). An implementor may not declare any, a reviewed name may not be a reviewer, and a reviewer reviews no reviewer. A redispatch that omits `reviews` keeps the previous pairs, so every `agent-spawned` entry records the effective list, `[]` included: a resume reads the pairs only from each member's latest spawn. A reviewer whose log has no `reviews` (spawned before pairs existed) has none to keep, so its redispatch must pass `reviews`. A resume reads the pairs from an untrusted log, so it checks each spawn's `reviews` with the spawn rules against every member's kind, and each name in the checkpoint's coverage against the roster and each dismissal's `why` as one line, and refuses the resume on a failure, before any coverage rule reads them. A redispatch may not drop a pair whose review of landed work is unsatisfied: the refusal names `team_dismiss_review`, the recorded bypass, and is checked before anything changes. An implementor's work lands at a stamp `{ attempt, round }`, `round` being its revision-round count, on four paths: `reportComplete`, `convertStrandedStandby`, `convertOwedTerminalToReview`, and a run that settles `completed` unapproved, which only the revision cap produces. That last check reads the raw run status, because an approved or synthesis-released run settles `cancelled` and synthesis clears the round counts. A re-land in the same round keeps the stamp. A checkpoint without `review.coverage` lands every implementor that is `confirmedComplete` or `completed` at its `{ attempt, rounds }` on restore, so settled work always has a stamp. A reviewer with pairs reports only after reading the current version of every section its implementors authored (`checkReviewerReportGate`), and it passes one verdict per implementor, `approve` or `changes_requested`, recorded against each implementor's stamp at that moment (null if it had not landed). An implementor with no landed stamp has nothing to judge, so its verdict may be left out; its first landing then re-requests every live reviewer that reported without one, as it does a stale sign-off. A sign-off is current while its stamp equals the landed one, and a review is satisfied by a current `approve` or by a dismissal bound to the current stamp. Rule A: a landing that changes the stamp invalidates every older sign-off of it, and each reviewer whose run is still subscribed gets a direct `[RE-REVIEW REQUESTED]` message. A run holds its note sink exactly as long as its bus subscription, so that is the test: a run in the gap between its loop ending and its promise settling gets nothing and owes nothing, and a settling run's owed re-review is cleared. Its state changes first: it leaves `confirmedComplete` and turns `running` before the send, so no review-round notice counts it settled. Invalidation happens at landing, never at the revision request, so no reviewer is woken to review half-done work. An owed re-review may report past `MAX_SPECIALIST_REVIEW_ROUNDS`, because it is not a lead revision round. A reviewer's report in its last revision round is refused like an implementor's, but only after its read gate and verdicts pass and its verdicts are recorded, since a reviewer's work is its verdicts as an implementor's is its landing. So the `team_request_revision` that sends a stale reviewer back clears the block in any round, and the cap still ends the run. Only a report discharges it, and a cancel or redispatch of the reviewer clears it. At the cap a bare end earns one nudge and never a conversion to awaiting-review, since keepAlive holds a converted run only below the cap. Rule B: an implementor is approved only when every reviewer's review is satisfied, and a current `approve` satisfies it only while the reviewer has read every section the implementor authored at its current version (the report gate's staleness), because an implementor woken by a peer can change them without landing. That reads as stale, names `team_request_revision` on the reviewer, and wakes nobody. Rule C: a reviewer is approved only once every implementor it reviews is final (`isSpecialistFinal`: completed, cancelled or failed) and each completed one is satisfied. Rules B and C and the `[REVIEW ROUND READY]` coverage lines all come from one decision per pair (`ReviewCoverage.decisions`), so a line says "approval blocked" exactly when approval throws. Every rejection names the moves that clear it and never a tool that would throw: a completed reviewer cannot be redispatched, so its one move is a dismissal; a never-spawned implementor is spawned or cancelled; a reviewer still re-reviewing is waited for. `team_dismiss_review` needs a reason of at least 10 characters and is allowed only for a final reviewer that is not current or for a current `changes_requested`; a live reviewer with a stale sign-off must re-review instead. A dismissal records why the review was unsatisfied when the lead dismissed it, and `synthesizeResult` puts every dismissal at the top of the result, above a list of any review still unsatisfied on a path that bypassed the synthesis gate. The gate and that list cover every implementor with a landed stamp that is not cancelled or failed, standby included, because synthesis releases a standby member as completed. The block quotes the lead's reason as JSON, and a roster name must be one line with no control or format characters (Unicode Cc and Cf, checked before the event log is written), so no text it holds can add a line or reorder one. Implementor to implementor cross-review stays prose and advisory: only a reviewer's verdict gates. A log with no `reviews` declares no pairs, so no rule applies.

- **A team agent's work fields are per attempt; its usage fields are cumulative.** Status, last tool, active time (a stopwatch derived from entry timestamps, next entry), tool count, result and effort describe the attempt running now. A `resume_team` continues the attempt, so its tool count carries on; a redispatch starts a new attempt at zero. Tokens and cost sum across every attempt, because a cancelled attempt's spend was still spent. Three places must agree or a reopened team contradicts the live one: the runner (`carriedUsage` plus the running attempt's usage, and `carriedToolCallCount`, restored from the checkpoint, plus the tool calls since the resume), the loader (each `agent-completed` entry holds its own run's usage, so it sums those, and takes the work fields from the last, including `toolCallCount`, which is the attempt's running total), and the webview store (which resets the work fields when the `attempt` counter advances). `attempt` is 0-based; a log written before it existed has no field and its spawns are the first attempt. Never write cumulative usage into `agent-completed`, or the loader double counts; never write a per-run tool count there, or a resumed member's count restarts. A team card's per-run totals are a separate figure: `TeamRunLog` (`runs.ts`) takes them from the `run` field of `team-completed` or `team-cancelled`, and otherwise derives them from the `agent-completed` entries of that run. A run's usage has the same counters as an agent's (`TeamRunSummary.usage`: each token kind and the cost), so the card's tokens and cache rate use the definitions `AgentUsageStats` uses on the agent cards and overlays, and the runner, `TeamRunLog` and the store each derive all of them. A log written before those counters recorded `run.tokens`, input plus output only; it is read into `legacyTokens` and never into the token kinds, so such a card shows that figure and no cache rate.

- **A team agent's active time is a stopwatch derived from entry timestamps** (`src/shared/team-stopwatch.ts`: `activeMs`, the attempt's closed segments, and `runningSince`, the open segment's start or null). A segment opens at the member's `agent-spawned` entry, which starts a new attempt at zero, or at its `agent-resumed` entry, which continues the attempt, park mode included: time spent awaiting review or in standby counts, because the stopwatch runs from a launch or resume until the run settles. It closes at the member's `agent-completed` or the run's `team-completed`, and closing a closed segment does nothing, so a member that settles after `team-completed` keeps the figure that entry fixed. A runner that has written `team-completed` appends no further entry and sends no further webview message (`appendEntry` and its gated `onMessage`), since a resumed runner may own the log and the cards by the time a member it gave up on settles. A run cut short by a reload closes its open segments at the entry before the next `team-created` or `team-resumed`, or at the log's last entry, matching the run cut-short rule. The time a team spends stopped between runs therefore never counts. `TeamRunLog` (`runs.ts`, `memberActiveMs`) is the one derivation: the loader reads it and `parseTeamEventLog` hands it to the runner's restore as `TeamEventLog.activeMs`. It keys each member by agentId: `agent-spawned` starts a new attempt, `agent-resumed` opens a segment only for that attempt and only while none is open, and `agent-completed` closes one only when its `toolUseId` (the runner stamps its run's on every one) names the open run; an entry without the field, from a log written before it, closes as before. The live runner stamps one `Date` into each opening or closing entry and into the stopwatch, so a live card and a reloaded card agree to the millisecond; it sends the stopwatch on the spawn update and on every settle update, a run that throws included, and in `getTeamState`, and `getTeamStatus` reports it. The team's finalize also sends one, before `teamCompleted`, for every member it forced terminal after the drain timeout or whose open segment it closed at `team-completed`, because a member that settles after that entry sends nothing. It builds those updates right after the `team-completed` append, before its await, where a late settle could still change a member. A member forced terminal there has no `agent-completed`, so the loader applies `team-completed.agentResults[].status` to every member still active. A run that throws before its settle handler wrote `agent-completed` writes one from the throw path, `failed`, with the same `Date` as its stopwatch; a throw after that entry keeps the status it recorded (a per-launch flag), so a run never has two. The webview store applies only that stopwatch, after the attempt reset, and never stamps an agent time from its own clock; a member's card and overlay tick while `runningSince` is set, never by status, since an approved member's run counts until it settles. The team overlay sums its runs (`runsStopwatch`: each ended run's duration plus the live run's open span), so the gap between runs is excluded there too. `agent-completed` carries no `durationMs`.

- **Every effort badge shows the effective level pi ran at, never the requested setting** (`src/shared/effort-badge.ts`). The value is the session's `thinkingLevel`, which pi returns after clamping the requested level to the model (`_clampThinkingLevel`), so a subagent requested at Max on a model whose top level is High shows High, and Damocles' `ultracode`, which reaches pi as `max`, shows Max. It is published only when the model reasons (pi's `Model.reasoning`); a non-reasoning model shows no badge rather than "Off". A chat reply carries the level pi stamped on its `AssistantMessage.thinkingLevel`, on the existing `assistant` and `assistantReplay` shapes: live the rule reads the session's model, on reload the registry entry for the message's provider and model id. Which reply shows a badge is derived at render time (`useVirtualizedMessages.ts`: the first reply after each user message, and any later reply in the turn whose level differs from the last one shown), so nothing about placement is stored. A subagent's effort is stored per run: `onSessionCreated` reads it from the new session and writes it on the launch record of a fresh run or the segment record of a resume, because a resume can reopen at a different level; the reload gives a spawn card the launch's value and a resume card only its own segment's, so a resume that recorded none shows none, as its live card did. An `effort` this build does not know (a newer build's level, in a shared `~/.damocles`) is dropped on read, never a reason to reject the launch or segment entry. The bridge sends it in `subagentModelUpdate` once the session exists, with no model when the launch recorded no label, and its once-guard keys on the (model, effort) pair, so the spawn-time model message does not swallow it. A replay reads `Model.reasoning` from `PiRuntime.modelRuntimeReady()`, which waits only for init to build the model registry, not for its credential sync. The replay reaches the runtime through `PiRuntime.unlessRetired()`: a panel restored at startup replays before its session creates the runtime, so the replay may create it, but once `disposeInstance` retired it at shutdown nothing creates one, because a late replay's runtime would start watchers nothing disposes. A team agent's `effort` is a per-attempt work field: `agent-spawned` is written before the session exists, so the session helper appends an `agent-session-started { agentId, attempt, effort }` entry once it does, and the live `teamAgentStatusUpdate` beside `logFilePath` carries the same value. A redispatch starts the attempt with no effort; a resume, which continues the attempt, takes the effort of its new session; an entry whose attempt is no longer the member's current one is ignored. The runner, `persistence.ts` (through `TeamRunLog.memberEffort`, which the resume reader's `TeamEventLog.efforts` also uses) and the webview store (which resets it when `attempt` advances) apply that one rule. Records and logs written before this existed carry no effort, and show no badge.

- **A live agent's usage is a `getSessionStats()` delta, never a sum of `message_end` usage** (`session-usage.ts` `runUsageMeter`, used by the subagent stream bridge and the team `AgentRunner`). The baseline is taken when the run attaches to its session, so a reopened session's earlier runs stay on earlier cards. pi's total counts every billed entry, compaction summaries and cache warms included, which is what keeps the tokens consistent with the cost; a per-message sum misses both. pi notifies `message_end` listeners before it persists the message, so a reading taken inside the listener lags one response: the reading is deferred a microtask. A subagent's budget roll (`AgentManager.rollCost`) takes the same reading the bridge sends the card, through `onUsage`, so each response is read once and the budget never runs a response behind; the run's end reads once more (`settleUsage`) for spend that raised no event. The reload path rebuilds the same figure per segment with `usageOfEntry` (`agent-records.ts` `parseAgentEntries`). A resume segment records `dollarBilled` from the model its session reopened on, and the loader prefers it over the launch entry's flag, so a resumed card is labelled the same live and after a reload.

- **The twenty-one team tools have one naming table, `src/shared/team-tool-labels.ts`.** The Tools panel catalog, the card in the transcript and any future reader all take their label from it: `team-tools.ts` keeps the descriptions and the schemas but no labels of its own, mapping each spec through `toSpec`, which throws at module load for a name with no entry. That is deliberate and must stay: a `?? name` fallback would render a card reading `team_write_scratchpad` and nobody would notice for a release. The table is imported by both the webview bundle and the extension host, so it imports nothing at all. The raw snake_case name is still what the expanded overlay shows, because session logs and greps are keyed on the name the agent actually called, so a label must never replace the name in a persisted or searchable surface. Adding a team tool means adding its label in the same change.

## Webview overlays

- **An overlay's z-index is derived from the shared overlay stack, never hardcoded and never left to DOM sibling order** (`composables/useOverlayEscape.ts`, consumed by `OverlayShell.vue`). Every overlay used to render at `z-50`, so equal-z siblings painted in the order they appear in `App.vue`: a tool overlay opened from inside a team agent overlay opened behind it and looked like a dead click, while the same card worked from a subagent overlay purely because that mount is written earlier in the file. The stack `useOverlayEscape` already keeps is the same ordering paint order needs, and the composable now returns `zIndex` = base + stack depth. Reordering mounts in `App.vue` fixes one pair and leaves the next nested overlay to rediscover the bug, so it is not the fix. Mount order is what the stack records and a nested overlay mounts strictly after the one it opens over; Vue guarantees nothing about sibling order, which is exactly why the stack rather than the DOM is the source. An overlay that reintroduces a fixed `z-` class cannot be opened over.

- **The overlay stack's Escape listener stays on `document` in the bubble phase, so a control inside an overlay can keep Escape for itself** (`composables/useOverlayEscape.ts`, consumed by `OverlayShell.vue`; the control is `components/ToolCancelControl.vue`). The cancel note textarea closes its note on Escape and stops the event, which only works because the stack's handler runs later, on an ancestor node. Bind it in the capture phase, or on the overlay root, and it fires first and throws away a half-typed note by closing the overlay around it. `overlay-stacking.test.ts` goes red if either moves.
- **While a reka popup or dialog is open, the overlay stack leaves Escape to it** (`composables/useOverlayEscape.ts`). reka's dismissable layers (Select, Popover, DropdownMenu, the range calendar's Popover, Dialog) hear Escape on `window`, which a keydown reaches after `document`, so the stack's handler runs first. It therefore returns without stopping the event whenever an open element carries `data-dismissable-layer`; a stopped event never reaches the popup, and Escape closes the whole overlay around a half-picked date range. A stack overlay that is itself built on a reka dismissable layer (the image lightbox's `DialogContent`) marks that element `data-overlay-layer`, or the stack would yield Escape to the overlay forever.
- **A host prompt is a modal layer of the stack** (`ExtensionUiDialog.vue`, `useOverlayEscape(onClose, { modal: true })`). It is a reka `Dialog` marked `data-overlay-layer`, mounted only while a prompt is queued, and paints on `MODAL_Z_INDEX`. A plain element under an open reka modal (the Settings sheet, which holds the sign-in panels) gets no pointer events and loses focus to the sheet's focus trap; a nested reka layer takes both. An overlay opened while a modal is up is inserted below it in the stack, so Escape and the Tab trap stay with the prompt the user sees. While the stack yields Escape to an open reka layer beneath the prompt, reka dismisses only its highest layer, the prompt, so nothing may close the Settings sheet on a window-level Escape of its own.
- **Popper content inside an overlay paints one above it** (`usePopperZIndex` in `composables/useOverlayEscape.ts`, bound by `ui/popover/PopoverContent.vue`, `ui/select/SelectContent.vue` and the two `ui/dropdown-menu` contents). Popper content is portalled to `body`, so it stacks against the overlay rather than inside it; a fixed `z-50` ties with an overlay at the base of the stack and sinks behind one opened at depth 1 or deeper. Every stack overlay provides its z-index, and the popper binds that plus one; outside any overlay it keeps `z-50`.

## Session store

- **Nothing may append to a session file after it is deleted.** pi's `SessionManager._persist` sets `flushed = true` on its first write and from then on appends blindly, without re-checking that the file still exists. So a late write recreates the path holding only that one entry. Such a file has no `session` header, `SessionManager.open` rejects it forever, `listPiSessions` skips it, and because it is not in the list it cannot be deleted from the UI. Damocles cannot fix the writer, so it refuses to create the precondition, at three points: every holder detaches before the `rm`; a writer that resumes after an `await` re-checks liveness; and the reader caches negatives so one bad file is re-read once per change, not once per rebuild.
- **Detach is routed by session id, not by "is this my panel".** Two panels resuming the same file get the same session id (it comes from the header), and `registerSessionMutator` is a `Map`, so the second registration displaces the first. `deleteSession` therefore detaches the registered owner and `ctx.session`, deduped. The panel you clicked in may be the displaced one, or may only be pointing at the session as a not-yet-started resume/fork target. A panel mid-`start()` has no runtime yet, so detach awaits `startPromise` before resetting; without that, `reset()` bails, `whenReplaced()` resolves instantly, and `start()` goes on to open a manager on the path being removed.
- **`whenReplaced()` must report reality.** `runtime.newSession()` can throw, and returns `{ cancelled: true }` without tearing the old session down when a `session_before_switch` handler cancels. In both cases the old session is still installed and still writable. The promise rejects for both, and the logging `.catch` hangs off a separate handle so the rejection stays observable to callers while never becoming an unhandled rejection. `MessageRouter` catches handler throws, so a failed detach surfaces to the user and aborts the delete with no per-handler try/catch.
- **The session metadata cache is a pure cache, trusted only per file** (`session-store/session-meta-cache.ts`). Each session dir's list metadata and prompts persist in `~/.damocles/cache/session-meta/<encoded dir>.<app version>.json`, and an entry is used only while its file's size and mtime both still match, so a stale or foreign entry costs a re-read, never a wrong row. That is what makes last-writer-wins across windows safe, and why the file carries a schema constant plus the app version (`AppInfo.version`): a change to `sessionFileMeta` or anything it calls must bump the schema, or a same-version dev build serves the old fields. The version is in the file name so two apps on different versions sharing a folder (the extension and the desktop app update separately) each keep a valid file instead of rebuilding each other's on every read. A writer removes the other-version files for its own dir, and the unversioned `<encoded dir>.json` of older releases, once they have gone 30 days unwritten, checking once per dir per process. A live session's metadata comes from its in-memory manager with the leaf at the last entry, which is where `SessionManager.open` of the file puts it; reading the manager's own leaf would cache a rewound branch the file does not show yet. The stat and that snapshot run synchronously back to back, so pi cannot append between them. That snapshot assumes this window's manager is the file's only writer; two windows holding one conversation live already corrupt the file itself. A live session's updates stay in memory until the next scheduled write or dispose, so a turn does not rewrite the cache file after every tool call.
- **A stored conversation has one writer across processes: its session lease** (`session-store/session-lease.ts`). The lease is a `proper-lockfile` lock at `~/.damocles/locks/sessions/<sessionId>.lock`, outside every session dir so pi's listing, the session watcher and the list cache never see it. It is stale after 20 s against a 2 s heartbeat, so a killed holder's lease is taken over once stale, never before. `claimStoredSession` takes it with `lockSync` inside its synchronous check-and-bind step, after the in-process panel scan, so a held lease is refused at once and the user is told the conversation is open in another Damocles window. On Windows an `EPERM` from a lock another process is removing counts as held, and any other lease failure refuses the claim with the reason, logged; a claim never throws into its handler. A resume and a panel restore read the lease (`sessionLeaseBlocker`, which takes nothing) before they switch the panel's folder, so a refused conversation leaves the panel's own conversation and folder alone; the claim inside the switch stays the race guard. A lease whose heartbeat is more than three beats behind belongs to a holder that died or hung: the user is told so, and a panel restore refused by it is retried once, when the lease turns stale, unless the panel holds a conversation by then. The lease is per process: panels of one process share it by holder count, and the one-panel rule inside a process stays the panel scan's job. `PiSession.syncSessionLeases` keeps the leases equal to what `holdsSession` reports, so every unbind path releases through it: a switch or reset (the rebind), a delete (`detachFromDeletedSession` resets), a folder switch and a panel close (dispose, after the runtime's teardown has appended its last entry), and host dispose, because `ChatPanelProvider.dispose` awaits every session's dispose (the extension's `deactivate` and desktop's `before-quit` both run it), including those of panels closed before it: `PanelManager` tracks every session disposal it starts until it settles, which is what covers desktop's window close on Windows and Linux, where the tabs close before `before-quit`. proper-lockfile also removes held locks on a normal process exit. A session with no file yet (a fresh conversation, a fork's branch) is leased when it is bound, on the path pi will write, since the lock never touches the session file itself. When the lock is taken from a holder (`onCompromised`: another process found it stale, or it was deleted), the holder replaces its SessionManager's `_persist` with a no-op in that same tick, because pi's manager has no close and a detach lands only after an await, then detaches as for a delete and tells the user. Loss is detected at the heartbeat, so if this process's event loop stalled past the stale window while another process took over, an append queued ahead of the heartbeat can still land once. A file write outside a live panel (a delete, a rename or tag of a conversation no panel here holds) runs under the lease too (`whileSessionLeased`), as its writer: it is refused when another process holds the session or another write of this process is running on it, and while it runs no new holder of this process joins the lease, so a claim from another panel is refused ("being deleted or changed"). A delete takes the lease before any detach, so neither another process nor another panel can claim the session between the detach and the `rm`. A session id reaches the lock path only after pi's own id rule (`isSafeAgentPathId`).
- **A list upsert never applies metadata older than the list it lands on** (`chat-panel/storage-manager.ts`). A watcher event whose file still matches its cached size and mtime applies the cached row and never reads the file: on Windows a read updates the last-access time, which `fs.watch` reports as a change, so reading would re-trigger the event. An upsert captures the list generation before its metadata read and is dropped if the list was invalidated (rename, delete) or its folder closed meanwhile, because the list loaded since then read the file later. A delete event during an in-flight load invalidates that load, which may have listed the file before it went.
- **A prompt index has one definition, `pi-session/session-store/prompt-index.ts`, read by both the live session and the reload.** A prompt is a user message entry on the active branch other than one delivered mid-run (a queued batch or a cancel note, both keyed by a `damocles-mid-stream` entry), counted from the root. `PiSession.sendMessage` stamps a new prompt with `nextPromptIndex` of the branch it extends, `agent-start.ts` keys its injection with `nextPromptIndex` of the dispatch's own branch, and `history-loader.ts` stamps a replayed prompt as it walks the branch with the same `promptTest`, so the `userMessage`/`userReplay` index, the injection message's `details.promptIndex`, the Injected Context record, the permission turn key and the memory candidate name the same prompt live and after a reload. A per-panel counter cannot do that: a resumed or forked panel starts it at zero, and a reload that counts only the messages it displays restarts after every compaction. Counting from the root keeps an index unique within one session file, which is what lets the injection database key on it. That holds because Damocles never moves a leaf back within a file (a rewind forks to a new session and so a new database); anything that navigates a branch in place must first re-key those records by user entry id. A fork inherits its parent's indices below `nextPromptIndex` of the branch at the fork point, so `spawnPiFork` copies exactly those records into the fork's database through `MemoryService.copySessionInjections`; the fork's own prompts start at that index. A session-id migration whose source has no database leaves the destination's records in place (`renameInjectionDatabaseFile`), because every session start migrates from the panel id. The injection reads the dispatch's branch rather than panel state because pi commits the user entry only after `before_agent_start` and adds no prompt before it, while a run can start with no `sendMessage` in flight (a resent steer that finds the run settled). A cancel note's entry gets the mid-stream marker once pi commits it, so it consumes no index and reloads with the amber styling of its injected live echo. A run a note starts, because pi accepted it with no run in progress, dispatches before that entry exists, so `agent-start.ts` recognises it with `isCancelNoteDispatch` and keys it to `nextPromptIndex - 1`, the prompt the note annotates; it builds no memory injection, as a note steered into a running run gets none, because a record under that index would replace the annotated prompt's Injected Context, and it posts no injection chips. A note's run still sends a changed Compass status, keyed to that index; a note written before notes were marked has no marker, keeps the index it was counted with, and reloads as a prompt. An echo that commits no user entry (a pi extension command such as `/todos`, a locally handled `/compact` or `/init` notice) is emitted injected with the latest prompt's index, so it names no prompt and the next prompt keeps its own number. That uses the existing `isInjected` flag; never add a message type for it.
- **A reload shows a stopped turn as the live view did** (`session-store/turn-stopped.ts`). On Stop the adapter abandons every tool call in flight and drops any later late completion or assistant error, but pi still writes each call's aborted result (its text varies by tool) and can write an error entry for the request the Stop cut off. Neither says the user stopped the turn, so `beginAbort` appends one `damocles-turn-stopped` entry after the run settles: the abandoned `toolCallIds`, and the ids of the assistant error entries written after the leaf at Stop. `history-loader.ts` replays those calls as abandoned and drops those error rows. Never infer a stop from result text. A session written before the entry existed replays them as failed.
- **A turn's `userMessageIdAssigned` names the entry its own `prompt()` committed** (`prompt-entry.ts`, read by the adapter through `promptEntryId`). The webview keys the prompt's rewind control, its fork point and its checkpoint marker on that id. Never read the branch's last user entry for it: pi persists a message only after its `message_end` has reached every listener (`_handleAgentEvent`), so at the prompt's own `message_start` the last user entry is the previous prompt's, and a steered batch or note can commit after the prompt within the same run.
- **Two writers append after an await, and both re-check liveness first.** `maybeGenerateTitle` waits on an unbounded sub-call (15 s timeout on the small/fast model); `persistTurnStopped` waits on `session.abort()` and appends only while the runtime session still has the stopped session's id and its lease was not lost, the rule `persistCheckpointRecord` uses. A delete or switch during a Stop calls `abort()` again, which waits for the same wind-down, so the record lands in the old file before the replacement installs. `recordMidStreamMarker` and `recordSteer` re-read `this.runtime?.session` and write synchronously; `renameActiveSession`/`setActiveSessionTag` re-read after `ensureStarted()`. `recordOriginalInputIfDiverged` receives a captured session and is ordered safely only by pi's teardown awaiting `abort()` first. An implementation detail of the dependency, so it carries the liveness check explicitly rather than relying on it.

## Checkpoints

- **One shadow repo per folder, shared by every conversation in it** (`pi-session/checkpoints/`). The repo lives at `~/.damocles/pi/checkpoints/folders/<folderId>/`, where `folderId` is the first 16 hex of sha256 of `folderKey(cwd)` (the keying Compass uses). It holds one bare git dir, one index, `folder.json` (`{ path, layout: 1 }`) and the mkdir lock. The fixed-length id keeps `GIT_DIR` under git's `'$GIT_DIR' too big` limit for any project path. The shared index is the point: its stat cache lets a new conversation re-hash only the files that changed. Every git step that writes a folder repo runs under that repo's lock (`checkpoints/lock.ts`): an in-process queue per repo plus the cross-process mkdir lock with owner pid, heartbeat and stale takeover. The lock is not reentrant, so no code awaits a baseline while holding it, and only checkpoint git work (baseline, finalize, compaction snapshot, pre-rewind snapshot, restore, maintenance, ref delete and copy) ever holds it. No tool holds it. It never waits forever: a holder is stale once its heartbeat lapsed past 30 s and its pid is gone, or, whatever the pid says (a pid can be reused), once the waiter has itself polled for 10 minutes without seeing the heartbeat move. The bound counts the waiter's own polls, not wall-clock time, so a system suspend counts as one poll and never makes a live holder look stale. Every wait where the user waits takes an `AbortSignal` (`withRepoLock(dir, fn, { signal })` throws `LockWaitAbortedError`).
- **A git lock file a killed git left behind is removed only when no git of the folder repo can still hold it.** Every git command that can create `index.lock`, `packed-refs.lock`, `refs/**.lock`, `HEAD.lock`, `config.lock`, `shallow.lock` or `gc.pid` in a folder repo runs under the folder lock and registers its pid in `<repo>/git-procs/<pid>` while it runs. When a holder acquires the lock and any registered git still runs, nothing is removed. Otherwise the index, packed-refs, HEAD, config, shallow and gc.pid locks go, logged with their age, and `refs/**.lock` too when there is evidence of a dead holder: a takeover of the folder lock, or a registration whose process is gone, runs another program, or is over 24 hours old. A holder that released normally awaited all its git children, so a git lock left then is from a killed git. This assumes the spawned git process (on Windows the `git.exe` launcher, which waits for the real git) outlives the git work it started unless it is killed on its own.
- **Folder repo state is written atomically.** `size-excludes.json`, `info/exclude`, `info/attributes`, `folder.json` and `sessions/<id>.json` go through a synced temp file and a rename, the two `info/` files only when their content changes. An unreadable or malformed size state is logged and read as none, which costs a full rescan. A repo is built in `<repo>/.git-init-*` (init, identity, tuning, ignorecase, version stamp, attributes) and renamed to `.git` last, so `isInitialized` never accepts a half-built repo; the next init removes a leftover temp dir with a log line. The size state records every file over 1 MiB, the smallest cap the setting allows, so hosts with different `maxFileSizeMB` sharing a folder repo derive their size section without a rescan.
- **Snapshots and restores are byte-exact.** A folder repo's `$GIT_DIR/info/attributes` is `* -text -eol -ident -filter -working-tree-encoding`, written at creation and refreshed when it differs, so no line ending is converted, no `$Id$` expanded and no filter run, whatever the project's `.gitattributes` says. `diff` is left alone so numstat still counts lines. Legacy per-session repos do not get it: their blobs were captured through the project's attributes, so restoring through the same attributes is the closest to the original bytes. `core.filemode=false` is set only on Windows; elsewhere git's own probe applies, so an executable keeps 100755 and a restore brings its executable bit back. The rewind preview uses the checkpoint repo's exact config (`PORTABLE_CONFIG`: autocrlf and safecrlf off, filemode per platform, `core.excludesFile=` so no user-global ignore applies, `core.fsmonitor=false`, `core.hooksPath=/dev/null`).
- **Commits live only through per-conversation refs.** A snapshot is `write-tree` + `commit-tree` with no shared parent, and HEAD never moves, so nothing but a ref keeps a commit alive. A turn writes `refs/damocles/sessions/<sessionId>/<userEntryId>/before` and `/after`, plus `/skipped` for its skipped-file manifest; a compaction snapshot writes `.../<compactionEntryId>/snapshot`; a pre-rewind snapshot writes `.../_rewinds/<id>/snapshot` and `/skipped`. `_` cannot start an entry id, so that namespace never collides with an entry's refs. Ids go into ref names only after `isSafeRefId`. Deleting a conversation deletes its own ref namespace in every folder repo its entries name, under each repo's lock, after every holder detached and after its session file is gone, and nothing waits on it: that lock can be held by another conversation's first baseline for minutes. The folder ids are read from the file before the `rm`. Refs whose removal fails or never runs (the process exits) are left to maintenance's orphan rule below. A fork copies the refs of the checkpoints it inherits (and their manifests) into its own namespace and carries every checkpoint record whose `userEntryId` is on the inherited branch, wherever the record sits in the parent's file. The records are written before the fork opens; the ref copy runs after, without the user waiting on the folder lock, and checks each object under that lock when it runs, so a copy never names an object already gone. Before the fork opens, its registration in each folder repo those records name is written with `pendingCopy: true` (`markForkCopyPending`), without the folder lock, because nothing deletes a new session's registration; the copy clears the flag and keeps the file's mtime, which dates the fork for eviction. A fork's inherited checkpoints become its own refs before any ref deletion or prune in that folder repo: every lock hold that deletes a conversation's refs (delete, age eviction, orphan sweep) or prunes first runs `reconcilePendingCopiesLocked`, which copies each pending fork's refs from the validated v3 entries of its session file and clears the flag, or drops a pending registration whose session file is gone, so a copy the process exited before running is still made. The in-process lock queue is first come first served, so a restore or a delete of the fork queued later runs after the copy. A fork inherits no pre-rewind record or ref: an undo belongs to the conversation whose files it replaced. Maintenance evicts a conversation's refs by `damocles.checkpoints.retentionDays` or when its registered session file (`sessions/<sessionId>.json`) is gone and its newest ref is older than 24 hours; it never removes a folder repo as a whole and judges a conversation only by its own refs and registration.
- **gc runs off the folder lock, and still never drops what a ref or the index reaches.** Under the lock, maintenance evicts refs, rewrites `refs/damocles/index` (a commit of the shared index's tree, so blobs only the index references survive) and runs `pack-refs --all --prune`. It then runs `git repack -A -d -l` without the folder lock, under a separate `<repo>/repack` lock, and finally `git prune --expire=1.hour.ago` under the folder lock again. After a snapshot, when the repo has 50 or more packs, the producer starts `git repack -d -l --geometric=2` under the repack lock, off the folder lock and off its queue. Only `prune` deletes objects, and it runs under the folder lock, where no writer runs. Every writer (add, update-index, write-tree, commit-tree, hash-object) writes its objects and the refs or shared index that reach them within one lock hold, and git treats the shared index (`GIT_INDEX_FILE`) as a reachability root. `repack -A -d` without `--unpack-unreachable` never deletes: reachable objects go to the new pack and unreachable packed objects are written loose, and `--geometric` copies every object of the packs it rolls up. So an object a writer reuses during a repack is in the new pack or loose, and the next prune sees what reaches it. The one-hour prune grace protects only the lock-free rewind preview's throwaway objects.
- **Entries say which repo holds them.** A v3 `damocles-checkpoint` entry carries `repo: 'folder'`, `folderId` and `skipped`; new turns, including new turns in an old conversation, always write v3. A v2 entry (no `repo`) resolves to the conversation's legacy per-session repo through `getRepoDir(sessionFile)` exactly as before, for rewind, diff preview, file content and fork clone. Legacy repos are never migrated or widened; their existing age eviction retires them. A turn with no usable baseline gets a `{ v: 3, kind: 'not-rewindable', userEntryId, reason, params: { tool?, waitSeconds?, error? }, createdAt }` record under the same custom type; the webview renders its text from `reason` and `params`, and raw git text appears only as `params.error`. A pre-rewind snapshot gets a `{ v: 3, kind: 'pre-rewind', id, folderId, commit, skipped, target, createdAt }` record. `getCheckpointEntries` and `getCheckpointRecords` return neither, so every consumer of checkpoint entries still sees only entries with commits; the rewind view reads them through `getNotRewindableEntries` and `getPreRewindEntries`. Every validator checks every field and drops any other shape (an earlier unreleased v3 shape, or a v3 entry whose commits are not object ids) as no checkpoint; none throws. A restore or manifest read checks that the entry's `folderId` is cwd's and that the repo's `folder.json` names cwd, and otherwise touches nothing.
- **No pi handler awaits checkpoint git work.** pi awaits extension handlers before it forwards stream events and runs tools (`_handleAgentEvent`), and awaits `agent_settled` before `prompt()` resolves, so an awaited `git add -A` of a large folder held the first streamed text back for minutes. The `message_start`, `agent_settled` and `session_compact` handlers in `damocles-extension.ts` call synchronous `CheckpointService` methods that queue the work on the service's chain and return; there is no checkpoint `turn_end` handler. A turn's baseline starts at the prompt's own user entry, one microtask after its `message_end` (`watchPromptEntry`'s `onCommitted`): pi appends the message synchronously after notifying listeners, so the entry exists and no model request has gone out. A run opened without `sendMessage` (a cancel note, a re-steer) and a steered message start at the next assistant `message_start`, keyed on the branch's last user entry. A turn starts once per entry: the service remembers every entry it started and every entry a resumed or forked branch already has a record for, and the producer refuses a turn it already finalized, so a run keyed on a finished turn gets no second baseline and its gate waiters return at once. Finalize runs on the same chain after a still-running baseline and before the next turn's baseline, so it never delays the next prompt's stream. `checkpoint-stream-latency.test.ts` pins it on the real pi event path: another holder keeps the folder lock for the whole prompt, so the baseline cannot finish, and the first text must still stream and `prompt()` settle; it logs the time from the prompt entry's commit to the first text.
- **Records minted off the handler path are appended by the panel, and only to its live session.** The service hands each record, pre-rewind records included, to `PiSession.persistCheckpointRecord`, which appends it with `sessionManager.appendCustomEntry` only while the panel is not disposed, its runtime session still has that session id, and its lease was not lost. A delete, a switch, a lost lease and a panel close all move the runtime off the session and dispose the service first. A switch, a delete and a close first abort the running turn, then wait up to 2 s (`CHECKPOINT_DRAIN_MS`) for the queued checkpoint work while the session is still installed and the panel still registered. The abort resolves only after pi's `agent_settled`, whose handler queues the turn's finalize, so the drain covers the turn that was running, and no tool call runs after the teardown began or meets the unregistered gate's fallback block. A finalize that is nearly done still records the last turn; work still running after that (a first baseline of a large folder) is dropped, and its before-ref waits for age eviction. `dispose` stops the producer synchronously, so it writes no ref afterwards, and a late record is dropped with a log line. Never use `pi.appendEntry` from a continuation: the extension instance is shared by the folder's panels. A record lands at the leaf, which may be after the next prompt's user entry or between a tool call and its result. That is safe because a custom entry is not model context and every reader matches records by `userEntryId` or pre-rewind `id`, and tool results by `toolCallId`, never by position (`damocles-agent-invocation` entries already land mid-turn the same way).
- **File-changing tools wait for the turn's baseline in the permission gate, bounded by `damocles.checkpoints.baselineWaitSeconds`** (default 30, 5 to 600). `waitsForCheckpointBaseline` in `permission-gate.ts` decides, given the folder the checkpoint captures (`CheckpointBaselineGate.folder`, the session's cwd). Read tools, read-only-annotated MCP tools, shell commands `readonly-shell.ts` proves read-only (in every mode), the task and interactive tools, the in-process coordination tools (memory, Compass, browser, team messaging; none writes into the folder), and an Edit or Write whose target is the session plan file (`isPlanFilePath`) or outside the folder never wait and never mark the turn. The target resolves against the folder, so a path the check cannot place reads as inside and waits. Other Edit and Write, other shell (whatever path it names), MCP tools without a read-only annotation, unknown tools and the spawn tools (`Agent`, `create_team`, `resume_team`, `team_spawn_specialist`, `team_redispatch_specialist`) wait. The wait runs in the gate's single `proceed()`, after approval, so the approval prompt's time counts and a blocked call never waits. Configured PreToolUse hooks run before it, so a hook that itself writes into the folder is not bracketed by the turn's baseline; that is accepted. Past the limit the tool runs (a timeout is not a block, so no `formatPolicyBlockReason`), the turn is marked not rewindable (`markNotRewindable(userEntryId, 'baseline-timeout', { tool, waitSeconds })`), and the user gets one `notification` warning for the turn. The late baseline still finishes and warms the index, but it gets no ref and finalize yields the not-rewindable record, because the tool's changes may be in it. Later waiters in that turn return at once, and a later `message_start` for the same entry starts nothing. An abort or a dispose releases a waiter at once. The wait does not register in `PermissionState`: the session is working, not waiting on the user. Each wait logs `[perf] checkpoint.wait <ms> outcome=<ready|timeout|aborted|disposed>`. The timer is the only bound; git is never killed on a timeout, which would leave `index.lock` in the shared repo.
- **Subagents and team agents wait on the parent turn's baseline through the same gate.** Their gate context carries the parent panel's `checkpointBaseline`, which reads the panel's live service at call time, so a nested file change never lands before the parent's current baseline, under the same limit, the same folder rule and the same single notice. A background agent still running after the parent's turn settled has no turn to wait for; its changes land in the next turn's window. This cannot deadlock: a baseline waits only on the service chain and the folder lock, no tool holds the lock, and every gate wait ends at the timer, an abort or a dispose.
- **Every restore first keeps the folder's current state, and the user can undo it.** A rewind to a turn and an undo both snapshot the folder exactly like a baseline (same excludes, protections and tracked capture) before anything changes, and log the commit (`pre-rewind snapshot <id> of session <sid> is commit <hash>`). If that snapshot fails, nothing is restored and the user is told no file changed. A v3 target is snapshotted and restored in one folder-lock hold; for a v2 target the snapshot goes to the folder repo of cwd under its lock, then the legacy restore takes the legacy repo's own lock, so no code nests two locks. The panel persists the pre-rewind record whenever there is one, including when the restore failed, and the rewind view lists each as a restore point, "Before rewind at 14:32" or "Before undo at 14:32", with an Undo rewind action (`undoRewind`). Undo (`restorePreRewind`) puts back the files of that snapshot through the same `safeCheckout` protections and takes its own pre-rewind snapshot, so an undo is undoable. It changes files only; the conversation tree is already navigable in pi. When the apply and its rollback both fail, the user's error says the folder may be partly restored and that the files from before the rewind are kept, and names both errors. The user's wait is bounded: `PiSession` gives a restore `RESTORE_WAIT_MS` (30 s) to get past earlier checkpoint work on the service chain and the folder lock; past it the restore resolves `aborted` at once and never runs later, and once it holds the lock it runs to completion. A missing or disposed service (`service-unavailable`) and a failed git probe (`git-unavailable`) are told apart. Every message is localized.
- **Files the project's own git tracks are always captured.** A snapshot captures every file the project's git tracks under the conversation folder, even under a path the exclude set drops (`dist/`, `build/`, `out/`, `coverage/`, `.cache/`, `node_modules/`, `*.log`, `.DS_Store`) or one the project's `.gitignore` matches (a force-added `.env.example`). The list comes from `git -C <cwd> -c core.fsmonitor=false ls-files -z`, which never writes the project's index or refs, cached per process while the project's index keeps its size and mtime. No enclosing repository means no tracked list, and a failed read is logged and read as empty. The security excludes (`.git`, `.damocles/settings.json`, `.damocles/settings.local.json`, `.damocles/mcp.local.json`) always win: a tracked copy is never captured or reported. The size cap, the category excludes and LFS still apply to tracked files, and each file they leave out is a skip in the checkpoint's list. Mechanism: `add -A`, then `update-index --add` of the tracked files the shared index lacks; once there, the stat cache keeps them current and `prepareSnapshot` keeps them, so an unchanged tracked file is never re-hashed. A submodule is tracked only as its gitlink, which is never staged, so files inside a submodule or a nested repository follow the exclude rules like untracked files; an embedded repository with no commit is left out with one log line instead of failing the folder. Only folder repos capture tracked files: a legacy per-session repo never does, in a restore or in the preview, so a tracked file a legacy repo excludes is ignored now and protected, neither deleted nor restored. For a folder-repo target, a tracked file the exclude rules drop is restored when the target has it and left where it is, never deleted, when the target lacks it (the target may predate the project tracking it, or the tracked list may have been unreadable then). When a directory now stands where the target has such a file, that path is protected, so nothing the directory holds is deleted. The rewind preview follows the same rules.
- **Large and binary files stay out of folder repos, and a rewind never touches them.** A folder repo's `info/exclude` holds the exclude set of its version (`FOLDER_CHECKPOINT_EXCLUDE_SET`: the performance excludes plus media, archives and disk images, model weights and array dumps, and Python, JVM and JS build and environment caches; images and PDFs are left to the size cap), every `filter=lfs` pattern of the project's `.gitattributes`, and a generated section listing every file over `damocles.checkpoints.maxFileSizeMB` (default 25, 1 to 2048). Before each snapshot the size section is rebuilt from lstat of the untracked and modified files plus the previous section, never reading contents, and files that are now ignored are dropped from the index unless the project tracks them, because an exclude never stops `add -A` from restaging a file already in the index. Every checkpoint stores its complete skipped list (path, bytes or null for a directory skipped whole, reason `size`, `category` or `lfs`) as a JSON blob in the folder repo, referenced by its `/skipped` ref so it lives exactly as long as the checkpoint, with no truncation. The session entry keeps only the summary: `{ totalCount, totalBytes, byReason: { size?, category?, lfs?: { count, bytes } }, patterns: [{ pattern, reason, count, bytes }], manifest }`. A skip counts under a category or LFS pattern only when `check-ignore -v` names the folder repo's own `info/exclude`; a project `.gitignore` line such as `*.mp4` is the project's own ignore, not a skip. The rewind view shows the summary under "Not restored by this checkpoint" and loads the full list when the user expands it (`requestSkippedFiles` answered by `skippedFiles`, read by `readSkippedManifest` without the folder lock, since a ref keeps the blob alive). A restore never modifies or deletes a file that is protected now: one ignored now (and not a tracked file a snapshot captures anyway), over the cap now, or recorded as skipped by the target snapshot. That includes a file captured small and grown past the cap since, which a rewind leaves as it is. A path that is ignored now but absent is recreated from the target, because that changes no existing bytes. The `clean -fd` after the apply protects every path ignored at the start of the restore by exact lines, so a restore that removes or replaces a `.gitignore` never deletes a file only that `.gitignore` protected. When a protected file or directory stands where the target needs a path, the restore refuses and touches nothing, because `read-tree -u` would delete an ignored file in its way. A turn's change list reports a file that grew past the cap during the turn as a skip, not a deletion. The protection is path-based and applies to legacy rewinds too, without widening a legacy repo's excludes. The rewind preview uses the same cap, so it lists exactly what the restore changes.

## Agent auth store

- **pi owns `auth.json` and is its only writer; Damocles reads it without pi's lock** (`pi-session/auth-file.ts`). pi's `FileAuthStorageBackend` rewrites the file in place with `writeFileSync` under `proper-lockfile` and retries only `ELOCKED`, so a reader that took the same lock could make pi's own write fail on Windows, where a `mkdir` racing the reader's lock-dir `rmdir` fails `EPERM`. A read that lands between pi's truncate and its write sees empty text or an unterminated prefix of one JSON object, which `JSON.parse` rejects, so `readAuthFile` re-reads up to 5 times, 20 ms apart, and then returns the last content this process parsed from that path, which may be older than the file on disk; with no earlier read it throws, and the status reads as signed out. Every Damocles read of auth state (`readClaudeAuthFromDisk`, `readOpenAIAuthFromDisk`) goes through it. A failure is logged by error name and code only, because a `JSON.parse` message quotes the tokens it failed on, and only once until a read succeeds or the failure changes. A missing agent dir or file reads as no credentials and creates nothing.
- **A change to `auth.json` re-syncs the OpenAI runtime key and republishes the account chip in every live session.** `PiRuntime` watches it through `FileWatcherFactory.watch(agentDir, 'auth.json')` and, debounced, re-applies the runtime key rule and then calls `publishAccountInfo()` on each registered session: a login, logout or token refresh in another Damocles app or a pi CLI lands only in that file. That keeps account state on its one publisher, called because one of its inputs changed.
- **The OpenAI API key lives in per-app secret storage, and in `auth.json` only on a host without a persistent store; the ChatGPT grant lives in `auth.json`.** pi's `auth.json` holds one credential per provider, and Sign in with ChatGPT is the `oauth` method of `openai`, so a stored key and a ChatGPT grant cannot both live there. The key is the host secret `damocles.openai.apiKey`, applied as pi's in-memory runtime key for `openai` while `openaiRuntimeKeyWanted = apiKey && (preferApiKey || !chatgpt)` holds (`openai-runtime-key.ts`); pi reads a runtime key before the stored credential, so the prefer toggle switches billing with no login. The sync only sets or removes the runtime key and never calls `logout`, which would delete the ChatGPT grant; for the same reason OpenAI is not in `CUSTOM_PROVIDER_DEFS`, whose deauth logs out. At `PiRuntime` init, before the `auth.json` watcher starts and before init resolves (every sign-in awaits it), a plain-text `openai` api_key an older version wrote is copied to the secret (read back before anything is deleted; a different key already in the secret wins), the `auth.json` copy is deleted with `logout('openai')` while the entry is still an api_key, and `~/.damocles/openai-api-key-moved.json` (`{ movedAt, by }`, no secret) is written atomically. A host whose secret store is not persistent (`SecretsStore.isPersistent` false, the desktop app with no OS encryption or Linux `basic_text`) moves and deletes nothing and writes no marker: moving the key there would lose it at the next restart. The key stays in auth.json, where pi uses it as the stored `openai` credential, `openaiAuthStatus` counts it as a configured key, clearing the key removes it there too (`logout('openai')`, safe because that entry is an api_key and so no ChatGPT grant), and a later start with a persistent store migrates it. Saving a key on such a host writes it to `auth.json` too (`login('openai', 'api_key')`), or the next restart would bring back the previous key; while that one `openai` slot holds a ChatGPT grant, which the write would delete, the key goes only to the session-long secret. pi has no compare-and-delete, so a sign-in by another process between that check and the delete would be removed; that window exists only at the first start after the upgrade. Each host has its own secret store, so the other host, finding its secret empty, no key in `auth.json` and a marker naming the other host, shows a one-time notice that opens the OpenAI auth panel, recorded in its own global state. `getChatGPTAccessToken()` returns a token only while ChatGPT is the active credential and pi resolves it as OAuth, because pi's `getAuth('openai')` returns the runtime key first and wham/usage must never receive the API key.
- **`logout('openai')` drops the runtime key, so every OpenAI auth change re-syncs it.** pi's `RuntimeCredentials.delete()` clears the override along with the stored credential, and its `login` keeps it. The migration, each key set or clear, the prefer toggle, a secret change from another VS Code window (`SecretsStore.onDidChange`), the `auth.json` watcher, and every OpenAI login or logout re-apply the rule, all on PiRuntime's OpenAI credential chain (`_openaiCredentialSync`), so each sync reads the state it applies and no sign-in in this process lands between the migration's check and its delete. The sync keeps no last-applied-key cache, which would turn the re-sync after a logout into a no-op. A pending ChatGPT sign-in holds the chain (and pi's own `openai` credential queue) until it ends, so every user OpenAI change (key save or clear, the prefer toggle, both sign-outs) aborts it first, and the auth.json and secret-change resyncs republish the account chip before they wait on the chain as well as after.
- **The account publisher's inputs include the ChatGPT grant and the key secret.** `openaiTokenSource` orders preferred key, ChatGPT (`chatgpt-oauth`), Codex (`codex-oauth`), key, exactly as `resolvePiModel` does, and `openai` bills dollars only while the runtime key is wanted; sub-call billing (`describeSubCallModel`) reads the same prefer flag, because the provider alone no longer names the credential. Key presence is cached in `PiRuntime` at init and on every secret change, so the status stays synchronous for the settings panel; the sync records it from the secret read before it calls pi, so a pi failure cannot leave it stale, and until init's first sync has run the settings panel reads the secret itself. pi's `CredentialSynchronizationError` comes after pi committed the change, so a key sync or a ChatGPT login that throws it counts as done.

## Memory injection

- **Injection is a delta against the session projection** (`pi-session/agent-start.ts`, `memory/managers/injection-manager.ts`). Each `before_agent_start` dispatch reads `ctx.sessionManager.buildSessionProjection().messages` once, folds it with `readLiveInjections` (`pi-session/live-injections.ts`), and sends only memories not already live, plus notices for live ones that were superseded, edited or forgotten. The projection is exactly what the model will receive, so rewind, fork, compaction and context edits are handled for free: a message compacted away or omitted by an edit reads as absent and its memories become eligible again. When nothing is new and the Compass change key is unchanged, no custom message is sent at all.
- **In-context ids come only from `details`, never from the message text** (`memory/injection/details.ts`). pi stores a custom message's `details` and never sends them to the model. Every injection message carries a `ContextInjectionDetailsV1` listing each memory it rendered (id, content hash, tier), its notices, whether it carried the profile, and the Compass key it sent. Parsing ids out of the text would make a memory that quotes another memory's id look injected. A message without valid details (a session recorded before this existed) is ignored, so its memories are re-injected once.
- **Nothing about injection is held on the extension instance.** The pi extension is process-global and outlives any one session, so there is no first-message set, no per-session cache and no rename bookkeeping. Profile presence (`profileInContext`) and the live Compass key also come from the projection: the profile returns after compaction, a fork already carries it, and a restart re-reads the projection from disk and re-injects nothing.
- **The Injected Context record is written after an await, so the build re-checks liveness first** (`pi-session/agent-start.ts`). A `before_agent_start` still in its memory build is not awaited by the abort a session delete runs, so the delete can finish first. The handler therefore asks the extension's panel registry, which every holder of a deleted session leaves before the delete, whether a panel still holds the session, and posts and persists nothing when none does; persisting would recreate the deleted session's injection database.
- **No `context` handler, and past injection messages are never rewritten.** History stays byte-stable so the prompt-cache prefix survives; `damocles-extension.test.ts` pins that no outbound context handler is registered.
- **Stored text cannot open or close any tag the injection message carries** (`memory/injection/render.ts`). Every tag name in that message (the renderer's `damocles_memory`, `memory`, `observation`, `title`, `facts`, `compact`, `memory_updates`, the profile's `user_profile`, `project`, `global`, `static`, `dynamic`, and the Compass status's `damocles_compass`) gets a zero-width joiner after `<` wherever its opening or closing form appears in memory content, titles, facts, notices or a profile section, so a stored memory cannot close its block or forge another, and model-written profile text cannot fake a section. A notice is always one line, so stored text cannot forge a notice line. The pattern is a fixed-string alternation anchored on `<`, which keeps it linear-time. Attribute values, the Compass `error` included, go through `escapeAttribute`: `&`, `"` and `<` are escaped and line breaks flattened.
- **The gate searches only what the user typed** (`pi-session/agent-start.ts`). The opened-file or selection block Damocles prepends to a message is model-only context: `splitIdeContext` (`src/shared/ide-context.ts`, which also holds the `formatIdeContextBlock` the producer uses) takes it off the prompt before `queryTerms`, and its path is the file gate's only editor file: a message sent without the block gives the gate none, never the live editor, which the user chose not to attach and may have changed since Send. Its boilerplate words would otherwise match memories as if the user had written them. Anything else that reads the block back must use `splitIdeContext`, never its own copy of the format.
- **Lexical matching reads only a memory's own text** (`memory/managers/injection-manager.ts`). Per-term match sets and the df/N statistics use the FTS column filter `{content title facts}`; `search_terms`, `tags` and `summary` are model-generated and would admit a memory on a synonym it never states. The file gate's candidate query uses `{content files_read files_modified}`, the fields its proximity matcher confirms against. `search_memories` still searches every column.
- **Typed paths feed the file gate, not the query words** (`memory/injection/gate.ts`, `splitTypedPaths`). A path's parent directories locate a subject rather than name one, and a user or folder name in them (`C:\Users\<name>\…`, `C:\GameDev\…`) would otherwise admit memories on its own. A token with a separator and an extension is a file path: it goes to `query.files` and adds no term. A directory path (rooted, holding a backslash, or of 3+ segments) keeps only its last segment; two-segment slash words such as `app/Http` or `and/or` stay words. A bare file name such as `OrganizationScope.php` keeps its name as a term and drops the extension, which names a format, not a subject.
- **Term specificity comes from the store and from general vocabulary** (`memory/injection/gate.ts`). Two generated references, regenerated only by `npm run generate:reference-words` with a SHA-256 check on every download and credited in `THIRD-PARTY-NOTICES.md`: `english-reference.generated.ts`, the 49,104 single-token words of david47k's top-english-wordlists 50k list from Google Books Ngram (CC BY 3.0), ranked; and `software-reference.generated.ts`, 3,682 more words from cspell-dicts' software-terms and filetypes dictionaries (MIT), unranked and ranked after every English word. Book English alone missed software words (`repo`, `json`, `php`) and chat words (`hmm`, `yep`), which then admitted memories on their own. Lookup is by Porter stem (`memory/porter-stem.ts`, a port of FTS5's `porter` tokenizer that `porter-stem.test.ts` checks against SQLite). The generator stems both lists into `reference-stems.generated.ts`, which is the only reference the gate imports, so the first prompt builds a map instead of stemming 52k words; `porter-stem.test.ts` fails when the stems and the stemmer disagree. A term takes the rank of the most frequent reference word sharing its stem, because its FTS match is a match on that stem, so `summarization` ranks with `summarize`. Query terms sharing a stem run the same match and count once. A term is common, and dropped, when its store df exceeds `max(20, 0.05·N)` or its rank is within `coreVocabularyRank` (1,000). An `[a-z]+` term whose stem is unlisted is distinctive. There is no separate df cap on distinctive terms: after the vocabulary fix the highest-df distinctive terms in the replay stores were names whose matches were on topic (`oauth`, `iemis`, `toolsearch`, `scratchpad`, `baroulkos`), and store frequency alone cannot tell a name from a general word (`baroulkos` df 6 of 485 against `php` df 8). A term in any other script, and an identifier (3+ characters, starting with a letter and holding a digit, such as `oauth2` or `es2022`), is distinctive when its store df is at most `max(3, ceil(0.005·N))`, the in-store rule. When a prompt has at least 3 letter-only terms, in any script, and most of them miss the reference, the prompt is not English and its unlisted `[a-z]+` terms must also pass the in-store rule. Any other term with a digit (a number, a digit-led piece such as `26t18`, a two-character mix such as `s3`) is never distinctive and never counts toward coverage; two characters are too few to name a subject. When the query has a distinctive term, a memory passes only by matching one (relevance ≥ 0.1), in the manner of a common-terms query: general words would otherwise admit unrelated memories. A query with none is a coverage query, as a common-terms query with only high-frequency terms runs as a conjunction: a memory must match every topical term when the prompt has at most `coverageTerms` (3) of them and that many otherwise, carry at least half of the query's idf, and match at least 2, so a lone general word never admits. On the replay corpora two general words together admitted an unrelated memory far more often than a related one. English contractions are removed before tokenizing, because `doesn't` splits into the non-word `doesn`.
- **Only a strong lexical match renders full** (`memory/injection/gate.ts`, `LexicalMatch.fullAllowed`). A gated memory renders full only when it matched a distinctive term at relevance ≥ 0.4 (`GATE.fullMinRelevance`); a coverage match, one admitted only by the file gate, and one graded `low` by the rerank render compact at most. `assignTiers` treats both entry limits as maxima: over the token budget it demotes the lowest full entries to compact, dropping the lowest compact entry whenever a demotion would exceed the compact limit, then drops compact entries from the bottom.
- **A notice names the user only for a user forget** (`memory/injection/render.ts`, `memory/managers/injection-manager.ts`). A live memory forgotten with `user_forget` or `quality_audit` gets "was forgotten by the user"; decay, a purged row or any other loss gets "was retired from memory", because telling the model the user rejected a memory that merely aged out is false. A dedup merge records a `SUPERSEDES` edge from the primary to each merged row (`memory/dedup-decay.ts`), and the injection follows those edges, so a live merged memory yields a superseded notice naming its primary and a pasted merged id resolves to the primary. A merge with no edge cannot be resolved and stays unannounced.
- **The gate constants are calibrated, not guessed** (`memory/injection/gate.ts`, pinned by `injection-gate.test.ts`). Retune them only with the replay harness (`memory/__tests__/injection-replay.test.ts`, opt-in through `DAMOCLES_MEMORY_REPLAY`), which copies the real store and replays recorded sessions; it must keep at least a 70% byte reduction against what the old engine recorded and a p95 build time under 50 ms.

## Memory judges on Jev

- **The judge model follows the credentials** (`pi-session/classifier-model.ts`). Jev runs on TypeSafe (`typesafe/jev-latest`) when that provider is configured (the `damocles.typesafe.apiKey` secret, applied as a runtime key through `CUSTOM_PROVIDER_DEFS`, or `TYPESAFE_API_KEY`), else on OpenRouter (`openrouter/~typesafe/jev-latest`) when OpenRouter is, else the judges use the sub-call model alone. The TypeSafe settings panel names the active judge from `PiRuntime.describeMemoryJudge()`, so the switch is visible. That reading is used only once `memoryJudgeKnown` holds (a folder runtime exists and a custom-provider sync has applied the stored keys); before that, `typesafeAuthStatus` reads the TypeSafe and OpenRouter secrets and pi's `TYPESAFE_API_KEY` / `OPENROUTER_API_KEY` (`CLASSIFIER_ENV_KEYS`), and with neither reports `unknown`, never `none`, because the sub-call model is not resolved yet. The OpenRouter key has its own settings section that writes the secret without touching `damocles.explore.provider` or `.enabled`.
- **A refused credential opens that provider's breaker, never a per-call retry** (`pi-session/classifier-breaker.ts`). A 401, 402 or 403 describes the key or its account, not one request, so `runClassification` opens the provider's breaker and selection skips it: TypeSafe falls over to OpenRouter, and with neither the judges use the sub-call model. A credential change reported by `syncCustomProviders` (`changed`) resets the breaker at once, and the runtime re-runs that sync whenever any `CUSTOM_PROVIDER_DEFS` secret changes, which includes a change made in another window. Saving a TypeSafe or OpenRouter key resets that provider's breaker even when the value is unchanged (`resetClassifierBreaker`): the re-save is the user saying the refusal is resolved. A 402 can also clear with the key unchanged (credit added), so after `CLASSIFIER_PROBE_AFTER_MS` (5 min, on the monotonic `performance.now()` clock, so a wall-clock step cannot lengthen it) the next request is the one probe; the pick and the claim happen in the same tick, so concurrent judges never send a second one. Outcomes carry a generation ticket, so a request sent with the old key cannot reopen a reset breaker, and the ticket records the breaker it probes at claim time: a request claimed before the breaker opened can neither clear it nor end its probe, so parallel batches settling in any order leave one refusal standing and one probe in flight. 429, 5xx, timeouts and malformed answers never open it; each call falls back on its own. An OpenRouter 403 whose `error.metadata` carries moderation `reasons`, guardrail `patterns`, or an `error_type` of `content_policy_violation` or `refusal` declined that input (OpenRouter's documented error shapes), not the key, so it never opens the breaker (`isInputRefusal`); the body is parsed in memory and never kept. A body pi truncated past 4,000 characters no longer parses and is counted as a credential refusal, which only sends the judges to their fallback. `describeMemoryJudge()` reports `rejected` providers until an answer or a reset clears them. `PiRuntime.onMemoryJudgeChange` is static, backed by a module-level listener set, so `ChatPanelProvider` subscribes at activation without creating the runtime (every `PiRuntime.exists` guard depends on that). It fires on a breaker change, a published folder, the end of a custom-provider sync, an account republish (`republishAccountInfo` and the runtime's own) and a `damocles.explore.*` change; `ChatPanelProvider` also rebroadcasts on a TypeSafe or OpenRouter secret change, the pre-start inputs, and broadcasts only the newest of overlapping reads, so an open panel never shows a stale judge. The log names only the HTTP status (`classifierFailureCause`) and the reason the breaker holds after settling; pi's error text carries the response body, which can echo memory text.
- **`runClassification` is the only classifier seam** (`pi-session/pi-runtime.ts`). It never throws; it returns `null` when no classifier is configured, the request did not stop with `stop`, or any question lacks an answer of its type. Memories and prompts go only in `state`; the questions' instructions and criteria are constants in `memory/classifier-judges.ts`, and rerank questions name candidates by positional keys (`c0`…), never by stored text or ids. It logs the stop reason and `classifierFailureCause` (HTTP status, timeout, malformed answers or no response), never the error text, because a provider error message can echo the request body.
- **The contradiction judge keeps its three values.** Jev's probability that the facts cannot both be true now decides alone at or above `CONTRADICTION_THRESHOLDS.high` (0.85) and at or below `.low` (0.15). Between them, and when Jev fails, the LLM judge decides; with no sub-call model that is `null`, which defers the row to the conflict sweep exactly like an outage. Never map the middle band to `false`.
- **Reranks stay inside their caps** (`injection-manager.ts` about 2 s, `retrieval-manager.ts` 8 s). Jev runs first with the whole cap; on failure the LLM rerank gets only the time left, and with less than `LLM_RERANK_MIN_MS` (300 ms) left it is not started, since it could not finish but could still be billed, and the lexical (BM25) order stands. One Jev request carries at most `RERANK_BATCH_SIZE` (10) score questions; batches run in parallel and the first failed batch fails the Jev rerank as a whole at once, aborting the others through one `AbortController` passed as `abortSignal`, so a doomed rerank never spends the LLM's time.
- **Score semantics.** A score is the probability-weighted index into `RERANK_CRITERIA` (`unrelated`, `partially relevant`, `directly relevant`), so it can fall between levels; it rounds to the nearest level (low, medium, high). The injection records it normalized to 0..1 as `rerankClassifierScore`, and the Injected Context card renders the localized verdict from it, so a persisted record carries no language. A search result's `reason` is model-facing and stays English (`Classifier: <verdict> (<score>)`); the result also carries `rerankClassifierScore`, from which the Memory panel renders the localized verdict.
- **Thresholds and batching are calibrated, not guessed.** Retune them only with `memory/__tests__/classifier-eval.test.ts` (opt-in through `DAMOCLES_JEV_EVAL=1` and a TypeSafe or OpenRouter key in the environment), which copies the real store; `classifier-judges.test.ts` pins the chosen values. TypeSafe documents no per-request question cap, only a token budget (64k per request, 32k for the state plus the longest question; pi lists 32k for OpenRouter's Jev).

## Usage accounting

- **One inclusion rule decides what counts as spend** (`src/shared/usage-accounting.ts`). It mirrors pi's `getSessionStats()`: every assistant message whatever its `stopReason` (aborted and error turns were billed), a `toolResult` message that carries usage, `usage` entries (the cache warmer writes `kind: 'cache_warm'`), and `compaction` and `branch_summary` entries that carry usage. The status bar (live and on reload), the subagent meters and reload, and the `/stats` worker all import this module, so a figure never differs between the live view and a reload. The module is imported by the webview bundle and the worker thread, so it imports nothing from pi, `vscode` or Node. `pi-parity.test.ts` builds a session with pi's `SessionManager` and asserts the indexed cost equals a real `AgentSession.getSessionStats()`.
- **Image cost travels as toolResult `usage`.** `GenerateImage` returns `usage: result.usage` on its result, a failed call included, and never throws once usage exists, because pi replaces a thrown result with one that has no usage. It writes no ledger line, which would count the same spend twice. The recorded cost is what OpenRouter billed. pi prices image models by token from its catalog, at the text rate for image tokens, and drops the `usage.cost` (USD) OpenRouter returns on every response. So the tool hands pi a per-call `fetch` that reads `usage.cost` from a clone of the same response (no second request), accepts it only as a finite, non-negative number, and records it as `cost.total`, with `cost.output` taking what pi's prompt-side estimate leaves. When the field is absent or invalid it keeps pi's estimate and logs the model id only; the body, prompt and image are never logged. Only models with a positive output token price are offered, so the fallback is never $0. `details` carries `provider` and `model` on every outcome, which `/stats` uses to attribute the toolResult row to the image model.
- **A fork's inherited spend is not its own.** A fork copies its parent's entries verbatim (same `id`, same `timestamp`) into a new file whose header carries a later timestamp, so a copied entry always predates its file's header. `isOwnEntry(entry, headerTimestamp)` is that test; a conversation's totals count only its own entries. They are derived from `sessionManager.getEntries()` on every read, never cached, so a session replacement or a switch cannot leave a stale baseline.
- **The budget counts the conversation's own spend plus its subagent and team spend.** `ownSessionUsage` (`session-usage.ts`) is the figure for the status bar and for every budget check (`checkBudgetAtTurnEnd`, `enforceBudgetInFlight`, `addExternalCost`, the pre-prompt gate), so a fork is never stopped by what its parent spent. Subagent and team cost is added from the adapter's external total, which resets when a new conversation is seeded. The status bar shows the conversation's own spend only; subagent and team spend show on their own cards. The in-flight check runs a microtask after `message_end`, because pi appends the message only after notifying listeners, and it uses the same reading the status bar receives in that microtask.
- **Never bill from `history-loader.ts`'s context snapshot.** Those fields describe the last request's prompt size for the context meter. Cumulative spend comes from summing entries under the rule above, and the two sets of fields are kept apart in the webview store. The snapshot follows pi's `getContextUsage`: it skips an aborted or errored message and one with no tokens, and a compaction resets it to zero until the next response, live (`compaction_end`) and on reload (`contextSnapshotOf` in `context-snapshot.ts`).
- **Every billed internal model call appends one ledger line.** Titles, memory work (extraction, rerank, merge, profile, query expansion, quality audit) and `/btw` run outside any session file, so their spend lives in `~/.damocles/usage/subcalls.jsonl` (`usage-stats/subcall-ledger.ts`). `PiRuntime.runStructuredCompletion` appends the line for titles and memory, and `PiRuntime.runClassification` for every Jev request that reports usage, a failed one included (purpose `memory-merge` or `memory-rerank`; TypeSafe's direct `jev-latest` has no catalog price, so its rows are unpriced tokens). The `/btw` aside runs on an in-memory pi session, so its own `message_end` subscriber in `pi-session.ts` appends it. A call site that does neither is spend `/stats` never sees. `appendSubCallUsage` skips a call with no tokens and no cost (`carriesUsage` in `usage-accounting.ts`). It never reads `totalTokens`, because a provider may leave that at 0 while it reports tokens. The ledger is append-only JSONL, one `appendFileSync` per line, which is safe across VS Code windows.
- **Formulas.** Every `/stats` card shows its formula in a tooltip and must match these.
  - Cost is the recorded `cost.total`. An entry with tokens and a zero cost is unpriced: its tokens go into a separate "unpriced tokens" figure and never read as $0.
  - Total tokens is `input + output + cacheRead + cacheWrite`, pi's `totalTokens`.
  - Cache hit rate is `cacheRead / (input + cacheRead + cacheWrite)`, and has no value when the denominator is 0.
  - Net cache savings is `(cacheRead + cacheWrite) × inputRate − (cost.cacheRead + cost.cacheWrite)`: what the cached tokens would have cost as plain input, minus what they did cost. `inputRate` is `cost.input / input` from the same entry, which follows pi's pricing tiers. When `input` is 0 it falls back to the registry rate the host passes to the worker (pi's `model.cost.input` is USD per million tokens, the worker takes USD per token). Unpriced entries are excluded. The figure can be negative when 1-hour cache writes are rarely read.
  - The cost label always reads "API-equivalent" and adds "est." when the current account is not dollar-billed, because the billing mode at request time was never recorded.
- **The `/stats` index is a cache, and it never forgets spend** (`src/core/usage-stats/`). `~/.damocles/usage/usage.db` is a `node:sqlite` WAL database owned by one worker thread per window, because the first scan can read more than 1 GB. The worker imports neither `vscode` nor pi and takes every path from the host. The host closes it after 2 minutes idle, and never while it is making progress. When the worker sends nothing for 5 minutes with a request in flight, the host terminates it and rejects the waiting requests. The next request starts a fresh worker. Each file commits in its own transaction, so at most the file in progress is lost.
  - The first worker in each extension host runs `PRAGMA quick_check` on open. Later workers skip it, because it reads the whole file. SQLite still reports corruption from real statements, and the worker then closes the index, so the next open checks it and moves it aside.
  - Rows upsert on `entry_key = "<id>|<timestamp>"`. A copied entry belongs to the oldest top-level session whatever the scan order. For session-file rows, `entries.session_started_ms` is the start of the top-level session the row is attributed to, not the file's own header time: a fork copies subagent files into its own folder (`fork-agent-data.ts`), and the copies' own headers cannot order them. Ties break on session id, agent session id and path, a strict total order, so every scan order gives the same rows.
  - Nested subagent and team files attribute to their parent's session id and keep their own id in `agent_session_id`. Team event logs and `.json` checkpoints are not sessions and are never indexed.
  - Rows keep the raw provider and model. `model_key` maps a dated id to its base id when only the base is in the registry. `meta.model_registry` holds a fingerprint of the registry keys the rows were keyed with. When a scan sees a different registry, it re-keys every row in one `UPDATE`, so the model filter, `byModel` and the fallback rate join never split one model across two keys.
  - Files are read from a stored byte offset, complete lines only; a trailing partial line waits for the next scan. A shrink or a changed tail hash reparses from byte 0, which is idempotent. Each file is indexed in one `BEGIN IMMEDIATE` transaction. The worker re-reads the file's row and its size inside it, so a second window's worker serializes rather than resuming from a stale offset. A migration re-reads `user_version` under the write lock, so two windows opening an old index migrate it once.
  - Marking vanished files and recording the scan time fail soft. When another window holds the write lock too long, the worker logs it, retries on the next scan, and still answers with the rows it indexed.
  - Spend rows are never deleted. When a file vanishes its rows stay, its conversation is marked missing and its title is cleared, so it shows as "Deleted conversation". A file counts as vanished only when a stat inside the marking transaction finds it gone, because another window may have indexed a file created after this scan listed the directory. The index runs with `secure_delete` and truncates its WAL after it clears a title, so the title leaves the database files too. Rebuilding the database would lose that spend, so schema changes are additive migrations under `PRAGMA user_version` and the code never rebuilds a readable database.
  - A corrupt database is moved aside as `usage.db.corrupt-<ms>` and the loss is logged. Only the newest aside copy is kept, and it can still hold titles from before the corruption. Windows refuses the move while another window's worker holds the file open, and the request then fails with an error that says so.
  - Filter values reach SQL only as bound `json_each` parameters. Time buckets use the webview's zone, not the extension host's. Under Remote-SSH, WSL or a container the two often differ, and the webview matches bucket keys as strings. The webview sends its IANA zone with each query. The host rejects a zone that is not a name of at most 64 characters or that `Intl.DateTimeFormat` does not accept. The worker cuts days, weeks, months, heatmap weekdays and hours, and active days in that zone through the `usage_local` SQL function in `queries.ts`, with the zone as a bound parameter. The function formats each 15-minute UTC slot once per zone with `Intl.DateTimeFormat` and caches it. That is exact because every UTC offset and DST change since 1972 falls on a 15-minute UTC boundary. An offset zone such as `+05:37` breaks that, so the host accepts zone names only. Weeks start on Monday in every locale. The chart never drops a point whose bucket it did not expect. `chartRows` gives it its own row in key order, so the chart still sums to the KPI.
  - Every breakdown (`series`, `byModel`, `byProject`, `bySource`) groups the same filtered rows as the totals with the same unpriced rule, so each sums to the KPI total; `queries.test.ts` asserts it under every filter kind. `buildReport` reads every figure in one read transaction, so another window's commit never lands between the totals and a breakdown. Sources are exclusive: a ledger row is a background task by purpose; otherwise a `compaction` or `branch_summary` entry is compaction and summaries, and a `usage:cache_warm` entry is cache warming, whichever file it sits in; only the rest take the file's origin (main chat, subagent by agent type, team by role). A new source must keep that one-branch-per-entry `CASE` in `queries.ts`, or a row is counted twice or dropped.

## Platform boundary and shared stores

- **Core reaches the host only through `src/platform`.** Classes take the services they use (`SettingsStore`, `TrustService`, `FileWatcherFactory`, `NotificationService`, ...) by constructor, wired from `activate` through `ChatPanelProvider`. The one global is the accessor in `src/core/platform-host.ts`: the host calls `installPlatform` at the start of `activate`, before any core code that reads it runs (only `perf.ts` `markActivationStart`, which records a timestamp and reads nothing, comes first, so the platform's construction counts toward activation), and `platform()` throws if nothing is installed. Only functions with no owning object read it: `perf.ts` `perfDebugEnabled`, `asset-sources.ts` precedence, `pi-session/agent-dir.ts` `cacheWarmingSetting`, `web-access/config.ts`, `team/index.ts` `isEnabled`, `subagents/enabled-models.ts`, `skills/utils.ts`, `tools/shell-sentinel-client.ts`, `l10n.ts` `t`, `mcp/mcp-auth-flow.ts` (`authenticate` and the auth provider's `onRedirect`), `voice/sidecar/output-channel.ts` `getVoiceOutputChannel`, and `PiRuntime`, a lazily created process singleton that reads it once in its constructor and hands the services to its folder runtimes by constructor. Worker threads (compass, usage stats) and the sentinel process never call it: nothing installs a platform there, so it throws. Tests get a default fake from `src/__mocks__/fake-platform.setup.ts` and reinstall one with `installFakePlatform` for specific values. `logger.ts` writes to an installed `LogSink`; the host installs its output channel at activation and the compass worker installs one that posts to the host.
- **Trust is asked per folder.** Every site that loads repository-authored input calls `TrustService.isTrusted(folderPath)` with the folder it acts for (a folder runtime's `cwd`, a nested session's `opts.cwd`, a `FolderTarget`, a workspace path argument); a site that loads only user-scope input does not ask. `onDidGrantTrust` delivers the granted folder paths; a listener either reloads only the listed folders (`PiRuntime` and `CompassService`, matching by `folderKey`) or re-reads `isTrusted` for its own folder on any grant. The VS Code implementation ignores the path and answers `workspace.isTrusted`, and a window grant fires with every open folder, or with `homeDirectory()` when none is open, so the extension behaves as a single window-wide gate. A site must never cache the answer across a grant.
- **Damocles-owned JSON config is written through `config/json-config-write.ts` only** (`~/.damocles/settings.json`, the project and local settings files, `~/.damocles/mcp.json`). `writeJsonConfig` serialises per path in process, then takes a `proper-lockfile` lock (`<file>.lock`, stale after 20 s against a 2 s heartbeat, a compromised lock fails the write), reads, applies the mutation, and returns without writing when the text is unchanged (a rewrite would only wake every watcher). Otherwise it removes any `<file>.<pid>.tmp` a crashed writer left (only a lock holder writes one, so any found under the lock is an orphan), writes a sibling temp file, `fsync`s it, and renames it over the target, retrying the rename on Windows for EPERM, EBUSY and EACCES. The `fsync` comes before the rename, or a power loss can leave the renamed target zero-length. The temp file gets `fileMode` when the caller passes one, on every write and not only on creation, so `~/.damocles/mcp.json` and the desktop secrets file are 0600 even when the user created them wider; otherwise it copies the existing file's mode. A lock that fails to release is logged and left to go stale, since the write already landed. Readers take no lock: the rename means they see the old file or the new one, never a partial one. A reader that holds the file open delays the rename on Windows, so poll-reading a config file in a loop slows every writer. A second writer that skips the helper reintroduces the lost update between windows.
- **The lock's stale takeover is not exclusive, and that residual risk is accepted.** `proper-lockfile` checks staleness and removes the lock directory in two steps, so two waiters that both see a stale lock can both remove it, the second removing the first's fresh lock; and a holder stalled for more than 20 s (a suspended laptop, a blocked event loop) is superseded while it still believes it holds the lock. The losing holder learns so only at its next heartbeat, up to 2 s later, and a rename before then overwrites the other writer's file. It needs a dead or stalled holder plus a second writer inside that window. Comparing the lock directory's mtime before the rename does not close it: the library does not expose the mtime it wrote, and two holders created by the race can carry the same mtime (each process's first lock is stamped with the next whole second plus 5 ms).
- **A symlinked config file is written through, and a repository's file is confined to its `.damocles`.** `writeJsonConfig` follows a symlink, dangling or not, and writes the file it names instead of replacing the link, so a user's `~/.damocles/settings.json` may live in a dotfiles repository. Project and local files pass `confineTo: <folder>/.damocles`: the write is refused unless the file resolves directly inside that directory with the directory itself not a symlink, so a repository cannot aim a permission rule or a settings save at another tool's file such as `.claude/settings.json`.
- **`proper-lockfile` has process-wide side effects at import**, in the extension host (shared with every other extension) and in Electron main: its `signal-exit@3` installs listeners for the exit signals and wraps `process.emit` and `process.reallyExit` to remove held locks on exit, and `graceful-fs` replaces the global `fs.close` and `fs.closeSync` with queued versions. Both are widely shipped and benign. `json-config-write.ts` and `session-store/session-lease.ts` import it; `auth-file.ts` must not, see "Agent auth store".
- **A host affordance the webview may lack is a `HostCapabilities` flag** (`Platform.capabilities`, type in `src/shared/types/messages.ts`). The `ready` handler posts `hostCapabilities` right after it re-posts pending dialogs and before any state, so the webview hides a missing affordance before rendering it. The webview store's defaults equal the VS Code values (`VSCODE_HOST_CAPABILITIES` in `messages.ts`, which the VS Code host sends as is: everything but `settingsSources` and `monaco`), so the extension's UI is the same before and after the message arrives; a new desktop-only or VS Code-only affordance adds a flag with a VS Code default that keeps the extension unchanged, never a host sniff in the webview. Each flag has a webview consumer; a flag nothing reads is removed. `hostSpeechExtensions` lives only here (the VS Code Speech conflict check in `voice/service.ts` reads it). Desktop builds its value in `src/desktop/main/platform/capabilities.ts` (`voice` is false on macOS, where an ad hoc signed app gets no microphone input).
- **Migrations to shared stores are additive only.** The memory database, the per-session memory injection databases, the Compass indexes and the `/stats` usage index are shared by every Damocles app on the machine, and those apps update on their own schedules. A release may add a column or a table; a removal or rename waits until no supported version reads it. An app that finds a store migrated past its own schema version (Compass also checks the extraction format, `isSchemaAhead` in `compass/migrations.ts`) opens it read only (`node:sqlite` `readOnly`), turns off every write path, keeps serving reads, and tells the user once per store per session through `notifySchemaAhead` (`schema-skew.ts`) to update. A newer app can also migrate a store while an older window holds it open, so three stores re-check before writing and switch to read only on the spot: memory reads `MAX(version)` inside each write-queue transaction, under the write lock (`MemoryWriteQueue`'s schema guard), and refuses that write with `MemoryReadOnlyError`, the one write that fails; the Compass worker re-checks at the start of every index write request (`fullBuild`, `incrementalUpdate`, `postprocess`, `mcp:build`) and of `webview:validation`, whose stale-file cleanup and FTS rebuild are writes; the usage worker re-checks `user_version` before it starts a scan. Compass and usage reopen the file read only. The Compass check runs per request, not per transaction, so a migration landing in the middle of a running build is caught at the next request. A per-session memory injection store is checked only when it is opened. Compass and the usage index open inside worker threads, which post `schemaAhead` for the host to show. Never let an older app migrate down, rebuild or write into a newer store.

## MCP client and config sources

- **The client layer is `@earendil-works/pi-mcp`; the host layer is Damocles' own** (`pi-session/mcp/`). pi-mcp speaks the protocol (stdio and streamable HTTP transports, JSON-RPC, OAuth discovery and grants). Damocles decides which servers run, shares one connection per server across every chat of a folder, exposes tools through ToolSearch, applies permissions, routes elicitation and drives the panel. Never load pi's built-in MCP extension (`pi-coding-agent/src/extensions/mcp/`): it keeps all server state on the extension instance, rebuilds it on every `session_start` and closes every connection on `session_shutdown`, and Damocles shares one extension instance across every panel of a folder, so a second panel would orphan the first panel's servers. There is no SSE transport; an SSE entry is an error row.
- **Sources and precedence**, lowest first: `codex`/`claude` (tie broken by `damocles.assetSourcePrecedence`), `pi` (`~/.pi/agent/mcp.json`, user scope), `pi-project` (`<folder>/.pi/mcp.json`, repo-authored, read only in a trusted folder), `claude-local`, `damocles`, `workspace` (`.mcp.json`), `damocles-local` (`SOURCE_ORDER_*` in `src/shared/types/mcp.ts`). The Claude Code, Codex and pi imports rank below `~/.damocles/mcp.json`; the project's `.mcp.json` ranks above it, and only `.damocles/mcp.local.json` ranks above `.mcp.json`. In an untrusted folder `demoteRepoAuthored` (`mcp-manager.ts`) folds the repository-authored sources (`workspace`, `damocles-local`) below every other source, keeping their relative order. Names equal after `[^A-Za-z0-9_]` → `_` (`mcpServerNamespaceKey`) are one server: the highest-ranked entry keeps it, and every other becomes a failed `nameCollision` row; the write path refuses such a name up front. ToolSearch groups by the descriptor's `serverName` namespace key, never by parsing a tool name.
- **Tool names are pi's** (`naming.ts` `createMcpToolName`, an exact port): `mcp__<server>__<tool>` with every character outside `[A-Za-z0-9_]` replaced by `_`, capped at 64, and an 8-character hash suffix on every colliding or over-long name. Resource `get_<slug>` tools use it too. The old prefix algorithm survives only as `legacyServerPrefixMap`, for migrations. Two migrations follow from the rename. Legacy `mcp__…` entries in `damocles.tools.disabled` that resolve to exactly one (server, tool) and differ from that tool's current name become `damocles.mcp.toolExposure[server][tool] = "off"` at the user or local scope they came from; an entry already equal to the current name stays, because `damocles.tools.disabled` matches current names exactly. Legacy prefixes are rebuilt over the enabled servers, as `legacyToCurrentToolNames` does, without an untrusted folder's repository-authored servers, and nothing moves while a config file is unreadable. Project-scope entries stay, because Damocles never writes the committed `.damocles/settings.json`, and those naming a renamed tool go into the notice below. Permission rules naming a renamed tool are rewritten (keeping the `(…)` part, idempotent, inside `writeJsonConfig`) only in `~/.damocles/settings.json`, `~/.damocles/settings.local.json` and a trusted folder's `.damocles/settings.local.json`; a file that cannot be rewritten is logged by path and error code and the rest carry on. The repo-committed `.damocles/settings.json`, hook matchers (whole tool names only, one entry per matcher) and agent `disallowed_tools` are never rewritten: their affected entries go to the folder's panels once as a `mcpRenamedToolRules` notice, remembered per file and rule, in workspace state for a file inside the folder and in global state for any other. Claude Code's settings files are neither rewritten nor listed: Claude Code keeps `-` in MCP tool names, so a rule there equal to a legacy Damocles name is correct for Claude Code. A legacy name that is also a current tool name is never renamed. The migration reruns when the folder's tools change and on a trust grant; a run counts as done for its trust state and rename map only once it completes.
- **stdio servers never receive the host environment.** The transport gets `inheritEnv: false` and `mcp/stdio-env.ts`, an exact port of the MCP SDK's `getDefaultEnvironment()` allowlist (the platform's process variables, no credentials), plus the server's own expanded `env` (`stdioEnvironment`; on Windows an own key that differs from a default only in case, such as `Path`, replaces it). The extension host holds provider keys in its environment; a server gets one only when its config names it. A failed stdio row shows the last `MCP_STDERR_TAIL_CHARS` (2048) of the server's stderr with control and bidi characters stripped, cut on a character boundary, and never for an untrusted row; stderr is not logged (`McpServerConnectError.stderrTail` is not enumerable and the error carries no `cause`, so even `%O` cannot print it).
- **Long tool results are cut in the middle** (`content.ts`, a port of pi's `limitMcpContent`/`truncateMiddle`): model-facing text over 20 KB (20480 bytes) becomes one block cut in the middle (`…N chars truncated…`) under a truncation warning, and the full text goes to `os.tmpdir()/damocles-mcp-<16 hex>.txt`, created exclusively (`wx`) with mode 0600, whose path is in the result so the agent can Read it. `PiRuntime.dispose` removes every such file the process wrote (`removeSavedMcpOutputs`).
- **The health check pings a supervised server only when it has no call in flight** (`lifecycle.ts`, `McpServerManager.answersPing`), because a server that handles one request at a time cannot answer mid-call and closing it kills the call. Any JSON-RPC reply proves the server alive, an error reply such as `-32601` from a server without `ping` included; only no reply within `HEALTH_PING_TIMEOUT_MS` (10 s, not the call timeout, because servers are pinged one after another) or a closed connection closes and reconnects it. A spec edited under the same name, including a trust grant flipping `trusted`, closes the old connection and clears its failure backoff in `doReconcile`, then connects at once.
- **Config values follow their file's format** (`mcp/config-value.ts`, `resolveMcpServerValues`). pi-format sources are pi's `~/.pi/agent/mcp.json` and `.pi/mcp.json` and Damocles' own `~/.damocles/mcp.json` and `.damocles/mcp.local.json`; there `env`, `headers`, `bearerToken` and `oauth.clientSecret` follow pi's `resolveConfigValue`: a value starting with `!` is a shell command whose trimmed stdout is the value, `$VAR` and `${VAR}` interpolate, `$$` and `$!` are escapes, and an unset or empty variable fails the server with an error naming the field and the variable. Other sources (`.mcp.json`, Claude, Codex) keep `${VAR}` and `$env:VAR` with a missing variable read as empty, and a leading `!` stays literal, because their formats do not define it. `bearerTokenEnv` naming an unset or empty variable fails the server in every source. A stdio server's `cwd` is resolved by the host when it builds the spec (`McpManager` `serverSpec`): relative to the folder for a folder-scoped entry and to the home directory for a user entry, and that directory is the default when `cwd` is absent, as pi's `createDefaultTransport` does, so no server inherits the host process's working directory. A legacy entry's `cwd` keeps `${VAR}`/`$env:VAR`; pi does not expand `cwd`, so a pi-format entry whose `cwd` holds `${` or `$env:` is an `invalidConfig` row naming `cwd`. A resolved header or `bearerToken` holding a line break or NUL, or an `env` value holding NUL, fails the server by field name, because Node and undici quote the offending value in their own errors. Values are expanded on every connect, so a rotated token applies on the next one. Commands run asynchronously (pi's own `spawnSync` would block the extension host): on Windows through pi's `getShellConfig(shellPath)` with the bash tool's `shellPath`, falling back to the default shell only when that shell cannot start, elsewhere in the default shell, with a 10 s timeout that kills the command's process tree. Command output and resolved values are credentials and are never logged; errors and `errorInfo` params carry only field names, variable names and source ids.
- **Commands never run from an untrusted folder's file.** `.pi/mcp.json` is repo-authored and loads only in a trusted window. A `!` value in `.damocles/mcp.local.json` of an untrusted folder fails the server (`commandUntrusted`) before any command runs; it is never run and never sent literally.
- **The two Damocles-owned MCP files are migrated once to pi's format** (`migrateOwnedMcpFile` in `mcp-config-write.ts`, run before each read: a lock-free read first, and the file's `writeJsonConfig` critical section only when something needs migrating, so a load never waits out a stale lock). `$env:NAME` becomes `${NAME}` (pi would read `$env` as a variable named `env`) and `oauth.redirectUri` becomes `oauth.callbackUrl`; no alias for `redirectUri` remains. The rewrite is idempotent and touches nothing else, so a bare `$`, `$$` or leading `!` in an old value now has pi's meaning. `.damocles/mcp.local.json` is migrated only in a trusted folder and written only inside its `.damocles` directory (`confineTo`). Damocles never rewrites `.mcp.json`, `.pi/mcp.json`, `~/.pi/agent/mcp.json` or another tool's file.
- **Remote OAuth runs on pi-mcp's flow over the keychain store** (`mcp-auth-flow.ts`, `mcp-oauth-provider.ts`, `mcp-auth.ts`). Credentials stay in the host secret store keyed by server name and URL; `createOAuthStateStore` maps the stored entry to pi-mcp's `McpOAuthState` and back, so sign-ins stored before pi-mcp keep working, and discovery results stay in memory. A connection never opens a browser: it sends the stored token and refreshes after a 401 through `adaptOAuthProvider`; with no refresh token, or on an `insufficient_scope` challenge (a refresh keeps the granted scope), it throws `McpOAuthAuthorizationRequiredError` and the server shows as needing authentication (`hasScopeChallenge` marks the step-up). A connection's store never changes the stored PKCE verifier or CSRF state, so a background refresh cannot clobber a sign-in in progress. The Authenticate action runs `authorizeMcp` with the configured scope (on a step-up, also the granted and the challenged scopes, skipping refresh). Dynamic registration sends `client_name: oauth.clientName ?? 'Damocles'`. `client_credentials` stays a Damocles `AuthProvider`: discovery plus a token POST, because pi-mcp has no such grant. Every OAuth request goes through `createOAuthFetch` (`mcp-oauth-provider.ts`): both `authorizeMcp` calls of a sign-in and the connection refresh (pi-mcp threads `OAuthFlowOptions.fetch` and the refresh context's `fetch` into protected-resource and authorization-server discovery, registration and the token endpoint), Damocles' own discovery and metadata-URL fetch, the `client_credentials` registration and token POST, and revocation. It refuses a URL that is not https or loopback http with `OAuthInsecureEndpointError` before anything is sent, so discovered endpoints (`authorization_servers[0]`, `registration_endpoint`) are held to the rule too. It never follows a redirect, because a followed 307 re-sends the body (code, client secret) to a URL the check never saw; the 3xx reaches pi-mcp as a failed response. It bounds each request, body included, by 15 s on top of the caller's signal (revocation keeps its own 10 s). The browser's authorization URL must be https or loopback http as well. A connection never registers a client: its provider's `clientInformation()` throws `McpOAuthAuthorizationRequiredError` when no client is configured or stored, and pi-mcp asks for it right before registering, on the first run and on its `invalid_client` retry alike. The keychain store is safe for several connections of one identity: a save whose tokens or client equal what that store last loaded keeps what is stored now, because pi-mcp's provider saves what it loaded outside the identity lock. Server error text is flattened and capped before it reaches a message, and the failure log lines (connect, ping, list, transport, OAuth) get `failureForLog` (`server-manager.ts`): an HTTP failure logs its status, a non-JSON server reply fixed text and an OAuthError its code, never response-body text or server output. A connect error decides its log text from the error it wraps (`McpServerConnectError.logText`), because its message copies that error's server text. A stored credential blob that fails to parse is logged without the parse error, which quotes the blob.
- **Damocles enforces three OAuth rules that the published pi-mcp 0.99.2 lacks** (pi's unreleased source has them; drop each local copy once a pi-mcp release ships it). RFC 9207: `signInWithBrowser` captures the discovery pi-mcp used for the redirect right after the first `authorizeMcp` returns `REDIRECT` (failing closed if there is none), and after the callback compares the redirect's `iss` with that copy's issuer, rejecting a mismatch, or a missing `iss` when the metadata sets `authorization_response_iss_parameter_supported`; the code exchange runs on the provider with that copy pinned (`withDiscovery`), so the check and the exchange see one authorization server even if another connection of the same identity dropped the stored discovery during the callback wait. `oauth.authServerMetadataUrl`: `discoverAuthorizationServer` fetches the configured document (trusted as configured, so its issuer is not checked, as in pi) and primes the provider's discovery state, which pi-mcp's flow uses instead of discovering; sign-in, connection refresh, `client_credentials` and revocation all go through it. `stepUpScope` is a local port. Known upstream issues in pi-mcp 0.99.2, fixed only in pi's unreleased source and not worked around here: token and registration responses with an empty optional field such as `"scope": ""` fail to parse (pi #10266), so such a server cannot sign in; `expires_in: null` marks an authorization_code token as already expired (Damocles' own `client_credentials` grant reads it as no expiry); `McpClient.listTools()`/`listResources()` page internally and fail on a server that ends pagination with `nextCursor: null` (invalid cursor) or a repeated `""` (duplicate cursor), so such a server fails to connect on tools, or connects without resources; and `adaptOAuthProvider`'s own step-up requests only the challenged scopes (Damocles never reaches it, because a connection throws on `insufficient_scope` before delegating).

- **Per-tool exposure: Off, On (deferred), Always loaded (`direct`).** Each MCP descriptor carries `exposure`, `exposureSource` and `configExposure`. The manager sets the config value (`mcp/exposure.ts` `configToolExposure`: the server's exact `toolExposure` key, then the first matching `*` pattern in file order, then the server's `exposure`, then deferred; pi's `hidden` reads as off and `codemode`/`codemode-deferred` as deferred). The pattern matcher treats every character but `*` literally, is anchored at both ends and runs in linear time (each literal segment found once, leftmost, by KMP); never swap in a generated regex, which backtracks. `FolderMcpView` overlays `damocles.mcp.toolExposure`, resolved per tool from `inspect()`: local over project over user, project and local only in a trusted folder, never from the host's merged value, whose object merge differs between hosts. The overlay lives in the view, not the manager, because the user manager serves every folder and trust is per folder. The panel's three-way control writes one entry at one scope (`mcpSetToolExposure`, `toolExposureMapForScope`): it reads that scope's map from `inspect()`, sets or removes the entry, and removes it when the scopes below and the config already give the chosen value. The scopes offered are those the host store can write in that folder (`McpManager.toolExposureScopes`: User; Project in a trusted folder with a project layer whose write target, the default project (`defaultProjectPath`), is trusted too, because the store has no folder argument and desktop refuses an untrusted project; Local where the host keeps a local file, i.e. desktop). Renaming a `~/.damocles/mcp.json` server moves its `damocles.mcp.toolExposure` key at every scope, project included. The panel's writes run one at a time on one promise chain, each `inspect()` read and `update()` write inside it, so a quick second change never starts from a map without the first; a write that a higher scope's entry for the tool still overrides posts a notice naming that scope. `PiRuntime` listens on the setting itself, so a change from any writer (the panel, a `settings.json` edit, Settings Sync, another window, the desktop settings editor) runs every folder's `refreshActiveTools`, which re-applies each session's active set, republishes ToolSearch and re-sends that panel's MCP status; the handler has no refresh path of its own and sends status only to the requesting panel, since a failed or unchanged write fires no change event.
- **The first prompt of a session waits, up to 10 s, only for servers with Always-loaded tools that are still connecting** (`mcp/startup-wait.ts`, pi's startup wait). It runs in the Damocles extension's `before_agent_start` handler through the panel's `waitForAlwaysLoadedMcp(sessionId)`, so the shared extension instance holds no record of who waited; the panel keys "already waited" by session id. A Stop, a reset (New chat) or a resume switch ends it and sends no model request: pi 0.99.2's `before_agent_start` cannot cancel a prompt and `AgentSession.abort()` is a no-op until `_runAgentPrompt` sets `_isAgentRunActive` (which then clears `_agentRunAbortRequested`, `agent-session.js:1321-1326`), so each of them bumps `abortEpoch` and aborts the wait (`stopPromptBeforeRun`, synchronously in `setResumeSession`), and `sendMessage`'s `preflightResult('started')`, which pi calls synchronously just before `_runAgentPrompt` (`:1568-1569`), throws when the epoch moved or the session was replaced. `prompt()` then rejects before the run exists and the message goes back to the composer. The wait fails soft: a throw from it is logged and the prompt is still built. Its notice is an ordinary `notification` (plural for several servers, and a second one naming the servers still connecting when the 10 s pass), and a server that connects later has its tools active from the next turn. Eager connects emit tools-changed once the batch settles, so a slow sibling can hold the wait to the cap.

## MCP OAuth callback server

- **Damocles keeps its own callback server instead of pi-mcp's `OAuthCallbackServer`,** because the rules below (port reuse across sign-ins, strict ports, CSRF state reservation) live here. `oauth.callbackUrl` with a port binds that port strictly, and the redirect URI is sent exactly as written, because servers compare it as a string; `oauth.callbackPort` binds strictly on the callback URL's host and path or on `127.0.0.1/callback`; with neither, a pre-registered client (`clientId`) binds `MCP_OAUTH_CALLBACK_PORT` (default 19876) strictly, and a dynamically registered one binds non-strictly, trying the port of its stored client's registered redirect URI first. A `localhost` callback binds `127.0.0.1`. The callback hands `code` and `iss` to the flow.
- **The loopback callback server lives only while an authorization is pending or reserved** (`mcp/mcp-callback-server.ts`, RFC 8252). It closes when the last one settles (success, error redirect, cancel, `CALLBACK_TIMEOUT_MS`), and `ensureCallbackServer` re-checks after its serialized bind, so a flow that settled mid-bind leaves nothing listening. The bound port, host and path survive the close: a settled flow's token exchange still sends the redirect URI it was authorized with, and the next flow rebinds. A non-strict flow first rebinds the port of the stored client's redirect URI, else the port the previous non-strict flow was given (`lastEphemeralPort`, kept for the process lifetime, through `stopCallbackServer` too), and falls back to an OS-assigned port only on `EADDRINUSE`, because a dynamically registered client is registered with its redirect URI and a changed port discards the client and its tokens on the next sign-in. On a strict (pre-registered) port, `EADDRINUSE` names the likely cause, another Damocles window completing a login for that server, before the config fields and `MCP_OAUTH_CALLBACK_PORT`. The security headers and the state-keyed CSRF lookup are unchanged; an unknown state settles nothing and closes nothing.

## Desktop host

- **Trust is per folder, by exact path** (`src/desktop/main/trust-store.ts`). An allowlist of absolute folder paths plus a schema version lives in `<userData>/trusted-folders.json` and matches only on `folderKey` equality: a trusted parent never trusts a child, and a trusted child never trusts its parent. An unreadable or unknown-schema allowlist trusts nothing. Adding an untrusted project asks once through a native dialog (default and cancel: Don't Trust). The folder stays untrusted until the user grants trust, and a decline persists nothing. A grant writes the allowlist atomically, then trusts the folder in memory, fires `onDidGrantTrust([folder])` and takes effect with no restart. VS Code's trust database is separate, so a folder trusted there still prompts on desktop.
- **Desktop stores change memory only after their file write lands** (`trust-store.ts`, `projects.ts`, `platform/key-value-state.ts`, `platform/secrets-store.ts`). Each builds the next state inside the `writeJsonConfig` mutation, from memory as it stands once the earlier writes to that file have landed, and commits it and fires its listeners after the write resolves. A write that fails changes nothing, so memory and disk never disagree for the rest of the run and a retry is not a no-op; a folder trusted in memory but not on disk would never fire the grant and would be untrusted again after a restart.
- **Desktop secrets are encrypted with the OS credential store, or kept in memory and the user told** (`platform/secrets-store.ts`, `src/core/volatile-secrets-notice.ts`). `SecretsStore.isPersistent` is false when safeStorage cannot encrypt (no encryption, or Linux `basic_text`); `withVolatileSecretsNotice` then warns once per run, on the first secret stored, that it lasts only until restart, with an action that opens the README's "Desktop credential storage". An entry that fails to decrypt (a locked keyring, a denied keychain) keeps its ciphertext in the file across later writes and is dropped only when its key is stored again or deleted, because a keyring unavailable for one run must not cost the user every saved token.
- **The renderer is untrusted.** Every WebContents (the window, each tab and page view, and the pane view) runs `contextIsolation: true`, `nodeIntegration: false` and `sandbox: true`, with `app.enableSandbox()`; a chat tab or browser page reaches main only through the panel preload's four-method `damoclesBridge`, the window page only through `damoclesShell` and the pane view only through `damoclesPane`. `app.on('web-contents-created')` hardens every WebContents: popups are always denied (http/https go to `ShellService.openExternal`, which accepts only http and https and opens the canonical href); `will-navigate` and `will-redirect` are cancelled for anything but the exact `app://` page main loaded; `will-attach-webview` is prevented. Permissions are denied by default, media and notifications included. The single exception is `clipboard-sanitized-write` (`navigator.clipboard.writeText`, for the copy buttons), granted only to a registered panel view's own webContents, main frame, exact `app://damocles` origin, through one predicate shared by the request and check handlers; `clipboard-read` stays denied, and device permissions are denied. The `app://` handler serves only files that stay inside `dist/webview` or `dist/desktop-shell` after decoding, resolution and realpath (plus the single app icon file), and in-memory panel pages by exact panelId plus the shell and pane pages at their exact paths; anything else is a 404, including the built `index.html` files, which carry no CSP (every page is generated in memory under one). A script response carries its own `default-src 'none'; script-src app://damocles`, because a worker does not inherit its page's CSP. Panel IPC uses fixed channel names registered on each view's own `webContents.ipc`, which only that view's messages reach, so the renderer never carries its panel id (a process argument would be wrong once Chromium reuses a renderer process across same-site views); each handler still accepts a message only from that view's webContents, main frame, on its own `app://` page URL, and JSON-normalizes and bounds the payload before core sees it. A refused `init` answers null and the preload asks again on its next call. `EditorService` never launches a file: `openFile`, `showDiff` and `openUntitled` show it in a chat tab's Monaco overlay, and `showMarkdownPreview` reveals it in the file manager. `ShellService.openFolder` opens only a folder, on both hosts, and `openExternal` opens only http and https in the canonical form on both hosts (`src/core/web-url.ts`), so a model-named path or a third-party URL can never launch a local handler.
- **The login shell environment is merged once, before anything spawns or connects** (`src/desktop/main/shell-env.ts`). On macOS and Linux the app runs `$SHELL -l -i -c` once, in its own process group with a 10 s deadline that kills the group, and reads the environment its own binary prints (running as Node) between random markers, so profile noise on stdout cannot corrupt it. Stdout is decoded as UTF-8 across reads (a non-ASCII `HOME` or `PATH` split between two reads stays whole), its 4 MB cap counts bytes, and the environment is taken as soon as the closing marker arrives, so a profile's background job that keeps stdout open neither delays the launch nor is killed. The command holds only the binary path and the marker; no environment value is ever interpolated into it. A failure is logged and the launch environment kept. Windows GUI apps inherit the user's environment and skip the merge. Then `probeGit` checks `git` once: its absence is one localized warning, and `setCheckpointGitAvailability` turns checkpoints and rewind off with that reason instead of failing per operation. The extension never sets it, so its checkpoints probe `git --version` per session as before.
- **A quit resumes on a new task after its prevented `before-quit`** (`src/desktop/main/index.ts`, `e2e/desktop/quit.spec.ts`). `before-quit` is prevented while the core disposes, bounded at 10 s, and then `app.quit()` runs again. Electron's `Browser::Quit` stores the handler's prevented result only after the handler returns, and a quit started in native code (Cmd+Q, the Dock, logout, CDP `Browser.close`) runs the handler as the outermost JavaScript frame, so its microtasks run first. A dispose that settles in microtasks would then call `app.quit()` inside the first quit, which overwrites it. The window closes, `window-all-closed` fires instead of `will-quit`, and on macOS the app keeps running in the Dock, so the second `app.quit()` waits for `setImmediate`. The log records each step (`[shutdown] quitting`, `[window] closed`, `[shutdown] will-quit`), and the log sink closes at `will-quit`.
- **Main-process failures reach the log, never Electron's error dialog** (`src/desktop/main/process-errors.ts`, `index.ts`). An uncaught exception or unhandled rejection in main is logged, as VS Code's main process does. The stores are read after the log sink is installed and inside the startup error handling, so what they skip is logged and a store that cannot be read ends in the startup error dialog. The log sink reports its own write failures once on stderr (a failed rotation keeps appending, a failed append drops that batch). A tab or window page that crashes more than three times in a minute is left dead and the user is told: a toast with Reload Tab for a tab, a native dialog with Reload Window for the window page, whose own toasts could not render. A toast raised before the window exists, while its page loads or while it is closed waits in main, and its timeout starts once a page shows it. `app.setName` runs before any path is read: `damocles` when packaged, `damocles-dev` unpackaged, so a dev build shares userData, the safeStorage key and the single-instance lock neither with every unpackaged Electron app nor with an installed Damocles. For the same reason the unpackaged app's AppUserModelID is `io.github.aizenvoltprime.damocles.dev`. Electron's notification support creates a Start Menu shortcut to the running binary under that ID, and Windows takes the taskbar icon and name for the ID from it, so the unpackaged app runs on a branded copy of the Electron runtime, never the downloaded one. `dev:desktop` and `test:desktop` run `scripts/brand-dev-electron.mjs`, which copies `node_modules/electron/dist` to `dist-damocles-dev` with Damocles' icon and the product name "Damocles Dev" in `electron.exe`, as electron-builder brands `Damocles.exe`, and redoes it only when the icon or the downloaded binary changed. The copy keeps the name `electron.exe`, because Electron reports `app.isPackaged` for any other executable name, and lives in its own folder, because the shell caches an icon by path. `scripts/launch-desktop.mjs` and `playwright.desktop.config.ts` select it with Electron's `ELECTRON_OVERRIDE_DIST_PATH` (`devElectronDist` in `scripts/dev-electron-binary.mjs`), never Playwright's `executablePath`, which drops the preload Playwright adds to the app it launches. A host reload (`core-host.ts`) joins a reload already running, does nothing once quitting began, and still starts a new core when the old one fails to dispose.
- **Closing tabs while their states are retained leaves the persisted selection and panes alone** (`views.ts`). Quit, window close and a host reload close every tab in core's order, and each tab its pages; a closed selected tab then shows no neighbour and a closed page leaves its tab's saved pane as it was, so the next launch or the reopened window restores the tab the user had selected with its pages. `PanelViews.restore` puts every saved tab in the strip and selects the saved one before any loads, and `openInitialTabs` loads the selected tab first; `create` never selects or focuses a restored tab, so the selection does not pass through the others and a quit during the restore keeps it. A tab closed before its turn to load is skipped. The other tabs lay out when first selected, because Chromium sends a view's size to its page only once the view has been visible (a never-shown view's page reports a 0×0 viewport whatever its bounds), which is how browsers and VS Code restore background tabs.
- **One process-wide network dispatcher, installed before the first connection** (`src/desktop/main/network/`). `installCaCertificates` sets Node's default CA list to the bundled roots plus the OS store (`tls.getCACertificates('system')`, which returns the OS store on Electron 44) plus the `NODE_EXTRA_CA_CERTS` file, read after the login shell merge and deduplicated by fingerprint. In the packaged app Electron strips an inherited `NODE_EXTRA_CA_CERTS` (see "Desktop packaging and updates", fuses). `installProxyDispatcher` installs an undici dispatcher with `setGlobalDispatcher`, plus undici's `fetch`, as pi's CLI `configureHttpDispatcher` does, and with its settings (pi's `httpIdleTimeoutMs`, `allowH2: false`, CONNECT tunnels, the ignored `error` listener). pi's library entry never calls `configureHttpDispatcher` (only its CLI `main()`, `rpc-entry` and interactive mode do), and nothing in the desktop process may, or it would replace this one. When `HTTP(S)_PROXY` is set it governs every origin through undici's `EnvHttpProxyAgent` (with `NO_PROXY`), because Chromium ignores those variables on Windows and macOS. Otherwise each origin asks `session.resolveProxy`, which applies the OS settings, PAC and WPAD, and takes the first route undici supports (`PROXY`, `HTTPS`, `SOCKS5`, `DIRECT`); `SOCKS` (v4) and `QUIC` fall back with a logged reason. Answers are cached per origin for 60 s, dropped once expired at the next lookup, and cleared on `powerMonitor` `resume`, because Electron exposes no network-change event. Logs name a proxy by scheme, host and port only, never its credentials. `safe-fetch.ts` validates every hop before it calls `fetch`, so its SSRF guard applies unchanged through a proxy. NTLM and Kerberos proxy authentication are not supported.

- **The shell renderer is the window's own page and reaches main only through `window.damoclesShell`** (`src/desktop/main/shell.ts`, `src/desktop/preload/shell.ts`, `shell-channels.ts`). Main generates `app://damocles/shell/index.html` on every load with a fresh script nonce (CSP `default-src 'none'`, nonce `script-src`, no inline handlers) around the built `dist/desktop-shell` assets. The shell preload exposes project, tab, pane toggle, content-bounds and toast calls and has no access to the panel or pane channels. Every `damocles:shell:*` handler accepts a call only from the window's own webContents, main frame, on the exact shell URL (`isPanelSender`, read at call time), and resolves every id against main's own lists; ids and toast actions are length bounded, a move index must be an integer, and content bounds must be finite, non-negative and below 100000 CSS px before main converts them to DIPs and positions the active tab view.
- **Browser pages live only in their chat tab's side pane** (`src/desktop/main/views.ts`, `pane.ts`, `pane-layout.ts`). There are no top-level browser tabs: `views.create` refuses a page whose `PanelOptions.owner` is not an open chat tab. A page is a panel view with the same panel preload and `damoclesBridge`, its own channel pair with the same sender check, the same navigation, popup and permission hardening, and the core-assembled screencast HTML with `localResourceRoots: []` and its unchanged CSP. Host messages go out through `webContents.send` (structured clone, so screencast frame buffers arrive intact); webview messages are JSON-normalized and bounded; the page renderer's `setState` persists nothing. The page script picks `acquireVsCodeApi` or `window.damoclesBridge` at load (`browser-webview-script.ts`).
- **The pane chrome is one trusted pane view per window, reaching main only through `window.damoclesPane`** (`src/desktop/main/pane.ts`, `src/desktop/preload/pane.ts`, `pane-channels.ts`). Main generates `app://damocles/pane/index.html` like the shell page, around `dist/desktop-shell/assets/pane.js` and `pane.css`, with CSP `default-src 'none'`, a nonce `script-src`, `img-src data:` only (a favicon is a size-capped data: URL, so the chrome never fetches from the network) and `base-uri`/`form-action 'none'`. The view is transparent so the overlay scrim shows the chat, and it is not a registered panel view, so it holds no permission. Its `damocles:pane:*` channels are registered on its own `webContents.ipc`; each accepts a call only from that webContents, main frame, on the exact pane URL (`isPanelSender`, read at call time), bounds ids to 200 characters, flags to booleans and widths to finite numbers in 0..100000, and resolves every page id among the selected chat tab's pages. The pane never reaches core directly: main turns each action into the webview message the page's own toolbar would post (`navigate`, `goBack`, `goForward`, `reload`, `pickElement`, `openDevTools`), so core's handlers and `isNavigableUrl` stay the authority. `navigate` first trims, bounds to 8192 characters, adds `https://` to a bare host and refuses what `isNavigableUrl` refuses; Open in system browser takes only a page id and passes the URL main observed, http and https only, to `ShellService.openExternal`. What the pane shows about a page (URL, loading, back and forward, picking) comes from the host messages core posts to the page, its title from `setTitle` and its favicon from `setIcon`.
- **Main is the pane's layout authority** (`pane-layout.ts`, `views.ts`). One pure function turns the shell's content rectangle, the pane width shared by every tab and the tab's open and maximized flags into the chat, pane and page view bounds: collapsed, split, overlay when the area is narrower than both minimum widths (the pane covers the chat and leaves a scrim strip), and maximized. `layout()` applies all three bounds in one synchronous pass. A persisted width is clamped to the window and never rewritten by the clamp; a divider request is clamped and answered with main's numbers, and only a committed one is saved. Views stack chat < pane < active page, restacked on every selection and pane change, since `addChildView` puts a newly created chat view on top.
- **No page or pane view takes focus from main, and no page outlives its chat tab** (`views.ts`, `index.ts`). Create, reveal, restore and selection never focus a page view; collapsing the pane or closing its last page while it holds focus returns focus to the chat, and selecting a tab whose pane is maximized focuses the pane. A new page selects itself in its chat's pane and opens it (a restore keeps the saved state); closing the last page collapses it. Closing a chat tab closes every page it owns, and core closes the chat's pages as well, including a failed subagent's kept tabs, and refuses any that register later. Close Tab with focus in the pane closes the active page instead of the chat tab. F6 and Shift+F6 cycle focus through the tab strip, the chat and the shown pane, because Tab cannot leave a WebContents. The pane toggle (top bar button and `CmdOrCtrl+Shift+B`, with no Alt because Windows AltGr is Ctrl+Alt) and New page do nothing while `damocles.browser.enabled` is off, and the pane hides.
- **`panels.json` holds the panes** (`panel-state-store.ts`). Each chat tab's entry carries its pane (open, maximized, page addresses in pane order, active index), and `paneWidth` is shared by every tab. Every field is validated on read, and what is dropped (a non-chat entry, a malformed address or width) is logged. A restart reopens every saved page into its chat's pane through `BrowserService.restoreChatPages`, which honours `damocles.browser.enabled` and refuses a non-navigable address per page.
- **Desktop settings come from three files, and project and local apply only for a trusted default project** (`src/desktop/main/platform/settings-store.ts`). `damocles.*` keys sit flat beside `permissions` in user `~/.damocles/settings.json` (always), project `<folder>/.damocles/settings.json` and local `<folder>/.damocles/settings.local.json`. Precedence is local over project over user over the `package.json` default, and `get` merges a plain-object value key by key, recursively, across those layers exactly as VS Code does (`mergeSettingValues` in `src/core/config/settings-file.ts`; the fake platform and the vscode mock merge the same way), while `inspect` reports each layer as written. `SettingsStore` has no folder argument, so project and local are read from the registry's default project (`defaultProjectPath`, the rule `WorkspaceFolderRegistry.defaultTarget()` applies), which is how VS Code's workspace scope applies to the whole window; changing the default project re-reads them. `inspect` reports only the layers that apply: an untrusted default project, no open project, or a user-only key leaves `projectValue` and `localValue` absent, because `updateConfigAtEffectiveScope` picks its write target from `inspect` and would otherwise route a settings toggle into a refused or untrusted file (YOLO and the permission mode would become unchangeable). That is the `SettingInspection` contract on both hosts: a store reports `localValue` only where `update(key, value, 'local')` can write it, so a toggle of a key the local file supplies writes the local file however many projects are open. VS Code reports and writes a `WorkspaceFolder` value only for a resource, which its store never passes, so there `localValue` is always absent. `update` to project or local rejects for a user-only key, an untrusted default project and no open project. Every write goes through `writeJsonConfig`, project and local ones with `confineTo` their `.damocles`. A file that stops parsing (a trailing comma, a `//` comment) keeps serving the layer it last parsed, and the user is told once, naming the file, until it parses again; an existing file read as empty while it held settings is taken as an editor mid-write and read again after 300 ms before it counts as empty; an unreadable path (EACCES, a directory) keeps the last layer too. Without that, one typo read as `{}` flipped every setting in the file to its default and back, `permissionMode` and tool availability included. The user file and every open project's two files are watched; an external edit, a trust grant, a default-project change and a project list change fire `onDidChange` for each key whose layers changed. `search.useIgnoreFiles`, `useGlobalIgnoreFiles` and `useParentIgnoreFiles` default to VS Code's defaults (true), which a user or project value overrides as in VS Code. A `damocles.*` key in a `.damocles` file affects desktop only; the extension keeps VS Code's settings. The settings panel shows the file behind each value a project or local file supplies (`settingSources` on `settingsUpdate`, `SettingsStore.scopeFile`), which is the default project's file in every tab, including a tab on another project, because that is what applies.
- **Project and local files never supply a user-only key** (`src/core/config/contributed-configuration.ts`). The set is derived from `package.json` at load, never hardcoded: `capabilities.untrustedWorkspaces.restrictedConfigurations` plus every key whose `scope` is `machine` or `application` (VS Code likewise never reads those from workspace settings; `machine-overridable` keys may come from a project). An entry that is such a key, a prefix of one or under one (`"damocles.compass": { "enabled": true }`) is dropped and logged, trusted or not. Known residual, as in VS Code: `damocles.browser.devToolsPort` is neither restricted nor machine scoped, so a trusted project may turn on the unauthenticated DevTools port.
- **Host dialogs render in a chat tab's webview** (`src/core/chat-panel/webview-prompts.ts`). Electron has no native text or list prompt, so desktop `DialogService.inputBox` and `quickPick` post `extensionUiRequest` (`password`, `items`) to the last active chat tab, or open a chat tab on the default project and wait for its `ready` when none is open (there is no shell-rendered prompt). A tab still being opened or restored counts as open: `PanelManager` registers a panel only once its session exists, well after its webview shows its input box, so `promptTarget` waits for the panels in `opening` before it opens one, which also makes prompts asked at once share one new tab. Request ids carry the `host-prompt:` prefix, distinct from PiSession's `<sessionId>:ui:<n>`, and `extensionUiResponse` is offered to `WebviewPrompts` first. An answer counts only from the panel the prompt was posted to, and a quick pick answer only when it names an offered item. An abort posts `extensionUiCancel` and resolves undefined; the panel closing resolves undefined; a webview restart re-posts the panel's pending prompts on `ready`. Answers are never logged: they carry API keys and pasted OAuth redirect URLs. The VS Code host keeps `showInputBox` and `showQuickPick`.
- **Desktop editors render with Monaco inside the chat tab that asked, and their content travels in messages** (`monaco` capability). Core threads the originating panel into every `EditorService` call (`OpenFileOptions.panelId`, `DiffRequest.panelId`, `openUntitled` options; each `PermissionHandler` carries its panel's id into `DiffManager`), and the VS Code host ignores both fields. The host reads the file, applies the size limit and binary check, decodes a UTF-8 or UTF-16 byte order mark as VS Code does, and posts `editorShowDiff` / `editorOpenFile` with an `EditorDocument`; the renderer never reads a file. `readText` reads the file under the same rules and rejects a missing, binary or oversized one, because desktop holds no unsaved editor text. A proposal diff carries `approvalId`, the `toolUseId` of the pending `requestPermission`: the permission prompt stays the only thing that decides, and closing the overlay decides nothing. Core closes the `DiffView` on approve, reject, abort, subagent auto-approve and panel dispose (`approval-manager.ts`, `subagent-manager.ts`, `DiffManager.dispose`), which posts `editorCloseView`.
- **Only the desktop chat panel page allows workers, and only from `app://`.** Monaco's editor and JSON workers are module workers served from `dist/webview/assets/monaco-*`, and a worker cannot carry a nonce, so `script-src` does not cover it. The worker itself runs under the policy on its script response (`default-src 'none'; script-src app://damocles`), not the page's. `PanelHost.workerSrc` is the one extension point: core appends `worker-src <value>;` to the chat panel CSP only when the host sets it. The desktop chat tab sets `app://damocles/webview/assets/` (`CHAT_WORKER_SRC` in `src/desktop/main/views.ts`); no `blob:`, no new `font-src` (the codicon font is served from `app://`, already in `font-src`) and no new `style-src` (it already allows `'unsafe-inline'`). The shell page, the pane page, a browser page and every VS Code host set nothing, and `chat-panel-csp.test.ts` pins the VS Code chat panel and sidebar CSP byte for byte.
- **The settings JSON editor saves only text that the settings reader parses, and never overwrites a file it cannot parse** (`src/core/chat-panel/settings-file-editor.ts`). It edits the three files `SettingsStore.scopeFile` names; project and local only for a trusted default project (`defaultProjectPath`, the store's own rule), checked again at save. `parseSettingsText` (`src/core/config/settings-file.ts`) is the single parser the desktop store, the editor, the permission rule writer (`syncPermissionRulesToSettings`) and the permission rule reader (`readPermissionsFromPath`, for all eight settings files, `.claude` included) share; it ignores a leading BOM, so a rule the store applies is never one the evaluator drops. The permission rule writer refuses a file that does not parse the same way, inside the lock, and the user is told the rule was not saved. A save runs inside `writeJsonConfig`'s lock and refuses, in order: a file on disk that does not parse, a file whose sha256 no longer equals the version the editor loaded (a conflict, which carries the file it read under the lock as `onDisk`), and text that does not parse (the parser's message goes back to the editor); otherwise it writes the user's text verbatim. After a conflict the editor keeps the user's text and offers Compare (an editable diff against `onDisk`, saved against its version) and Overwrite (a save against its version, after a confirmation); nothing discards the text without the user choosing so. A save is refused as a conflict with no `onDisk` when the default project moved after the load, and the editor offers a reload. A path that exists but cannot be read (a directory, no permission) is answered with `unavailable`/`unreadable`, so the editor never waits on it. Each panel that loaded a scope gets `settingsFileChanged` when that file's version changes on disk, never for its own save: the save records the version it writes before writing, and a watcher event that reads that version is ignored. The watchers are disposed with the panel. The Settings panel learns which files apply from `getSettingsFileAvailability`, which reads no file, and the host posts `settingsFileAvailability` again to each panel that asked on a trust grant or a project change. An open editor is never replaced by another request: the same scope keeps it as it is, and another scope asks before discarding unsaved edits. The editor's schema (`src/shared/generated/settings-schema.json`) is generated from `package.json` plus `permissions` by `scripts/generate-settings-schema.mjs`: unknown keys are flagged, and in the project variant every user-only key is flagged with a message.
- **A directory that appears under a desktop recursive watch is watched before it is listed, and what it holds is reported as created** (`src/desktop/main/platform/file-watcher-factory.ts`). On Linux the recursive watch is `startInotifyTree`, one non-recursive `fs.watch` per directory, never `@parcel/watcher`'s inotify backend: that backend adds a watch to a new directory without listing it, so a directory created with its contents in one go, or moved in, loses those files, and its subdirectories are never watched (parcel-bundler/watcher#97, #243). inotify(7) prescribes the order the tree follows: watch the new directory, then list it. The tree reports a change only against what it already reported, so a file both the listing and an event see is created once. On Windows and macOS parcel's native recursive watch sees later writes, but a directory moved in still arrives as a single create, so `startParcel` lists it and reports what the batch did not. Both skip `RECURSIVE_IGNORE`. The startup scan is asynchronous and stats directories only, so a large workspace never blocks the main process.
- **`FileWatcherFactory.onDidRenameFiles` never fires on desktop.** The app renames no files itself, so a rename on disk reaches watchers as a delete plus a create, exactly as VS Code reports a rename made outside its explorer.
- **A watcher glob is relative, on both hosts and in the fake** (`src/platform/file-watcher.ts`): `watch(base, glob)` matches paths relative to `base`, and `watchWorkspace(glob)` matches paths relative to each open folder and follows folders being added and removed. VS Code gets one `RelativePattern` per workspace folder, because a string glob there is matched against the absolute path and a glob without a leading `**/` would never fire. The fake platform's `fire*` reaches listeners only for a path the glob matches, so a core test cannot pass with a glob that never fires.
- **Desktop watchers never throw and never die quietly** (`platform/file-watcher-factory.ts`). `watch()` logs a watch it cannot start and returns a watcher that fires nothing; every listener runs even when another throws (`platform/emitter.ts`, as VS Code's `Emitter`), which the settings store, the key-value state and localization use too. A watched root that is deleted (a `git clean` removing `.damocles`) reports its files deleted, closes its watch and waits on its nearest ancestor again, and a recreated root replays what it holds; on Windows the closed watch also ends the endless rename events Node reports for a deleted watched directory. A recursive root is watched at its real path, because FSEvents reports real paths (`/var` is `/private/var`), and events map back onto the path the caller gave. A non-recursive root reports a burst of raw events once per file after 75 ms, as VS Code's non-recursive watcher does.

## Desktop packaging and updates

- **The packaged layout comes from `app.isPackaged`, never from a path guess** (`src/desktop/main/platform/app-paths.ts`, `app-info.ts`). Packaged, `resourceRoot` is `app.getAppPath()` (`resources/app.asar`), `unpackedRoot` is its `app.asar.unpacked` sibling, the three worker entries resolve under `unpackedRoot/dist`, and `AppInfo.version` is `app.getVersion()`. Unpackaged (`electron dist/desktop/main.js` from a checkout), all three roots are the repo root and the version comes from the repo `package.json`, because `app.getVersion()` then reports Electron's version. `package.json` `main` stays the VS Code entry; electron-builder gives the app its own with `extraMetadata.main: dist/desktop/main.js`. electron-updater reads the same version (`app.getVersion()`) and its feed from `process.resourcesPath`, the directory that holds `app.asar`.
- **`asarUnpack` has one source: `ASAR_UNPACK` in `src/desktop/main/platform/unpacked-assets.ts`.** `electron-builder.yml` `asarUnpack` must equal it, and `app-paths.test.ts` fails when they drift. A file belongs there when something other than the main process's asar-patched `fs` reads it as a real file: the worker scripts (worker threads and the sentinel, which runs as Node in a separate process), the tree-sitter grammars and `web-tree-sitter` (read from the unpacked compass worker), the Python sidecar package (Python cannot import from an archive), ripgrep (`spawn` cannot execute a file inside an asar) and the native Node-API prebuilds of koffi and `@parcel/watcher`. A new consumer that hands a bundled file to a worker, a child process or another runtime adds its path to `ASAR_UNPACK`; it never relies on reading that file through the archive. `scripts/verify-desktop-package.mjs` checks the unpacked tree of every CI build.
- **Fuses are set by electron-builder and read back from every built binary** (`electron-builder.yml` `electronFuses`, `scripts/verify-desktop-package.mjs`, which reads the fuse wire with `@electron/fuses` `getCurrentFuseWire` on each CI leg). `runAsNode` is enabled; `enableNodeOptionsEnvironmentVariable`, `enableNodeCliInspectArguments` and `grantFileProtocolExtraPrivileges` are disabled; `enableEmbeddedAsarIntegrityValidation`, `onlyLoadAppFromAsar` and `enableCookieEncryption` are enabled. Never weaken a fuse to make a test pass and never add an app-side environment hook instead: with `--inspect` disabled, Playwright's `_electron.launch` cannot attach to a packaged app, so tests against the packaged app drive its renderers through `--remote-debugging-port`, which reaches renderers only.
  - **`runAsNode` stays enabled because the POSIX shell sentinel needs it.** `startShellSentinel` spawns `process.execPath` with `ELECTRON_RUN_AS_NODE=1`, and the sentinel must outlive a crash of the main process, which a `utilityProcess` does not. Residual risk, accepted: a process already running as the user can use the Damocles binary as a Node interpreter and inherit the app's OS permissions, including its macOS privacy (TCC) grants. VS Code keeps the fuse enabled for the same reason.
  - **With `enableNodeOptionsEnvironmentVariable` off, the packaged app ignores an inherited `NODE_EXTRA_CA_CERTS`.** Electron strips it together with `NODE_OPTIONS` at startup, so `installCaCertificates` trusts the bundled roots and the OS store only. On macOS and Linux the file is still added when the login shell environment merge brings the variable back (it is set in the user's shell profile); on Windows, where there is no merge, it is never read. Corporate CAs belong in the OS certificate store. The VS Code extension and the unpackaged dev app are unaffected. Do not turn the fuse on to restore the variable: it would reopen `NODE_OPTIONS` injection.
  - **Files under `app.asar.unpacked` are outside the asar integrity check.** Electron validates asar integrity on macOS and Windows only, so on Linux `app.asar` itself is unchecked too and the root-owned `/opt/Damocles` is the whole protection. Where it runs, integrity validation covers `app.asar` only, so the unpacked worker scripts (which run inside the app), `sentinel.js`, the Python package, the grammars and the native modules are protected only by the install directory's file permissions: root-owned under `/opt/Damocles` on Linux, the user's own `%LOCALAPPDATA%\Programs` on a per-user Windows install, and `/Applications` on macOS.
- **Linux never runs without the Chromium sandbox.** Nothing launches the Damocles binary or its Chromium processes with `--no-sandbox` (not the app, its scripts, CI or the docs), and there is no AppImage, whose electron-builder workaround is exactly that flag. Ubuntu 24.04 and later restrict unprivileged user namespaces, so the deb and rpm `afterInstall` script (`build/linux/after-install.sh`) installs `/etc/apparmor.d/damocles`, an unconfined profile that grants `userns` to `/opt/Damocles/damocles` only, and reloads that one profile. It installs nothing when AppArmor is absent or older than 4.0, and it never fails the install on an AppArmor error. `after-remove.sh` removes the profile only on a real removal, never on an upgrade. The script makes `chrome-sandbox` setuid instead on kernels without unprivileged user namespaces, and when AppArmor restricts them (`kernel.apparmor_restrict_unprivileged_userns=1`) but the profile did not load, so Chromium falls back to its setuid sandbox rather than failing to start. Residual, accepted: AppArmor keeps an unconfined profile's label across exec of a binary with no profile of its own, so every descendant (agent shell commands, `git`, MCP servers, the voice sidecar) may create user namespaces too. That is the posture Ubuntu ships for Chrome and VS Code. `build/linux/**` is LF through `.gitattributes`, because a CRLF shebang or profile fails on Linux.
- **The update model differs per OS, and the feed is only the packaged `resources/app-update.yml`** (`src/desktop/main/updater.ts`). The updater starts after the window is up, returns before it loads electron-updater, and is off in the unpackaged app. It never calls `setFeedURL`, never sets `forceDevUpdateConfig` or `updateConfigPath`, and reads no environment variable or argument; `updater.test.ts` guards all of these. `allowPrerelease` is off, so every platform reads the latest stable release.
  - Windows and Linux download in the background, then offer **Restart Now**; a dismissed update installs on quit (`autoInstallOnAppQuit`). Linux deb and rpm install through electron-updater's own `pkexec` path; the app adds no elevation of its own.
  - Windows sets `autoUpdater.channel` to `latest-<arch>` because both architectures release from one tag and would otherwise both write `latest.yml`; electron-builder's combined multi-arch NSIS installer is not an option (non-deterministic `files` order since 26.0.13, issue 9745). `allowDowngrade = false` is set after the channel, because electron-updater's channel setter turns downgrades on. Feeds: `latest-x64.yml`, `latest-arm64.yml`, `latest-mac.yml`, `latest-linux.yml`, `latest-linux-arm64.yml`.
  - macOS cannot apply an update without a Developer ID signature (Squirrel.Mac checks the signature against the installed app), so `autoDownload` is off and an available update raises a notice whose one action opens `https://github.com/AizenvoltPrime/damocles/releases/tag/v<version>` through `ShellService.openExternal`. The version must match a plain release version pattern first, so a feed cannot turn the notice into another URL. Adding a Developer ID later is configuration only; see `docs/desktop-signing.md`.
  - electron-updater both emits `error` and rejects with the same error. The updater handles both and logs each error once through the log sink, so an update failure can neither crash the main process nor raise an unhandled rejection. A failed check (offline, a captive portal, a firewall blocking GitHub) is only logged, because it would otherwise warn on every such launch; once an update was found, the first failure to download, install or offer it shows one warning per run.
  - Update tests point an installed test copy at a loopback feed by rewriting its `resources/app-update.yml` (`scripts/desktop-update-override.mjs`, driven by `e2e/desktop/update/drive-update.mjs`). That file sits outside `app.asar`, so the app needs no test hook; the writer accepts only an `http://127.0.0.1:<port>/` generic feed and only over the packaged GitHub config.

## Tests

- Every test file runs under its own temp home: `src/__mocks__/hermetic-home.setup.ts` points `USERPROFILE` and `HOME` at a fresh dir before any module reads `os.homedir()`, so nothing a test writes through `DAMOCLES_HOME_DIR` reaches the developer's real `~/.damocles`. That setup file must never import `paths.ts`, which freezes the home at import.
- Those homes live under one per-run root that `src/__mocks__/test-home.global-setup.ts` removes in its teardown. Cleanup belongs there and not in a per-file `afterAll`: vitest skips a file's hooks when every test in it is skipped or filtered out by `-t`, and the teardown runs after the fork workers exit, when Windows has released their file handles.
- The redirect needs vitest's `forks` pool, pinned in `vitest.config.ts`. In a worker thread, `process.env` writes do not reach `os.homedir()`.
- **Desktop end-to-end launches stay off the developer's keyring** (`e2e/desktop/support/hermetic.ts`). Each launch gets a temp home and an allowlisted environment with `DBUS_SESSION_BUS_ADDRESS=disabled:`, because libsecret otherwise finds the session bus through `$XDG_RUNTIME_DIR/bus` and safeStorage reads and writes the real Linux keyring. `DAMOCLES_E2E_OS_KEYRING=1` opts in, and only then does `secrets.spec.ts` "encrypted at rest" run on Linux. On macOS every launch runs with `--use-mock-keychain`: Playwright's Electron loader appends it (with `--password-store=basic`) to each dev launch, and `support/packaged-app.ts` and `update/drive-update.mjs` pass the same two switches, because the real Keychain's modal prompt blocks the main thread on a runner and would add the app's Safe Storage item on a developer's Mac. Windows DPAPI stores nothing outside userData.

## Packaging

- **The VSIX node_modules allowlist is generated, never hand-edited** (`scripts/sync-vscodeignore.mjs`, run through `npm run sync:vscodeignore`). `.github/workflows/release.yml` runs the script with `--check` on `ubuntu-latest` while developers generate the block on their own machines, so every pattern it emits has to be identical on every platform. A native binary package therefore collapses to a family glob (`@vscode/ripgrep-win32-x64` becomes `@vscode/ripgrep-*`), and a name that is nothing but platform tokens collapses to its scope (`@esbuild/win32-x64` becomes `@esbuild/*`). A literal platform name in the block fails `--check` on the release runner and aborts the tag push before the package matrix runs. `scripts/__tests__/sync-vscodeignore.test.ts` pins both halves.
- **Desktop-only packages never enter the VSIX closure.** `DESKTOP_ONLY_PACKAGES` in `scripts/sync-vscodeignore.mjs` is the desktop externals the extension lacks (`electron`, `@parcel/watcher`, `electron-updater`), `undici`, which the desktop bundle inlines while pi ships its own nested copy, and the desktop build and test tools (`monaco-editor`, `@playwright/test`, `playwright`, `playwright-core`, `electron-builder`, `app-builder-lib`, `app-builder-bin`, `dmg-builder`), plus every package under the `DESKTOP_ONLY_PACKAGE_PREFIXES` `@electron/` and `@parcel/watcher-`; the closure walk fails when one of them reaches it.
- **Desktop files never enter the VSIX.** `DESKTOP_EXCLUDE_RULES` in the same script lists the `.vscodeignore` lines that keep out the desktop build (`dist/desktop/**`, `dist/desktop-shell/**`), electron-builder output (`dist-desktop/**`), the Monaco assets, the end-to-end suite and its output (`e2e/**`, `dist/e2e*/**`), the Linux package files (`build/**`), typecheck stubs (`types/**`), the desktop configs and every `**/*.log`. `--check` fails when a rule is missing or a negation could re-include one of them, and `--check-vsix-listing` checks the file list of a real built VSIX on every release leg.
- **The Electron binary is never downloaded by `npm ci`.** `electron` has no install script: its `index.js` downloads the binary the first time something requires it. So the VSIX jobs never fetch it, and anything that runs Electron downloads it first with the package's own idempotent `install-electron` bin: `npm run test:desktop` and `npm run dev:desktop` do, and the release workflow's `package-desktop` legs do right after `npm ci`, because the Linux legs make `node_modules/electron/dist/chrome-sandbox` setuid before any test runs. Without it, two Playwright workers race to download and extract into the same `dist/`.
- **The desktop Monaco editor never enters the VSIX or the VS Code webview's eager bundle.** Everything reachable only through the editor overlay's dynamic import (`src/webview/components/editor/EditorOverlayHost.vue`) is emitted as `dist/webview/assets/monaco-*`: JS chunks, the per-language tokenizer chunks, both workers, the extracted CSS and the codicon font; the settings schema is inlined into those chunks. `vite.config.ts` computes that set from the module graph, and its build fails when a chunk mixes Monaco-only and eager modules, when a non-prefixed chunk statically loads a `monaco-` file or bundles a `monaco-editor` module, or when a prefixed chunk loads an unprefixed CSS or asset file. `.vscodeignore` excludes `dist/webview/assets/monaco-*`, and `sync-vscodeignore.mjs` (both modes) fails when that rule is missing or a negation could re-include a Monaco file. Every URL Vite writes into JS is relative to the file that holds it (`experimental.renderBuiltUrl`), because the desktop app serves the bundle under `app://damocles/webview/` and a root-absolute `/assets/` URL (the default for base `/`) misses it; that is also why the preload helper takes `import.meta.url` at every lazy call site. The root `dompurify` range stays `~3.3.2` so `monaco-editor`'s exact `dompurify` pin nests under it instead of replacing the copy the VS Code webview bundles.
- **The settings schema is committed and checked, not generated per build only.** `npm run build:webview` regenerates it and `scripts/__tests__/generate-settings-schema.test.ts` fails when the committed file is stale, so `tsc` resolves the import on a fresh clone. The generator imports `parseContributedConfiguration` from `src/core/config/contributed-configuration.ts` through Node's type stripping, so that file must stay erasable TypeScript with `node:` imports only.
- **Attribution ships inside the VSIX and the desktop app.** `.vscodeignore` excludes `*.md` and re-includes `THIRD-PARTY-NOTICES.md` outside the generated block; `electron-builder.yml` packs `LICENSE` and `THIRD-PARTY-NOTICES.md` into `app.asar` and copies Monaco's `ThirdPartyNotices.txt` into `resources/`, and `scripts/verify-desktop-package.mjs` fails a package without them. A library that esbuild or Vite bundles ships no `node_modules` copy of its license, so adding one means adding its entry to `THIRD-PARTY-NOTICES.md`. The bundled word lists' credits (CC BY and MIT) are `/*!` legal comments emitted by `scripts/generate-reference-words.mjs`, which esbuild keeps in the minified bundle. Setting esbuild's `legalComments` to `none` or turning that header back into `//` comments strips that credit from the bundle.
- **The closure walk follows Node resolution, so it must climb the whole ancestor `node_modules` chain.** Checking the immediate parent and then jumping to the project root reports the hoisted top-level copy for any dependency npm nested to satisfy a version conflict, and that copy can be a devDependency the extension never loads. That is how a 10 MB Windows compiler binary reached the VSIX: `@earendil-works/chord` requires `esbuild@0.28.2`, npm nested it under `@earendil-works/pi-coding-agent`, and the walk reported our build-time `esbuild@0.24.2` instead. `assertNoDevOnlyPackages` fails the run when a devDependencies-only package reaches the closure, and names the package that asked for it.
- **Known exception, reported upstream: seven nested `@earendil-works/*` lock entries carry `resolved` with no `integrity`, so `npm ci` fetches those tarballs with no subresource check.** All seven are the copies npm writes under `node_modules/@earendil-works/pi-coding-agent/node_modules/`. For five of them (`chord`, `pi-agent-core`, `pi-ai`, `pi-telemetry`, `pi-tui`) another entry for the same version carries an `integrity` hash; `pi-codemode` and `pi-mcp` have no other entry, so nothing checks their tarballs. Do not describe those other entries as the top-level ones: which copy npm hoists, and whether a package has a second entry at all, changes whenever the dependency set does. The omission is upstream rather than local. pi ships its own `npm-shrinkwrap.json`, that file carries `resolved` with no `integrity` for exactly these seven, and npm copies the gap into our lockfile, so no amount of regenerating or cache-clearing fixes it here. The cache is not a variable: pi-coding-agent's own top-level entry does carry an `integrity` hash, and the shrinkwrap ships inside that verified tarball. Never hand-edit a hash into `package-lock.json`: a hand-written value is unverifiable and turns a missing check into a false one.
