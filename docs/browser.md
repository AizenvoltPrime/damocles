# Damocles browser

This page covers the integrated browser: how its pages open in VS Code and the desktop app, the tools the agent gets, how credentials and dialogs are handled, and its known limits.

The browser is enabled by default; turn it off in Settings › Tools & integrations or via `damocles.browser.enabled`.

## Pages and tabs

In VS Code every open page is its own editor tab with its own toolbar (back, forward, reload, URL bar, element picker, DevTools, new tab), so you can split or drag browser tabs like any other editor and both panes keep rendering live. Each page belongs to the chat that opened it and closes when that chat closes. After a window reload a page reopens in its chat, the sidebar's chat included, once that chat is shown again, however long that takes; a page of a project or design file reopens from the file at a new address. A page whose chat does not come back stays closed.

In the desktop app a conversation's pages open as tabs in the editor pane, with the same toolbar: a page opens without taking the cursor out of the message box, selecting another conversation swaps in its pages, View › New Browser Page opens another, and pages come back after a restart. A conversation with open pages stays loaded, and deleting the conversation closes its pages.

Each tab shows the live title and favicon. A self-healing screencast watchdog recovers a stalled view, and if Chrome exits unexpectedly the browser tabs close with a notification. Pages a site opens itself, `window.open` and `target="_blank"` links, are captured as tabs.

## Engine

The browser runs on **Patchright**, a stealth-hardened Chromium/Playwright engine that never calls `Runtime.enable` (the biggest CDP automation tell), scrubs the automation user-agent, and drives interactions through Playwright locators, so bot-protected pages load normally.

## Agent tools

The agent gets a full tool set for navigation, interaction (click, type, fill, select, hover, drag, upload), and reading (screenshot, DOM query, snapshot, evaluate), plus multi-tab control (`BrowserTabs` for list/open/switch/close), file downloads (`BrowserDownloads`), and request interception/mocking (`BrowserIntercept`). Both belong to the chat: `BrowserDownloads` lists only the files the chat's pages downloaded, and a `BrowserIntercept` rule applies only to the chat's own pages, its subagents' and team agents' pages included, and ends when the chat or the browser closes. A page a site opens gets its chat's rules once Damocles has taken it over, so its first load is not intercepted. `BrowserUpload` of a folder copies it into the browser profile first, and before copying anything refuses a folder past `damocles.browser.uploadFolderMaxEntries` or `damocles.browser.uploadFolderMaxSize` ([Configuration](configuration.md)) or one the disk has no room for at 1.5 times its size.

No page in the agent's browser ever opens from disk. `BrowserOpen`, `BrowserNavigate` and `BrowserTabs` (a new tab) of a `file://` address, a Windows path (`C:\...`, `\\server\share\...`) or `view-source:` of one, inside the chat's project (a worktree chat's working folder) or its design folder, load the file from a local http server Damocles runs for that folder, in the desktop app and in VS Code. A project's pages work as on a dev server: relative links, module scripts and `fetch` of the project's files work, and in an untrusted project the pages run no scripts. A design's pages load their own styles, images and fonts, run scripts (their own and inline ones) only when the design is interactive, and never fetch, open a socket, frame another page or start a worker. A folder address (`file:///home/you/app/` or `file:///home/you/app/docs/`) opens that folder's `index.html`, and the address's query and `#fragment` reach the page. The agent still sees the `file://` address in every answer. Files and folders whose names start with a dot, keys, certificates and 8.3 short names are never served. A file outside those folders asks you first, on an approval card that names the file and the folder Damocles would serve and says that the page can read every file in that folder and its subfolders. Approving it serves that folder to this chat until the chat closes, with the same rules as the project: dot files, keys and certificates are never served, no link leads out of the folder, and its pages run no scripts unless you trusted that exact folder in the desktop app. Later pages in that folder open without asking; another chat asks again; nothing is kept after a restart, so a tab of such a folder is not reopened. Rules decide the card as they decide other asks: a deny rule naming the tool blocks the page, an allow rule naming the tool and YOLO open it without asking and serve its folder, plan mode asks, and a `Read` deny or ask rule covering the page decides too. Damocles never serves a drive, share or file system root, your home folder or a folder holding it, a hidden folder such as `~/.ssh` or `~/.damocles`, or a folder where applications or the system keep their data (any `AppData` folder, `ProgramData` and the Windows folder at a drive's root, on every drive and through WSL's `/mnt/c` and `\\wsl$` paths, `~/Library` on macOS, `/proc`, `/sys`, `/dev` and `/run` on Linux, the XDG folders) or a folder holding one (a drive's `Users` folder and each profile folder, and `/mnt/c` on WSL), while the temp folder and pnpm's store stay allowed, and refuses such a page without asking, telling the agent to move it into a subfolder; one chat is served at most 8 such folders. A project file is refused while Damocles has no server for the chat's project (the chat opened before its project, or the project was removed). A chat on a remote host follows the same rule (see [Remote development](remote-development.md#ports-and-the-browser)), except that its `BrowserTabs` opens no file page: open the tab, then `BrowserNavigate` to the file. Its folders outside the project are the host's, read on the host, and need a Damocles app and server that both serve them; with an older one the page is refused.

Every chat reaches its folders' server on an address of its own, `http://<random>.localhost:<port>`, with a cookie only that address gets, although all your chats share one browser profile. Damocles also checks each request a page makes to such an address against that page's chat, and the server refuses a request from another site: only the pages of the chat that holds the address, its subagents' and team agents' pages and the popups they open included, reach it. So one chat's agent, or a page it opened, never opens another chat's project, design or allowed-folder pages, even with an address it learned from the profile on disk; its navigation fails, saying that served page belongs to another chat. No `BrowserIntercept` rule changes this: a rule never answers a request for another chat's served page, in a frame from another site either, while on the chat's own served pages its rules apply as anywhere else. A page's own relative and `/`-rooted links work as on any site. A served page cannot install a service worker. A program running as you that decrypts the profile's cookie store could still replay such a cookie outside the browser, but such a program can already read your files directly. Answers name the page by its `file://` address, and a page or address of another chat that turns up in an answer is named "[a served page this chat cannot open]".

The agent's `BrowserOpen`, `BrowserNavigate` and `BrowserTabs` open only `http://` and `https://` addresses and `about:blank`, the same addresses the address bar takes; a file address takes the route above. Anything else is refused before Chrome sees it, with a message naming the scheme: browser pages such as `chrome://settings` or `edge://`, other `about:` pages, `javascript:` (use `BrowserEvaluate` to run script), `data:`, `blob:`, `filesystem:`, `view-source:` of a web page (the agent reads a page's source with `BrowserEvaluate` or a snapshot), `devtools://`, extension pages and addresses that start another app.

The same rule holds at every redirect a server sends. Damocles checks each such redirect of a browser page before Chrome follows it, so an agent's open or navigation whose redirect chain reaches `mailto:`, another app's scheme such as `ms-settings:`, or any other address outside the rule fails with a message naming the scheme, at the first redirect or a later one, and no app opens. `BrowserIntercept` rules do not change this. A page that redirects to such an address while you or the agent use it shows Chrome's error page.

Websites' service workers never answer the agent's pages. A worker a site installed, in an earlier version of Damocles or since, answers no request of a page Damocles has taken over, its same-site frames and its own workers' requests included, so each such request reaches the network, where these checks and `BrowserIntercept` rules apply. A popup's first page, before Damocles has taken it over, and a frame from another site, which Chrome runs in a process of its own, are the exceptions. A site may still install a worker, but it answers none of the agent's pages. Sites lose their offline mode in the agent's browser only.

The agent's browser preloads no page. A site's speculation rules ask Chrome to fetch a page, or prerender it, before a link to it is clicked, and Chrome makes that request outside the page Damocles watches, where neither these checks nor `BrowserIntercept` rules see it. Damocles turns Chrome's page preloading off, so a page a link opens loads when it is clicked. A test against real Chrome runs these checks every night in CI (`.github/workflows/browser-it-nightly.yml`), so a Chrome update that changes what they rely on is caught.

Some navigations Damocles cannot check, and Chrome handles them itself: a `mailto:` address opens your mail app's compose window, and any other app's address waits on Chrome's prompt, which nobody can answer in the agent's browser. These are a page's own link, script, meta refresh or `Refresh` header that opens an app's address directly, since such a navigation never makes a request; the first page a popup loads, before Damocles has taken it over; and a frame from another site, which Chrome runs in a process of its own.

An open or navigation reports its outcome as Playwright's `page.goto` does: a page that fails to load is a tool error naming Chromium's error, a page that loads with an HTTP error adds its status (`(HTTP 404)`), and an address that starts a download points to `BrowserDownloads`. Over Chromium's error page the address bar, the tab and the agent all show the address that failed.

**`BrowserRequestInput`** asks *you* to fill a form (login, MFA/OTP, payment) whose values are injected straight into the live page and are never seen by the model, logged, or persisted. Press Enter or click Submit.

The element picker attaches DOM/CSS/screenshot context to chat.

`BrowserConsole` reports what the page actually logged, captured by an in-page bridge, since the CDP console API is one of the automation tells Patchright disables. It also reports any `alert`/`confirm`/`prompt` Damocles auto-answered on the agent's behalf, so an accepted dialog is never silent.

## Tabs per agent

Each subagent and team agent drives its **own isolated tab** (the main agent and you share the conversation's tabs, and each conversation has its own), so concurrent agents never clobber each other's page. `BrowserTabs` and `BrowserClose` only see the calling agent's tabs, and an agent's tabs close automatically when it succeeds but stay open after a failure so you can inspect the page.

## Credential redaction

Everything a page produces is **credential-redacted at capture**: values under credential-shaped keys and self-identifying token formats (JWT, `Bearer`, PEM keys, vendor-prefixed keys) never enter the transcript or the session file, and a picked password field is masked rather than attached.

## DevTools port

The DevTools port is off by default. `damocles.browser.devToolsPort` launches the browser with a DevTools debugging port, an unauthenticated loopback endpoint that any local process can attach to and drive the browser as you, with your logged-in profile. It exists only to power the toolbar's DevTools button, and a relaunch is required because it is a launch-time Chromium flag.

## Known limitation

Popup-based "Sign in with Google" / Apple / Microsoft windows attach as tabs but headless Chromium does not paint popup surfaces ([Chromium 696439](https://crbug.com/696439)), so there is nothing to click. Same-window OAuth that redirects the parent page is unaffected. For popup providers, sign in via your normal browser before bringing the URL into the panel.
